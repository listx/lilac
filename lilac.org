* Introduction

Lilac v1 (LV1) is an Org extension, in that it does all of its work as
Emacs Lisp on top of Org.

Lilac v2 (LV2) is a native program which understands a strict subset of Org and
which runs very fast. Notably, it can tangle [[https://orgmode.org/manual/Noweb-Reference-Syntax.html][Noweb]] references and also weave
HTML in under a second for all but the largest Org files. This speed allows us
to have rapid feedback.

We say /strict/ subset because we often require things to be a certain way,
whereas Org can be more generous. For example, Lilac requires all internal links
to be named uniquely whereas Org does not.

** Motivation

Although LV1 can fix most of the nondeterminism issues of Org, the Org HTML
export can still be very slow. It can take 10+ seconds on large documents.
Performance is the main reason for LV2.

The other problem with Org is that the syntax highlighting of code blocks
only works properly if you are exporting to HTML interactively. If you use Emacs
in batch mode (non-interactively), the syntax highlighting won't work.

Yet another problem is that tangling doesn't work very well with =#+include=
statements; that is, if you use =#+include= you must tangle each included file
separately from the main one.

LV2 is designed to fix these shortcomings, while still using Org's syntax;
this way users can edit Org files in Emacs and still enjoy most of the benefits
of using Org interactively for day-to-day writing.

** Why not extend Pandoc?

Tangling code is beyond the scope of Pandoc.

** Why not use org-parser?

[[https://github.com/200ok-ch/org-parser/issues/56][Performance is too slow.]]

* Differences with vanilla Org

** Org subset

We only support a subset of Org, just enough to make it viable for doing
Literate Programming with Noweb references. Many of Org's other features like
timestamps and planning lines (TODO keyword, etc) are not given special meaning
during parsing (they will be output as plain text without any styling during
export).

We also do not support non-math Latex fragments (vanilla Org supports [[https://orgmode.org/manual/LaTeX-fragments.html][non-math
Latex fragments]]).

** Tangling

*** =#+include= support

Org does not support including other files when tangling. That is, if you
=#+include= other Org files into a bigger Org file, and tangle the bigger one, the
nested Org files' code blocks do not get tangled.

LV2 supports this.

*** Padding between Noweb references

Org supports adding blank lines between concatenated source code blocks with the
[[https://orgmode.org/manual/Extracting-Source-Code.html][=padline= header argument]]. However this does not work for Noweb references.

For example, a blank line is inserted between =foo= and =bar= and =bar= and =baz=:

#+header: :tangle doc/tangling-padline.txt
#+begin_src txt
foo
#+end_src

#+header: :tangle doc/tangling-padline.txt
#+begin_src txt
bar
#+end_src

#+header: :tangle doc/tangling-padline.txt
#+begin_src txt
baz
#+end_src

But the same blank lines are not inserted for the following case using =Noweb
chunk= as a Noweb reference.

#+header: :tangle doc/tangling-padline-noweb.txt
#+begin_src txt
<<Noweb chunk>>
#+end_src

#+header: :noweb-ref Noweb chunk
#+begin_src txt
foo
#+end_src

#+header: :noweb-ref Noweb chunk
#+begin_src txt
bar
#+end_src

#+header: :noweb-ref Noweb chunk
#+begin_src txt
baz
#+end_src

** Weaving

*** HTML only

We only support weaving HTML output. Other exporters don't exist yet.

*** Noweb expansion disabled

Noweb references are never expanded during weaving. This is equivalent to the
=no-export= option described at
https://orgmode.org/manual/Noweb-Reference-Syntax.html.

* Design

** Language and libraries

We use Haskell for speed and Megaparsec for parsing Org syntax.

** Features

  - HTML export

  - syntax highlighting for code blocks

  - internal link checker (checks if links to headings and other files are
    broken)

** Summary of main parts

*** Org parser

This step parses the raw =.org= text into something more usable. These data
structures remain the source of truth for all subsequent operations.

*** Input validation

The first step before doing anything is to check that the input conforms to our
expectations. If there are any problems, we say so during parsing and reject the
input.

*** Tangling

Tangling requires two main things:

  1) finding all =:tangle= targets defined in code blocks

  2) expanding all Noweb references

The second step involves doing a topological sort, so that we know which
reference we can expand first.

*** Weaving

Weaving requires adding markup to the output so that things get displayed in an
aesthetically pleasing way. This part isn't very interesting and is quite
mechanical.

**** Split output

We allow the user to specify whether they want the entire Org file to be
woven as a single HTML page, or as a collection of smaller pages.

  pkgs,
  compiler,

  util = import ./util.nix {
    inherit pkgs;
    inherit (pkgs) lib gitignoreFilter;
  };

  conf = lib.importTOML ../lilac.toml;

  ghcVersion =
    if compiler != null
    then compiler
    else conf.ghc.version;

  ghcVer = "ghc" + util.removeChar "." ghcVersion;

  hlib = pkgs.haskell.lib;

  confPkg = pkg: let
    usingOr = x: b:
      if conf.ghc ? ${x}
      then conf.ghc.${x}
      else b;
    confFns =
      [
        hlib.dontHyperlinkSource
        hlib.dontCoverage
        hlib.dontHaddock

          "--ghc-option=+RTS"
          "--ghc-option=-A256m" # allocation area size
          "--ghc-option=-n2m" # allocation area chunksize
          "--ghc-option=-RTS"
        ])
      ]
      ++ pkgs.lib.optional (! (usingOr "optimise" true)) hlib.disableOptimization
      ++ pkgs.lib.optional (usingOr "profiling" false) hlib.enableExecutableProfiling
      ++ pkgs.lib.optional (usingOr "benckmark" false) hlib.doBenchmark
      ++ pkgs.lib.optional pkgs.stdenv.isAarch64 (hlib.compose.appendConfigureFlag "--ghc-option=-fwhole-archive-hs-libs");
  in
    lib.pipe pkg confFns;

  hlsDisablePlugins =
    pkgs.lib.foldr
    (plugin: hls: hlib.disableCabalFlag (hls.override {${"hls-" + plugin + "-plugin"} = null;}) plugin);

  # Create your own setup using the choosen GHC version (in the config) as a starting point
  ourHaskell = let
    # https://github.com/pwm/nixkell#direct-hackagegithub-dependencies
    depsFromDir = hlib.packagesFromDirectory {
      directory = ./packages;
    };

    manual = hfinal: hprev: {
      haskell-language-server =
        hlsDisablePlugins hprev.haskell-language-server conf.hls.disable_plugins;

      lilac = let
        cleanSource = util.filterSrc {
          path = ../.; # Root of the project
          files = conf.ignore.files;
          paths = conf.ignore.paths;
        };
      in
        confPkg (hprev.callCabal2nix "lilac" cleanSource {});
    };
  in
    pkgs.haskell.packages.${ghcVer}.extend (
      lib.composeManyExtensions [
        depsFromDir
        manual
      ]
    );

  # Add our package with its dependencies to GHC
  ghc = ourHaskell.ghc.withPackages (_:
    hlib.getHaskellBuildInputs (
      # Tell getHaskellBuildInputs to include benchmarkHaskellDepends
      # so that they are available in the shell for cabal to use them
      hlib.doBenchmark ourHaskell.lilac

  haskellTools = builtins.map (p: ourHaskell.${lib.removePrefix "haskellPackages." p}) conf.env.haskell_tools;

  tools = builtins.map util.getDrv conf.env.tools;

  # See https://nixos.wiki/wiki/TexLive for customizing texlive packages

  tex = pkgs.texlive.combine {

      (pkgs.texlive)

      dvisvgm

      fontspec
      hyperref
      luatex85
      metafont
      pgf
      sourcesanspro
      standalone
      xkeyval
      ;
  };

  scripts = import ./scripts.nix {inherit pkgs;};
in {
  inherit conf ourHaskell ghc confPkg; # TODO: remove

  bin = ourHaskell.lilac;

  shell = pkgs.buildEnv {
    name = "lilac-env";
    paths = [ghc] ++ haskellTools ++ tools ++ scripts ++ [tex];
  };

The last imported Nix code is =nix/util.nix=, which has some helper functions.

#+header: :tangle nix/util.nix
#+begin_src nix
{
  pkgs,
  lib,
  gitignoreFilter,
}: {
  /*
   Check whether a given list has an element

  > has "b" [ "a" "b" "c" ]
  true
  > has "d" [ "a" "b" "c" ]
  false
  */
  has = e: xs: lib.any (x: x == e) xs;

  /*
   Remove an element from a list

  > remove "b" ["a" "b" "c"]
  [ "a" "c" ]
  > remove "d" ["a" "b" "c"]
  [ "a" "b" "c" ]
  */
  remove = e: builtins.filter (x: e != x);

  /*
   Remove dots from strings

  > removeChar "." "9.2.3"
  "923"
  */
  removeChar = c: s: lib.replaceStrings [c] [""] s;

  /*
   Given a package return its derivation

  > getDrv "haskellPackages.implicit-hie"
  «derivation /nix/store/qb9j7iccna81dcs1szwryl4izli95w53-implicit-hie-0.1.2.7.drv»
  */
  getDrv = path: lib.getAttrFromPath (lib.splitString "." path) pkgs;

  # Filter using .gitignore + ignore files and paths defined in the config
  filterSrc = {
    path,
    name ? (baseNameOf path + "-src"),
    files ? [],
    paths ? [],
  }:
    lib.cleanSourceWith {
      src = path;
      inherit name;
      filter = let
        gitIgnore = gitignoreFilter path; # in let binding to memoize
        relToPath = lib.removePrefix (toString path + "/");
      in
        path: type:
          gitIgnore path type
          && ! builtins.elem (baseNameOf path) files
          && ! lib.any (d: lib.hasPrefix d (relToPath path)) paths;
    };
}

*** Linters

**** Audit tangled vs tracked files

Run a script which can detect whether we've accounted for all tracked files via
Literate Programming. That is, we want to detect any files that are checked into
source control without being tangled from an Org file.

#+header: :tangle check-tangled.sh
#+header: :shebang #!/usr/bin/env bash
#+begin_src bash
set -euo pipefail

SCRIPT_ROOT="$(dirname "$(realpath "$0")")"

# Files which are tracked outside of our tangling step, but for legitimate
# reasons (generated code, symlinks to dependencies, or LICENSE files,
# typically).
known_not_tangled=(
	LICENSE

	# Generated by Niv.
	nix/sources.json
	nix/sources.nix

	# Images.
	image/PNG-Gradient.png

	# Will become obsolete when we start pulling in Haskell packages from
	# Hackage or GitHub directly.
	nix/packages/.gitkeep
)

# List all files we explicitly tangle from Org files.
tangled_files()
{
	git -C "${SCRIPT_ROOT}" grep -P '^#\+header: :tangle' -- '*.org' \
		| awk '{print $3}' \
		| sort -u
}

# List all files checked into version control.
tracked_files()
{
	git -C "${SCRIPT_ROOT}" ls-tree -r HEAD \
		| awk '{print $2,$4}' \
		| grep '^blob' \
		| grep -v '\.\(html\|org\)$' \
		| awk '{print $2}'
}

main()
{
	echo >&2 -n "$0: checking tangled vs tracked files... "
	# Combine tangled files and those which are tracked but not tangled. This
	# list should match the sum of all tangled files (modulo HTML and Org
	# files).
	if diff -u \
		<(printf '%s\n' "$(tangled_files)" "${known_not_tangled[@]}" | sort) \
		<(tracked_files); then

		echo >&2 "OK"
	else
		echo >&2 "$0: failed"
		return 1
	fi
}

main "$@"
#+end_src

**** Audit missing newlines

Except for generated files, all files should have a trailing newline (line feed
character). That is, the last byte should be =\n=.

#+header: :tangle check-newlines.sh
#+header: :shebang #!/usr/bin/env bash
#+begin_src bash
set -euo pipefail

SCRIPT_ROOT="$(dirname "$(realpath "$0")")"

# Generated files (and binary files) should be excluded from this check.
excluded=(
	image/PNG-Gradient.png
)

check_trailing_newlines()
{
	local res=0
	mapfile -t files < <(git -C "${SCRIPT_ROOT}" ls-tree -r HEAD \
		| awk '{print $2,$4}' \
		| grep '^blob' \
		| awk '{print $2}')

	for f in "${files[@]}"; do
		# Skip empty files.
		if [[ ! -s "$f" ]]; then
			continue
		fi

		# Skip excluded files.
		if [[ " ${excluded[*]} " =~ [[:space:]]${f}[[:space:]] ]]; then
			continue
		fi

		if ! tail -c 1 "$f" | read -r line; then
			echo >&2 "$0: $f does not end in a trailing newline"
			res=1
		fi
	done
	return "${res}"
}

main()
{
	echo >&2 -n "$0: checking trailing newlines... "
	if check_trailing_newlines; then
		echo >&2 "OK"
	else
		echo >&2 "$0: failed"
		return 1
	fi
}

main "$@"
#+end_src

#+header: :tangle .github/workflows/nix.yml
#+begin_src yaml
name: CI

on:
  push:
    branches:
      - next
  pull_request_target:
  workflow_dispatch:

jobs:
  nix:
    name: ${{ matrix.os }} / ghc ${{ matrix.ghc }}
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os:
          - ubuntu-latest
          - macOS-latest
        ghc:
          - "<<GHC version>>"

    steps:
      # https://github.com/dependabot/dependabot-core/issues/3253#issuecomment-799466911
      - uses: actions/checkout@v4
        if: ${{ github.event_name == 'pull_request_target' }}
        with:
          ref: ${{ github.event.pull_request.head.sha }}
      - uses: actions/checkout@v4
        if: ${{ github.event_name != 'pull_request_target' }}

      - name: Free disk space (Ubuntu only)
        if: runner.os == 'Linux'
        uses: jlumbroso/free-disk-space@main

      - name: Set nix path
        id: nix-path
        run: |
          echo "nixpkgs=$(jq -r .nixpkgs.url ./nix/sources.json)" >> $GITHUB_OUTPUT

      - uses: cachix/install-nix-action@v30
        with:
          nix_path: nixpkgs=${{ steps.nix-path.outputs.nixpkgs }}
          extra_nix_config: |
            log-lines = 1000

      - name: Print nixpkgs version
        run: |
          nix-instantiate --eval -E '(import <nixpkgs> {}).lib.version'

      - name: Check code formatting
        # For linting, we don't need to run it on Mac (just once on Linux is
        # enough).
        if: ${{runner.os == 'Linux'}}
        run: |
          nix-shell --run "make lint"

      - name: Build
        run: |
          make build-release

      - name: Run
        run: |
          result/bin/lilac

** Org parser

*** Overview

We use Megaparsec to parse an Org document. The parsing requires us to read in
everything in a single Org file. If there are any includes (=#+include ...= bits)
of other Org files, we have to parse them as well, recursively, and expand them
into the original Org file being parsed. If we detect any cyclic includes, we
error out.[fn:1]

*** Data structures

We use two major data structures for parsing. The first is an *list of
/cells/[fn:2]*, where each cell can be things like

  - [[https://orgmode.org/worg/org-syntax.html#Headings][headings]] (aka [[https://orgmode.org/manual/Headlines.html][headlines]]),
  - paragraphs (prose text),
  - ordered and unordered list items (can be nested),
  - blocks (code blocks, quotations, examples, etc),
  - tables,
  - images, and
  - LaTeX fragments (typically equations).

This scheme is good for quickly making sense of the overall document
structure in linear fashion, start to finish. It also simplifies the parsing
data structure (we just parse one cell after the other). It's worth mentioning
that using a tree data structure for the headings (which naturally form a
tree-like hierarchy) could be useful for situations where tree-based
manipulations are desirable; however we will never need to do this for purposes
of weaving the Org input into HTML (or any other format). Hence our use of a
cell list.

The second major data structure is a *directed acyclic graph (DAG) for tangled
code blocks*, which we call a *code graph*, for handling Noweb references. Noweb
code blocks can reference other Noweb code blocks, so we create a dependency
graph for each code block which will get tangled to a file. That is, each
would-be-tangled file has its own code graph. Note that multiple code blocks can
reference (depend on) the same code block, which is why this is a graph and not
a tree.

In summary an Org document is made up of cells and code graphs, as well as some
metadata (the title, author name, etc).

#+header: :noweb-ref Data structures
#+begin_src haskell
type OrgDoc :: Type
data OrgDoc = OrgDoc
  { cells :: [Cell],
    code :: [G.Graph],
    codeBlocks :: IM.IntMap Block,
    meta :: M.Map T.Text T.Text
  }
  deriving stock (Eq, Show)

#+end_src

We'll examine the =Cell= type first, followed by code graphs.

***** Heading

Headings start with asterisks without any indentation, followed by some prose
text (see the next section for a discussion of prose text). The number of
asterisks determine the (nesting) level. There can be any number of levels,
although there should be probably no more than 6 in a section that will be
exported as a single HTML page or PDF file.

The heading may also have some metadata associated with it. In practice this
will be keys and values from a =:PROPERTIES:= [[https://orgmode.org/manual/Drawers.html][drawer]], although other drawers are
possible. We store drawer information inside the =meta= hashmap, with the drawer
name acting as a key prefix (this way we can store multiple drawers, if there
are any, in a single hashmap).

Other than the level, each heading is made up of =Prose= text, which we consider
in the next section.

#+header: :noweb-ref Data structures
#+begin_src haskell
type Heading :: Type
data Heading = Heading
  { level :: Int,
    body :: Prose,
    meta :: M.Map T.Text T.Text
  }
  deriving stock (Eq, Show)

#+end_src

***** Prose

Prose is the simplest. It's a series of contiguous lines of text, which can have
some styling (bold, italic, etc) as well as links, citations, footnote links,
etc. We convert the paragraph content as a list of /tokens/.

#+header: :noweb-ref Data structures
#+begin_src haskell
type Prose :: Type
type Prose = [PToken]

#+end_src

A prose token, or =PToken=, can be a string (styled or otherwise), a link of some
sort, or a Latex fragment.

#+name: PToken ADT

type PToken :: Type
data PToken
  = PTokenStyledString StyledString

  deriving stock (Eq, Show)

#+end_src

The =StyledString= is just some text that has one or more styles attached to it.
If the string has no style, then it's not stylized at all (plain style).

****** =LinkNoweb=

Links to Noweb references. We've been using Noweb references already in this
document, but here's an isolated example.

#+begin_src sh
echo <<LinkNoweb example>>
#+end_src

The block above refers to a Noweb reference named =LinkNoweb example=. We define
it below:

#+header: :noweb-ref LinkNoweb example
#+begin_src sh
hello world
#+end_src

Note that if no such Noweb reference is defined, Lilac will error out.

****** =LinkHeading=

Links to headings. For example, [[*Blocks]] links to the next heading named "Blocks"
in this document.

Unlike in vanilla Org, a =LinkHeading= link must start with an asterisk. This is
why the example above says =*Blocks= and not just =Blocks= inside the double
brackets.

****** =LinkIdProp=
:PROPERTIES:
:ID:       f8254d58-7a3d-4595-a265-e0d6255e6ab5
:END:

Sometimes, multiple headings can share the same name. So we need another way to
refer to link to a heading. The =LinkIdProp= gives us a workaround.

You can create a property drawer for a heading. This heading has a =:PROPERTIES:=
drawer and inside it, an =:ID:= field with a UUID. The link
[[id:f8254d58-7a3d-4595-a265-e0d6255e6ab5][here]] is an example of a link using this id property.

To add such an =:ID:= to an existing header, run the =org-id-store-link= elisp
function.

****** =LinkNameKeyword=

Link to an entry with a =#+name: ...= property. They can be used for blocks,
figures, and tables.

#+name: ex:LinkNameKeyword
#+begin_example
foo bar
#+end_example

The link [[ex:LinkNameKeyword]] is an example.

Note that by default Org allows you to use the syntax =[[foo]]= to refer to
multiple kinds of links. Lilac is more restrictive and requires you to use the
format =category:name= where =category= can be one of:

  - ex :: example block
  - q :: quote block
  - src :: code block
  * * :: headings (as seen in [[*LinkHeading]], although note that there is no colon
    after the asterisk)
  - ... or something else

In other words the =category= is required. Using a category like this helps to
keep link names unique.

The link [[ex:LinkNameKeyword][here]] is an example.

One thing to keep in mind is that if the material is printed on physical paper,
the links named "here" won't make much sense to the reader. So if you are
writing for physical media, you should try to avoid "hiding" the target of links
behind names, and instead only use the link target.

****** =LinkFootnote=

Links to footnotes. A footnote is constructed specially and only requires single
instead of double brackets. This sentence ends with a footnote link.[fn:3]

****** =LinkExternal=

Links to some external resource, such as a web page on the internet or a file on
disk. That is, the link points to something that exists /externally/ to the Org
document at hand.

A web link looks [[https://kernel.org][like this]]. A link to a file can look [[./README.org][like this]]. Note that their
format allows them to be named differently than the raw address. That's why the
two links earlier in this paragraph are displayed as "like this". The format is

#+begin_example
[[target][name]]
#+end_example

where =[name]= is optional. If it is omitted, then the =target= part is used as the
name.

***** Blocks

/Blocks/ are regions of text that start with =#+begin<...>= and end with =#+end<...>=.
They are used to delineates source code (used for Noweb references), examples,
quotes, and others. They have associated metadata, and their contents are a list
of =BToken= types, which are quite similar to =Prose= (a list of =PToken= types).

#+end_src

A =BToken= can be either some raw piece of text, or a link.

  deriving stock (Eq, Show)

#+end_src

  - foo
  - bar

  - quux

  + foo
  - bar
    - baz
  + quux

***** Math fragments

In vanilla Org, Latex fragments begin with =\begin{<ENVIRONMENT>}= and
=\end{<ENVIRONMENT>}=, where =<ENVIRONMENT>= can be anything. Presumably you could
inject images and illustrations; however those other non-mathematical facilities
are already supported by other Org features such as external links, so we don't
support them here.

Instead Lilac only supports Latex fragments for typesetting math. Because we
only support math, we call them /math/ fragments.

There are two ways to write math fragments: using =\begin{equation}= and
=\end{equation}= for a standalone equation like this

\begin{equation}
2 + 2 = 4.
\end{equation}

or by using inline math delimiters like this: \(1 - 1 = 0\) which can be placed
inside of some prose text.

When using the standalone form, you can assign a =#+name= keyword to it to refer
to the equation using a human-friendly name, like this:

#+name: eq:Pythagorean Theorem
\begin{equation}
a^2 + b^2 = c^2
\end{equation}

and you can link back to it using an internal link like [[eq:Pythagorean Theorem]].

#+header: :noweb-ref Data structures
#+begin_src haskell
type MathFragment :: Type
data MathFragment = MathFragment
  { meta :: M.Map T.Text T.Text,
    body :: T.Text
  }
  deriving stock (Eq, Show)

#+end_src

**** Code graphs

The code graph is just a =Graph= (from =Data.Graph= in the =containers= Haskell
library), where a =Graph= is an adjacency list of integers. The integers
correspond to unique IDs assigned to each logical code block. As we parse the
Org file we assign an incrementing integer ID to each code block we encounter.

A single logical block can be spread across multiple cells (as described in
[[*Padding between Noweb references]]). In such cases, those blocks are concatenated
together (with a newline interspersed between the blocks), and treated as a
single block.

**** Parser helpers for whitespace and comments

Before writing our first parsers, we have to consider the problem of whitespace
and comments.

Any syntax that is expected to be used by humans have some designation for
whitespace to separate meaningful tokens from each other. One way to deal with
(necessary) whitespace is to bake in whitespace parsers into each token we want
to parse. This gets cumbersome so we want to instead be able to teach parsers to
be able to skip over trailing whitespace. This way, these parsers will all know
how to deal with whitespace in a uniform way. Leading whitespace is a special
consideration because they can have meaningful information (e.g., indentation
for list items), so we will handle that case separately.

A slightly separate problem is how to deal with comments. In a sense they are
just like whitespace because they hold no meaningful information on their own.
Luckily, =Text.Megaparsec.Char.Lexer= provides a =space= helper which can create a
space-consuming function. This function produces a parser which is able to skip
over any combination of whitespace and comments (both single-line and block
comments). This is what we use below to create the =spaceConsumer= function below.
See https://markkarpov.com/tutorial/megaparsec.html#lexing for more information.

#+header: :noweb-ref Parsing mechanism
#+begin_src haskell
spaceConsumer :: OrgParser ()
spaceConsumer =
  L.space
    whiteSpaceParser
    singleLineCommentParser
    blockCommentParser
  where
    whiteSpaceParser :: OrgParser ()
    whiteSpaceParser = space1
    singleLineCommentParser :: OrgParser ()
    singleLineCommentParser = (L.skipLineComment "# ")
    blockCommentParser :: OrgParser ()
    blockCommentParser = (L.skipBlockComment "#+begin_comment" "#+end_comment")

#+end_src

The three arguments to =L.space= (where =L= stands for =Text.Megaparsec.Char.Lexer=)
are the parsers for whitespace, single-line comments, and block comments.
It's important that we use =space1= here (where the =1= denotes that it requires at
least 1 space character) because otherwise if it accepts 0 or more spaces, it
may loop forever upon seeing non-space input.

The ="# "= for =singleLineCommentParser= signifies that single-line comments start
with a pound sign and a space. The =blockCommentParser= uses =L.skipBlockComment= to
denote a region of text which is considered a commented area.

We have two more helpers for us. The first is =symbol=, which parses any trailing
spaces or comments after parsing the given text.

#+header: :noweb-ref Parsing mechanism
#+begin_src haskell
symbol :: T.Text -> OrgParser T.Text
symbol = L.symbol spaceConsumer

#+end_src

Lastly we have =lexeme=, which wraps around any other parser to make it consume
trailing spaces and comments.

#+header: :noweb-ref Parsing mechanism
#+begin_src haskell
lexeme :: OrgParser a -> OrgParser a
lexeme = L.lexeme spaceConsumer

#+end_src

***** Treading carefully around newlines

The =spaceConsumer= is somewhat "aggressive" because it uses =space1= which consumes
all kinds of whitespace, including newlines. We define two other types of
space-consuming parsers. One which does not consume newlines at all, and another
which consumes everything except a double-newline (two newlines in a row).

The first case is easy because we just need to tweak the =whiteSpaceParser= to
only allow a space or tab character.

#+header: :noweb-ref Parsing mechanism
#+begin_src haskell
spaceConsumerNoNewline :: OrgParser ()
spaceConsumerNoNewline =
  L.space
    whiteSpaceParser
    singleLineCommentParser
    empty
  where
    whiteSpaceParser :: OrgParser ()
    whiteSpaceParser = void $ some (char ' ' <|> char '\t')
    singleLineCommentParser :: OrgParser ()
    singleLineCommentParser = (L.skipLineComment "# ")

symbolNoNewline :: T.Text -> OrgParser T.Text
symbolNoNewline = L.symbol spaceConsumerNoNewline

lexemeNoNewline :: OrgParser a -> OrgParser a
lexemeNoNewline = L.lexeme spaceConsumerNoNewline

#+end_src

For the second case, the =whiteSpaceParser= is a bit more involved. We need to
look ahead to see that the newline is not followed by another newline.

#+header: :noweb-ref Parsing mechanism
#+begin_src haskell
spaceConsumerNoDoubleNewline :: OrgParser ()
spaceConsumerNoDoubleNewline =
  L.space
    whiteSpaceParser
    singleLineCommentParser
    empty
  where
    whiteSpaceParser :: OrgParser ()
    whiteSpaceParser = void $ some f
    f :: OrgParser ()
    f = do
      MP.notFollowedBy (string "\n\n")
      void $ char ' ' <|> char '\t' <|> char '\n'
    singleLineCommentParser :: OrgParser ()
    singleLineCommentParser = (L.skipLineComment "# ")

symbolNoDoubleNewline :: T.Text -> OrgParser T.Text
symbolNoDoubleNewline = L.symbol spaceConsumerNoDoubleNewline

lexemeNoDoubleNewline :: OrgParser a -> OrgParser a
lexemeNoDoubleNewline = L.lexeme spaceConsumerNoDoubleNewline

#+end_src

**** =orgDocParser=

The =orgDocParser= first needs to parse any metadata associated with the document,
such as the title and author. It starts by skipping any leading
whitespace/comments. We have to do this first because all of the other parsers
we use will follow the pattern of parsing the thing we want, followed by
skipping over as much trailing whitespace as possible. In other words, none of
the parsers are able to deal with leading whitespace/comments, so we have to
deal with it here separately.

***** Document metadata

The first thing we need to parse is the document metadata. Metadata is a line
that looks like =#+key: value= where =key= is a string and =value= is a series of
tokens (it can have multiple words in it). This is what the =docMetaEntryParser=
parses.

#+header: :noweb-ref Parsing mechanism
#+begin_src haskell
docMetaEntryParser :: OrgParser (T.Text, T.Text)
docMetaEntryParser = do
  _ <- string "#+"
  key <- MP.takeWhile1P (Just "keyword letter") isKeywordLetter
  _ <- symbol ":"
  value <- MP.takeWhile1P (Just "value letter") (\c -> c /= '\n')
  pure (key, value)
  where
    isKeywordLetter c = or $ map ($ c) [isAsciiLower, (== '_')]

#+end_src

The =docMetaParser= just parses =docMetaEntryParser= one or more times, while
consuming any trailing whitespace or comments with the =lexeme= helper from
[[*Parser helpers for whitespace and comments]].

#+header: :noweb-ref Parsing mechanism
#+begin_src haskell
docMetaParser :: OrgParser (M.Map T.Text T.Text)
docMetaParser = do
  metaKVs <- many (lexeme docMetaEntryParser)
  pure $ M.fromList metaKVs

******* Styled strings

Styled strings are text strings with special formatting markers around them.
Here are some examples: *bold*, /italic/, _underline_, =verbatim=, ~code~, and +strike
through+.

The =styleMap= keeps track of the characters that activate and deactivate each
style. The full list of =Style= data constructors can be seen at [[data:Style]].

#+name: func:styleMap
#+header: :noweb-ref Parsing mechanism
#+begin_src haskell
styleMap :: M.Map Char Style
styleMap =
  M.fromList
    [ ('*', Bold),
      ('/', Italic),
      ('_', Underline),
      ('=', Verbatim),
      ('~', Code),
      ('+', Strikethrough)
    ]

#+end_src

Styled strings (for headings) are somewhat tricky, because of two main problems

  1) the markers use the same character for both activation and deactivation,
     and

  2) the styles can be nested.

You can have, for example, lines that are /italicized like this but also have
*bold text inside* of it/.

We approach these problems with a simple idea: use a *bit mask*, or =StyleMask=, to
keep track of markers. Every time we see a starting marker, we turn on the bit
in the mask to activate that style. If we see that the user is trying to turn on
a style which is already active, we fail with an error
([[test:0005-styled-strings-redundant-activations]]).

If the input is such that the markers are not balanced, such that by the time we
finish parsing a paragraph (or end of a heading) and the mask still has active
styles in it, we throw an error ([[func:failIfLeftOverActiveStyles]]). That is, we
expect style starting and ending markers to always be balanced. This deviates
from vanilla Org, which does not have this restriction.

#+name: func:failIfLeftoverActiveStyles
#+header: :noweb-ref Parsing mechanism
#+begin_src haskell
failIfLeftoverActiveStyles :: OrgParser ()
failIfLeftoverActiveStyles = do
  orgParserState <- get
  let (StyleMask mask) = orgParserState.styleMask
  when (mask /= 0) $ do
    fail
      $ "leftover active styles: "
      ++ (show $ maskToStyles $ StyleMask mask)

#+end_src

heading, expecting to see the ending style marker for bold text, but never see
it. So the failure from =failIfLeftoverActiveStyles= gets triggered.

Note that we don't wait until seeing the closing marker to see if we should
stylize the text at hand; the =StyleMask= is "strict" in this sense. This way, we
can start parsing stylized text without needing to see a corresponding ending
marker.

So the overall algorithm should be:

  1) Parse any leading style markers.

  2) Parse the non-style text (word without spaces in it).

  3) Parse any ending style markers.

The markers in steps 1 and 3 are optional. The key is that by the time we get to
Step 2, we know what the =StyleMask= looks like, so we can use that information
to stylize the text we found in Step 2. The function =styledStringParser=
implements the above algorithm.

#+header: :noweb-ref Parsing mechanism
#+begin_src haskell
styledStringParser :: OrgParser StyledString
styledStringParser = do
  orgParserState <- get

  let mask = orgParserState.styleMask
  startingMask <-
    toStyleMask
      =<< T.unpack
      <$> MP.takeWhileP
        (Just "starting style marker")
        isStyleMarker

  let (StyleMask overlappingBits) = styleMaskIntersect mask startingMask
  when (overlappingBits /= 0)
    $ fail
    $ "redundant style activations: "
    <> (show $ maskToStyles $ StyleMask overlappingBits)

  let activeMask = styleMaskAdd mask startingMask

  word <- MP.takeWhile1P (Just "prose word") isProseWord

  endingMask <-
    toStyleMask
      =<< T.unpack
      <$> MP.takeWhileP
        (Just "ending style marker")
        isStyleMarker

  let (StyleMask overzealousBits) = invalidDeactivations activeMask endingMask
  when (overzealousBits /= 0)
    $ fail
    $ "overzealous style deactivations: "
    <> (show $ maskToStyles $ StyleMask overzealousBits)

  put orgParserState {styleMask = styleMaskSubtract activeMask endingMask}

  pure
    StyledString
      { body = word,
        style = activeMask
      }
  where
    isStyleMarker c = M.member c styleMap
    isProseWord c = M.notMember c styleMap && (not $ isSpace c)

#+end_src

Because of the way =isStyleMarker= and =isProseWord= checks membership of the
characters used for activating (and deactivating) styles in [[func:styleMap]], there
is no way to "escape" these characters. Using any of them will immediately try
to activate or deactivate a style. So if you need to use a style marker
character, but don't want Lilac to interpret it as a style marker, you'd have to
enclose it inside verbatim or code styles. Like this =snake_case_word= with
underscores in it (because otherwise the underscores would get interpreted as a
style marker for underlined text).

That's it for the high level overview of how we parse styled strings. We now get
into the lower-level details of the =StyleMask= itself. The =StyleMask= is an 8-bit
word, which can hold boolean values for the 6 different =Style= data constructors,
e.g. [[data:Style][=Bold=, =Italic=]]. It's a space-efficient type to replace an equivalent map
or list of =[Style]= values. We use a =newtype= around a =Word8= (an 8-bit word) so as
to keep it distinct from =Word8= itself.

#+header: :noweb-ref StyleMask details
#+begin_src haskell
type StyleMask :: Type
newtype StyleMask = StyleMask Word8
  deriving stock (Eq)

#+end_src

We have a custom =Show= instance because the default =Show= would just treat the
=Word8= as a number. Instead we want to show what the binary bits (turned on
inside the =Word8=) would represent in terms of actual styles. We have to import
=Prelude= because of the way =Relude= redefines =show= (and we need to use the =show=
that =Prelude= uses; see [[https://github.com/snoyberg/basic-prelude/issues/67#issuecomment-221628073][this related discussion for the Basic Prelude library, a
Relude alternative, for reference]]).

#+header: :noweb-ref StyleMask details
#+begin_src haskell
instance Show StyleMask where
  show (StyleMask a) = "styleMaskFrom " <> x
    where
      x =
        Prelude.show
          . catMaybes
          . map
            ( \(i, b) ->
                if b
                  then (Just $ (toEnum i :: Style))
                  else Nothing
            )
          . zip [0 ..]
          $ toListLE a

#+end_src

The shown text string is prefixed with =styleMaskFrom= because that function is
used as a constructor function to create a =StyleMask= easily from scratch; it's
also used in test cases. This follows the tradition used in =Data.Map= where they
also use a constructor function (=fromList=) when =show=-ing a =Map= data structure.

#+header: :noweb-ref StyleMask details
#+begin_src haskell
styleMaskFrom :: [Style] -> StyleMask
styleMaskFrom ss = StyleMask $ foldl' f (0 :: Word8) ss
  where
    f :: Word8 -> Style -> Word8
    f acc s = setBit acc (fromEnum s)

#+end_src

Similarly, we sometimes want to go the other direction --- that is, deconstruct
a =StyleMask= into =Style=. So we have =maskToStyles=.

#+header: :noweb-ref StyleMask details
#+begin_src haskell
maskToStyles :: StyleMask -> [Style]
maskToStyles (StyleMask mask) = foldl' f [] $ zip [0 ..] $ toListLE mask
  where
    f :: [Style] -> (Int, Bool) -> [Style]
    f acc (idx, b) =
      if b
        then (toEnum idx) : acc
        else acc

#+end_src

We have a helper function =toStyleMask= to convert =[Char]= into a =StyleMask=. This
is used to construct style masks as they are read in from the input text. The
function runs inside a =MonadFail= monad, because we want to detect an invalid
sequence of characters. For example, the sequence =**foo= is wrong because it
declares the =Bold= style (=*=, or asterisk) twice in a row to activate it when we
only need it once. The use of =MonadFail= is seamless inside =ParsecT= (the monad we
use inside =OrgParser=), because =ParsecT= has a =MonadFail= instance.

#+header: :noweb-ref StyleMask details
#+begin_src haskell
toStyleMask :: (MonadFail m) => [Char] -> m StyleMask
toStyleMask cs = pure =<< stylesToStyleMask =<< charToStyles cs

charToStyles :: (MonadFail m) => [Char] -> m [Style]
charToStyles chars = foldlM f [] chars
  where
    f :: (MonadFail m) => [Style] -> Char -> m [Style]
    f acc c = case EM.lookup c styleMap of
      Just style -> pure (style : acc)
      Nothing -> fail $ "programmer error: unrecognized style marker " <> (show c)

stylesToStyleMask :: (MonadFail m) => [Style] -> m StyleMask
stylesToStyleMask ss = pure . StyleMask =<< foldlM f (0 :: Word8) ss
  where
    f :: (MonadFail m) => Word8 -> Style -> m Word8
    f acc s
      | testBit acc sInt = fail $ "stylesToStyleMask: redundant style marker: " <> (show s)
      | otherwise = pure $ setBit acc sInt
      where
        sInt = fromEnum s

#+end_src

Lastly we have some helpers to perform binary AND, OR, and XOR operations on two
=StyleMask= objects, so that callers don't have to perform the deconstruction and
reconstruction of the underlying =Word8= primitive themselves.

#+header: :noweb-ref StyleMask details
#+begin_src haskell
styleMaskIntersect :: StyleMask -> StyleMask -> StyleMask
styleMaskIntersect (StyleMask a) (StyleMask b) = StyleMask $ a .&. b

styleMaskAdd :: StyleMask -> StyleMask -> StyleMask
styleMaskAdd (StyleMask a) (StyleMask b) = StyleMask $ a .|. b

styleMaskSubtract :: StyleMask -> StyleMask -> StyleMask
styleMaskSubtract (StyleMask a) (StyleMask b) = StyleMask $ a .^. b

#+end_src

Before invoking =styleMaskSubtract=, we want to see if =StyleMask b= above is even
valid, when looking at =StyleMask a=. In particular we want to check that if there
are bits turned on in =b=, we want to see that those bits are indeed already on in
=a=. The function =invalidDeactivations= detects cases where this isn't true.

#+header: :noweb-ref StyleMask details
#+begin_src haskell
invalidDeactivations :: StyleMask -> StyleMask -> StyleMask
invalidDeactivations (StyleMask a) (StyleMask b) = StyleMask $ (complement a) .&. b
#+end_src

****** Drawers

Drawers look like

#+begin_example
:DRAWER_NAME:
...content...
:END:
#+end_example

and the =:PROPERTIES:= drawer is a special drawer that can contain values that Org
recognizes, such as an =:ID:= key and value to encode a UUID which can be used as
a link target from elsewhere in the document.

For simplicity we capture all of the values of a drawer inside a single map,
with the drawer name as the key and the contents inside the drawer as the value.

#+header: :noweb-ref Parsing mechanism
#+begin_src haskell
drawersParser :: OrgParser (Map T.Text T.Text)
drawersParser = do
  kvs <- many (lexeme drawerParser)
  pure $ M.fromList kvs

drawerParser :: OrgParser (T.Text, T.Text)
drawerParser = do
  _ <- char ':'
  drawerName <- MP.takeWhile1P (Just "drawer name") isDrawerLetter
  _ <- char ':'
  _ <- char '\n'
  drawerContents <-
    MP.manyTill
      (MP.label "drawer contents" MP.anySingle)
      (string ":END:\n")
  pure (drawerName, T.pack drawerContents)
  where
    isDrawerLetter c = and $ map ($ c) [(/= '\n'), (/= ':'), (/= ' ')]

#+end_src

We need a helper function around =parseOrgDoc=, which will read in a file from a
given path (to feed to =parseOrgDoc=). We name this helper just =p=.

#+header: :tangle test/Lilac/ParseSpec.hs
#+begin_src haskell
p :: String -> FilePath -> L.OrgDoc -> Spec
p behavior path expected = do
  before (readFileBS path) $ do
    it behavior $ \input -> do
      MP.runParser
        (runStateT L.orgDocParser L.defaultOrgParserState)
        path
        (decodeUtf8 input)
        `parseSatisfies` ((== expected) . fst)
#+end_src

Sometimes we want to test that a file will fail to parse. We do this with =pf=
(for "parse fail").

#+header: :tangle test/Lilac/ParseSpec.hs
#+begin_src haskell
pf :: String -> FilePath -> String -> Int -> Spec
pf behavior path errMsg pos = do
  before (readFileBS path) $ do
    it behavior $ \input -> do
      MP.runParser
        (runStateT L.orgDocParser L.defaultOrgParserState)
        path
        (decodeUtf8 input)
        `shouldFailWith` (errFancy pos . fancy $ MP.ErrorFail errMsg)
#+end_src

Note that we use the =MP.ErrorFail= constructor because that's the only way we can
check for failures in parsers where we manually return an error with
=Control.Monad.fail= (as opposed to Megaparsec itself throwing the error because
of a failure of the given parser combinators to account for the shape of the
input text).
