#+title: Frontend

* Introduction
:PROPERTIES:
:ID:       3c0adfb2-3d51-4cf0-a2f7-6c66f372c2f1
:END:

We write [[https://clojure.org/][Clojure]] instead of [[https://en.wikipedia.org/wiki/JavaScript][JavaScript]] (JS) to add some interactivity to the
woven HTML documents. Here are some definitions:

  - Clojure :: Lisp dialect which traditionally targets the JVM (Java runtime).

  - [[https://clojurescript.org/][ClojureScript]] (CLJS) :: Clojure library which is able to convert Clojure
    code into JavaScript. In a sense this is a Clojure to JS compiler.

  - [[https://github.com/google/closure-compiler][Closure]] :: Library developed by Google which performs optimizations on JS.
    It is a JS to JS optimizer. ClojureScript uses this to clean up the JS code
    that it generates.

The main reason for using Clojure is because it is a much more
pleasant language to use than JS. It is also more established than something
like [[https://engineering.iog.io/2023-01-24-javascript-browser-tutorial/][GHC's JS backend]].

* ClojureScript with Figwheel
:PROPERTIES:
:ID:       a56e18d0-3c66-4202-8fd7-79f9597d07ed
:END:

There are three major CLJS tech stacks:

  1) The "official" tooling. This is what was described above.

  2) [[https://github.com/bhauman/figwheel-main][Figwheel]]. This is an older library that pioneered hot code reloading of
     CLJS (as JS) during development.

  3) [[https://github.com/thheller/shadow-cljs][shadow-cljs]]. This is a newer library that has tighter integration with NPM
     and the JS ecosystem. For example, to create a new project with it you must
     use the ~npx~ command which depends on having [[https://nodejs.org/en][Node.js]] installed.

We choose to use Figwheel because it's a smaller library with fewer moving
parts. Eventually when we feel the need to leverage NPM libraries (such as
[[https://react.dev/][React]]), we could make the move to ~shadow-cljs~.

** Dependencies
:PROPERTIES:
:ID:       473e9718-2454-43d9-9f17-c895ec1b9de5
:END:

Because of the relative immaturity of the Nix package manager's integration with
Clojure [fn:nix-clojure], we don't bother trying to set up a fully reproducible
environment with it. Instead we just install the ~clojure~ binary and let it
do the work of fetching all dependencies.

#+name: nix:tools-fe
#+begin_src nix
pkgs.clojure
#+end_src

As this is a Clojure project, we have to declare dependencies using ~deps.edn~,
where we declare the dependency on Figwheel.

#+name: cfg:deps.edn
#+header: :tangle deps.edn
#+begin_src clojure
{:deps {com.bhauman/figwheel-main {:mvn/version "0.2.20"}
        com.bhauman/rebel-readline-cljs {:mvn/version "0.1.4"}}
 :paths ["resources" "src/fe"]}
#+end_src

The ~:paths ["target"]~ is necessary for helping

#+begin_src sh
clj -M -m figwheel.main
#+end_src

work properly. Otherwise we'll see an error like

#+begin_src txt
[Figwheel:WARNING] Attempting to dynamically add "target" to classpath!
[Figwheel:WARNING] Target directory "target" is not on the classpath
[Figwheel:WARNING] Please fix this by adding "target" to your classpath
#+end_src

** Build configuration file
:PROPERTIES:
:ID:       783de6bf-e36b-4c9e-a405-2a86d0897795
:END:

The build configuration file ~lilac.cljs.edn~ is the main way of configuring a
particular ~build~. These are essentially compiler options for the CLJS to JS
compilation process.

#+name: cfg:lilac-fe-build
#+header: :tangle lilac.cljs.edn
#+begin_src clojure
{:main lilac.core
 :optimizations :none ; (ref:cfg:lilac-fe-build-none)
 :output-to "site/js/lilac.js"
 :output-dir "site/js/cljs-dev"
 :asset-path "js/cljs-dev"} ; (ref:cfg:lilac-fe-build-asset-path)
#+end_src

The ~:asset-path~ is where the HTML will try to load the various other JS files
that the dev JS will depend on (dev JS is not a single JS file); because we will
start the server inside the ~site~ folder (and ~resources/public~ is a symlink to
the top-level ~site~ folder), we have to delete the leading ~site~ prefix.

We can use the above like this:

#+name: sh:invoke-dev-build-watcher
#+begin_src sh
clojure -M -m figwheel.main --build lilac --repl
#+end_src

This will create a REPL that can evaluate CLJS and run it as JS in the browser
tab at http://localhost:9500 per the ~:open-url~ setting in
[[cfg:figwheel-main.edn]]. The ~lilac~ in ~--build lilac~ comes from the ~lilac~ substring
in the ~lilac.cljs.edn~ configuration file (this is a Figwheel convention).

The ~:optimizations~ option is set to ~:none~ [[(cfg:lilac-fe-build-none)]] because
that's required for the REPL to work. Actually it is already the default value,
but we specify it here for explicitness.

The traditional way to invoke [[sh:invoke-dev-build-watcher]] without typing
everything out is to save it as an ~:aliases~ entry inside ~deps.edn~. However we
have a unified Makefile interface already at [[id:5bbaf57a-217d-4e45-88bf-021c4c67b591][=Makefile=]], and so we just use that
instead.

#+name: make:Start frontend development environment (CLJS REPL)
#+begin_src makefile
dev-cljs: tangle
	<<sh:invoke-dev-build-watcher>>
.PHONY: dev-cljs
#+end_src

*** Known limitations

We cannot load the development-mode JS in [[cfg:lilac-fe-build]] in documents
outside of the ~doc~ directory, such as ~plan.org~ ([[id:48e76342-2498-44c5-9ed9-830cb80995fd][Plan]]) because
although we can correctly see ~lilac.js~, that script itself sources folders that
are in the wrong relative directory. Below is a sample of that hardcoded
behavior (what ~lilac.js~ looks like):

#+begin_src js
window.CLOSURE_UNCOMPILED_DEFINES = {"figwheel.repl.connect_url":"ws:\/\/localhost:8080\/figwheel-connect?fwprocess=48e35a&fwbuild=lilac"};
window.CLOSURE_NO_DEPS = true;
if(typeof goog == "undefined") document.write('<script src="js/cljs-dev/goog/base.js"></script>');
document.write('<script src="js/cljs-dev/goog/deps.js"></script>'); // (ref:hardcoded-js-src-path)
document.write('<script src="js/cljs-dev/cljs_deps.js"></script>');
document.write('<script>if (typeof goog == "undefined") console.warn("ClojureScript could not load :main, did you forget to specify :asset-path?");</script>');
document.write('<script>goog.require("figwheel.core");</script>');
document.write('<script>goog.require("figwheel.main");</script>');
document.write('<script>goog.require("figwheel.repl.preload");</script>');
document.write('<script>goog.require("devtools.preload");</script>');
document.write('<script>goog.require("figwheel.main.system_exit");</script>');
document.write('<script>goog.require("figwheel.main.css_reload");</script>');
document.write('<script>goog.require("process.env");</script>');
document.write('<script>goog.require("lilac.core");</script>');
#+end_src

In [[(hardcoded-js-src-path)]], it tells the HTML source to pull from a child
directory of ~js/cljs-dev/...~. This only works for HTML documents that are in the
project root directory, because that's where the ~js~ folder is located.

This is not a problem for the [[id:7e6758c8-a642-4cfa-9e03-498163d6ce68][Optimized production build]], because that build
uses a self-contained, single JS file (and thus does not need to import other
files like in development mode).

*** Optimized production build
:PROPERTIES:
:ID:       7e6758c8-a642-4cfa-9e03-498163d6ce68
:END:

We have to use the following configuration file to get a single minified JS
file.

#+name: cfg:lilac-fe-build-prod
#+header: :tangle lilac-prod.cljs.edn
#+begin_src clojure
{:main lilac.core
 :optimizations :advanced
 :output-to "site/js/lilac.js"
 :output-dir "site/js/cljs-prod"
 :asset-path "site/js/cljs-prod"}
#+end_src

You can run it like this:

#+name: sh:gen-prod-cljs
#+begin_src sh
clojure -M -m figwheel.main --build-once lilac-prod
#+end_src

Or if you're using the [[id:5bbaf57a-217d-4e45-88bf-021c4c67b591::Makefile][Makefile]], you can just do ~make prod-cljs~, which will
invoke the following rule:

#+name: make:Build prod JS
#+begin_src makefile
prod-cljs: tangle
	<<sh:gen-prod-cljs>>
	<<sh:update-injectable>>
.PHONY: prod-cljs
#+end_src

If we are readying Lilac for a production release, it will need to have the
contents of the single JavaScript file (at ~site/js/lilac.js~) injected into the
CLI binary. To perform this injection, we have to

  1) Run ~make prod-cljs~ to ensure we have the latest ~js/lilac.js~ file. This
     also creates a ~site/js/lilac.js.injectme~ which is a copy of the
     just-created (production) ~js/lilac.js~ file, per [[sh:update-injectable]].

  2) Recompile the CLI. This can be done with ~make tangle~ because tangling
     itself relies on the locally compiled version of the ~lilac~ CLI. Because we
     use the [[https://hackage.haskell.org/package/file-embed][file-embed]] library to inject the JavaScript file into the CLI in
     [[id:e31aed94-98f5-4c47-b9ab-e82a529e5be7][JavaScript injection]], Cabal will automatically detect whether the
     JavaScript file has changed and recompile the CLI if needed.

[[sh:update-injectable]] just overwrites the path ~site/js/lilac.js.injectme~ with
what's in ~site/js/lilac.js~.

#+name: sh:update-injectable
#+begin_src sh
cp -f site/js/lilac.js site/js/lilac.js.injectme
#+end_src

We cannot simply inject ~site/js/lilac.js~ directly because the development
environment also uses the same file path in [[cfg:lilac-fe-build]] (and the
development version of this file path does /not/ have a self-contained JS file).

Though the ~site/js/lilac.js.injectme~ file is
needed for compiling the Lilac CLI in [[id:e31aed94-98f5-4c47-b9ab-e82a529e5be7][JavaScript injection]], we don't want to
see this file treated as regular text file (because it cannot be sensibly
merged, and it doesn't make sense to show textual diffs of it between revisions
as it is minified JS). For this reason we treat it as a binary file for Git.

#+name: gitattributes-ignore-compiled-js
#+begin_src gitattributes
site/js/lilac.js.injectme binary
#+end_src

** Anchor link history
:PROPERTIES:
:ID:       318d5b9d-b42b-4fe7-b44c-0b5a5452f3d8
:END:

By default, browsers do not consider links that point to locations in the
current page (aka /anchor links/) as navigable history items. So after clicking on
a bunch of anchor links, if you press the back button on your mouse you'd only
see the URL bar change, but the window won't change locations.

In [[ns:lilac.popstate-history]] we make the browser treat anchor links as worthy of
being included in the history, so that the back button works to move around (to
previously visited locations) in the current page. It works by creating an event
listener which fires for every ~popstate~ event, and is the equivalent of the back
button.

#+name: ns:lilac.popstate-history
#+header: :tangle src/fe/lilac/popstate_history.cljs
#+begin_src clojure
(ns lilac.popstate-history
  (:require [clojure.string :as str]
            [lilac.focus :refer [activate]]))

(defn handle-popstate []
  (let [current-hash
        (if (str/blank? js/window.location.hash)
          "#top"
          js/window.location.hash)
        id (.substring current-hash 1)]
    (when-let [target-el (js/document.getElementById id)]
      (activate target-el))))

(defn init []
  (.addEventListener js/window "popstate" handle-popstate))
#+end_src

** Active headings TOC indicator
:PROPERTIES:
:ID:       c4c13ce7-23d9-49d9-8d3f-6faecf839afa
:END:

We want the TOC to highlight the headings we are currently looking at, so that
we can easily see where we are overall in the document. This works by checking
which heading container ~<div>~ elements are visible in the viewport.

Heading containers are created in [[id:c036cf17-0f61-4f07-bf76-bbe8b4eeb12e::f:weaveHeading][f:weaveHeading]]. Every time visibility changes,
we update the ~visible-headings~ atom, which is a set of visible heading IDs. We
also update the ~active~ and ~active-ancestor~ classes of the items in the [[id:e38fb4d1-72e1-40e0-905e-95bc8be2bf0b][Page
contents]]. We highlight the active heading from the visible heading containers,
and also all of their ancestor headings by reading in the [[id:4651cdd2-5f79-46e0-af4a-5344d71c7ea6][Heading ancestry]]
information, which is woven in as a JSON object in the HTML inside
[[id:4651cdd2-5f79-46e0-af4a-5344d71c7ea6::f:weaveHeadingAncestry][f:weaveHeadingAncestry]].

#+name: ns:lilac.toc-active-entries
#+header: :tangle src/fe/lilac/toc_active_entries.cljs
#+begin_src clojure
(ns lilac.toc-active-entries
  (:require [clojure.walk :refer [keywordize-keys]]
            [clojure.set]))

(defonce visible-headings (atom #{}))

<<f:get-heading-ancestry>>
<<f:update-visible-headings>>
<<f:update-toc-highlights>>
<<f:maybe-scroll-toc>>

(defn init [] ; (ref:ns:lilac.toc-active-entries-init)
  (let [heading-ancestry (get-heading-ancestry)] ; (ref:read-ancestry)

    (add-watch visible-headings :lilac-toc-updater
      (fn [_key atom _old-state _new-state]
        (update-toc-highlights heading-ancestry @atom) ; (ref:toc-callback)
        (maybe-scroll-toc @atom))) ; (ref:ns:lilac.toc-active-entries-maybe-scroll-toc)

    (let [options #js {:rootMargin "0px 0px 0px 0px" :threshold 0} ; (ref:ns:lilac.toc-active-entries-rootMargin)
          heading-containers
            (.querySelectorAll js/document ".heading-container")
          observer
            (new js/IntersectionObserver update-visible-headings options)] ; (ref:ns:lilac.toc-active-entries-update-visible-headings)
      (doseq [heading-container heading-containers]
        (.observe observer heading-container))) ; (ref:watch-heading-containers)

    (let [toc-entry-links (.querySelectorAll js/document ".toc-entry a")]
      (doseq [link toc-entry-links]
        (.addEventListener
           link "click" ; (ref:ns:lilac.toc-active-entries-click-handlers)
           (fn [event]
             (let [clicked-link (.-currentTarget event)]
               (when-not (.contains (.-classList clicked-link) "active") ; (ref:ns:lilac.toc-active-entries-reset-atom)
                 #(reset! visible-headings #{}))))))))) ; (ref:reset-headings-on-click)
#+end_src

The ~init~ function [[(ns:lilac.toc-active-entries-init)]] has four parts:

  1) Read in the heading ancestry JSON (as a native Clojure map), via
     [[f:get-heading-ancestry]] at [[(read-ancestry)]].

  2) Assign [[f:update-toc-highlights]] as a callback to fire whenever the
     ~visible-headings~ atom changes at [[(toc-callback)]].

  3) Use the browser's [[https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API][Intersection Observer API]] to watch all heading containers
     at [[(watch-heading-containers)]]. Make [[f:update-visible-headings]] get called
     (as another kind of callback) any time a heading container becomes (or no
     longer becomes) visible in the viewport
     [[(ns:lilac.toc-active-entries-update-visible-headings)]].
     [[f:update-visible-headings]] modifies the ~visible-headings~ atom.

  4) Assign click handlers to TOC entry links
     [[(ns:lilac.toc-active-entries-click-handlers)]], so that if a user clicks on a
     link from the TOC, we trigger a reset of the ~visible-headings~ atom at
     [[(reset-headings-on-click)]]. This is so that the Intersection Observer API
     can populate that atom again in its callback. This way, we cleanly separate
     what the user does in the main viewport (scrolling it to trigger the
     Intersection Observer API), and what the user does in the TOC by clicking
     on links. If we don't have these click handlers in the TOC, then clicking
     on the TOC can potentially end up with weird snapping behavior.

     Note that the reset of the atom is only done if the heading that is clicked
     on is not already active [[(ns:lilac.toc-active-entries-reset-atom)]] (that is,
     we don't do anything if the heading is already visible).

The ~:rootMargin "0px 0px 0px 0px"~ [[(ns:lilac.toc-active-entries-rootMargin)]] just
makes the entire viewport the thing to check intersections against, and the
~:threshold 0~ makes the observer sensitive to even just 1 pixel of intersection.

Now let's look at how we get the heading ancestry from the JSON. Recall that it
is woven into the document by [[id:4651cdd2-5f79-46e0-af4a-5344d71c7ea6::f:weaveHeadingAncestry][f:weaveHeadingAncestry]] ([[id:891f2674-2be9-4e63-b0f8-7ca43f1354fb::f:weaveObject][f:weaveObject]] calls it).
It gets woven with the ~#heading-ancestry~ ID, and so we use that to find the
element from the DOM.

#+name: f:get-heading-ancestry
#+begin_src clojure
(defn get-heading-ancestry []
  (if-let [script-tag (.querySelector js/document "#heading-ancestry")]
    (let [json-string (.-textContent script-tag)
          js-object (.parse js/JSON json-string)]
      (keywordize-keys (js->clj js-object)))
    (do
      (.error js/console
              "Warning: Heading ancestry data not found; using empty map.")
      {})))
#+end_src

If we find the element, we convert the JSON map into a Clojure one. The main
transformation is the conversion of string keys into keywords, with
~keywordize-keys~. This makes the map lookup faster (as strings require
character-by-character comparison).

Next is [[f:update-visible-headings]] which updates the ~visible-headings~ atom
whenever there is an intersection event created by the ~observer~ in ~init~. Because
we observe the heading /containers/, we have to extract the heading ID that they
contain, by dropping the first 18 characters (the ~heading-container-~ part of
their ID; see [[id:c036cf17-0f61-4f07-bf76-bbe8b4eeb12e::f:weaveHeading][f:weaveHeading]] to see its construction).

#+name: f:update-visible-headings
#+begin_src clojure
(defn update-visible-headings [entries]
  (doseq [entry entries]
    (let [heading-container-id (.. entry -target -id)
          heading-id (subs heading-container-id 18)
          visible? (.-isIntersecting entry)
          modifier (if visible? conj disj)]
      (swap! visible-headings modifier heading-id))))
#+end_src

The Intersection Observer API passes along a list of [[https://developer.mozilla.org/en-US/docs/Web/API/IntersectionObserverEntry][~IntersectionObserverEntry~]]
objects. This object has the following properties of interest to us:

  - ~target~ :: The DOM element whose intersection with the root changed.

  - ~isIntersecting~ :: True if intersecting (visible in viewport), false if not.

The code in [[f:update-visible-headings]] uses some special characters. The ~..~ in ~(..
entry -target -id)~ is a threading macro, which threads the result of the
previous operation as the /object/ for the next operation. So we start with the
~entry~ object and then access its ~target~ property, which gives us the element
(heading container), and then the ~id~ of that element.

The ~.-~ in ~(.-isIntersecting entry)~ is for accessing the ~isIntersecting~ property
of the ~entry~ object.

#+caption: CLJS and JS interop syntax.
| Intent          | ClojureScript syntax | JS equivalent    |
|-----------------+----------------------+------------------|
| Property access | ~(.-prop obj)~         | ~obj.prop~         |
| Method call     | ~(.method obj args)~   | ~obj.method(args)~ |

[[f:update-toc-highlights]] calculates ~visible-headings-with-ancestors~
[[(f:update-toc-highlights-visible-headings-with-ancestors)]], which is the set of
relevant ancestor headings for the current set of ~visible-headings~, and uses
this to check each TOC entry. It highlights the active headings (and their
ancestors).

#+name: f:update-toc-highlights
#+begin_src clojure
(defn update-toc-highlights [ancestry visible-headings]
  (let [toc-entries (.querySelectorAll js/document ".toc-entry")
        toc-container (.querySelector js/document ".toc")
        visible-headings-with-ancestors ; (ref:f:update-toc-highlights-visible-headings-with-ancestors)
          (reduce (fn [acc id]
                      (let [ancestors (set (get ancestry (keyword id) []))]
                        (clojure.set/union acc ancestors)))
            visible-headings
            visible-headings)]

    (doseq [toc-entry toc-entries]
      (when-let [toc-entry-link (.querySelector toc-entry "a")]
        (let [heading (subs (.-hash toc-entry-link) 1) ; (ref:f:update-toc-highlights-remove-initial-hash)
              class-list (.-classList toc-entry)]
          (cond
            (contains? visible-headings heading)
            (do
              (.add class-list "active")
              (.remove class-list "active-ancestor"))

            (contains? visible-headings-with-ancestors heading)
            (do
              (.add class-list "active-ancestor")
              (.remove class-list "active"))

            :else
            (do
              (.remove class-list "active")
              (.remove class-list "active-ancestor"))))))))
#+end_src

The ~heading (subs (.-hash toc-entry-link) 1)~
[[(f:update-toc-highlights-remove-initial-hash)]] is for removing the initial ~#~ part
of the ID (so ~foo~ instead of ~#foo~).

[[f:maybe-scroll-toc]] (potentially) scrolls the TOC so that it shows the active
heading. It is called in [[(ns:lilac.toc-active-entries-maybe-scroll-toc)]]. We
scroll up or down, depending on the relative position of the TOC entry and where
the TOC container is located. And within each case, we scroll all the way to the
top or all the way to the bottom if the active heading is the first or last TOC
entry.

#+name: f:maybe-scroll-toc
#+begin_src clojure
(defn maybe-scroll-toc [visible-headings]
  (let [toc-entries (.querySelectorAll js/document ".toc-entry")
        toc-container (.querySelector js/document ".toc") ; (ref:f:maybe-scroll-toc-toc-container)
        all-active-entries
          (filter (fn [toc-entry]
                    (when-let [toc-entry-link (.querySelector toc-entry "a")]
                      (contains?
                        visible-headings
                        (subs (.-hash toc-entry-link) 1))))
                  toc-entries)

        first-active (first all-active-entries)
        last-active (last all-active-entries)]

    (when (seq all-active-entries)
      (let [toc-rect (.getBoundingClientRect toc-container)
            first-active-rect (.getBoundingClientRect first-active)
            last-active-rect (.getBoundingClientRect last-active)]

        (cond
          (< (.-top first-active-rect) (.-top toc-rect))
          (if (= first-active (first toc-entries)) ; (ref:f:maybe-scroll-toc-scroll-up)
            (.scrollTo toc-container #js ; (ref:f:maybe-scroll-toc-js-reader-macro)
                       {:top 0 :behavior "instant"})
            (.scrollIntoView first-active #js
                             {:behavior "instant" :block "start"}))

          (> (.-bottom last-active-rect) (.-bottom toc-rect))
          (if (= last-active (last toc-entries)) ; (ref:f:maybe-scroll-toc-scroll-down)
            (.scrollTo toc-container #js
                       {:top (.-scrollHeight toc-container)
                        :behavior "instant"})
            (.scrollIntoView last-active #js
                             {:behavior "instant" :block "end"}))

          :else nil)))))
#+end_src

It's important to make sure that the ~toc-container~
[[(f:maybe-scroll-toc-toc-container)]] is the element that has a scrollbar.
Otherwise the scrolling actions will have no effect.

We scroll up if we see that the /first/ active TOC entry is above the TOC
container [[(f:maybe-scroll-toc-scroll-up)]]. This way we show /all/ active headings,
not just the first or last one. For example, if we need to scroll up but only
scroll to the last active TOC entry (and there are other entries above it), we
will still leave some of these other active entries out of view. We do the
equivalent thing for scrolling down (where we check for the bounding box of the
/last/ active TOC entry) [[(f:maybe-scroll-toc-scroll-down)]].

When ClojureScript encounters ~#js~ [[(f:maybe-scroll-toc-js-reader-macro)]], it
converts the Clojure data structure that follows it into its nearest JavaScript
equivalent. So for Clojure maps, it creates a JSON object.

** Lazy scroll

We don't want to do the default scroll behavior if the link target is already
visible in the viewport (where scrolling means putting the target element at the
very top of the page). In short, we should only scroll if we need to. The
prevention of unconditional scrolling is handled in [[ns:lilac.lazy-scroll]].

#+name: ns:lilac.lazy-scroll
#+header: :tangle src/fe/lilac/lazy_scroll.cljs
#+begin_src clojure
(ns lilac.lazy-scroll
  (:require [lilac.focus :refer [activate activate-element deactivate-element]]
            [clojure.string :as str]))

<<f:href->id>>
<<f:get-breadcrumbs-height>>
<<f:visible?>>
<<f:maybe-scroll>>
<<f:maybe-scroll-by-hash>>
<<f:weaken-anchor-links>>

(defn init [] ; (ref:lazy-scroll/init)
  (weaken-anchor-links) ; (ref:lazy-scroll/weaken-anchor-links)
  (.addEventListener js/window "popstate" maybe-scroll-by-hash) ; (ref:lazy-scroll/by-history)
  (maybe-scroll-by-hash nil)) ; (ref:lazy-scroll/page-load)
#+end_src

The [[(lazy-scroll/init)]] is the entrypoint. It is concerned with three types of events:

  1) clicking of links [[(lazy-scroll/weaken-anchor-links)]]

  2) changing of URL history (pressing the forward/back button of the mouse
     /without/ clicking on a link) [[(lazy-scroll/by-history)]]

  3) initial page load [[(lazy-scroll/page-load)]]

When we're clicking the forward and back (history) buttons on a mouse, we call
[[f:maybe-scroll-by-hash]] [[(lazy-scroll/weaken-anchor-links)]] (which tries to scroll
to the element in the current history (URL)) because pressing these mouse
buttons are not associated with click events (otherwise, just
[[f:weaken-anchor-links]] will suffice).

The initial page load [[(lazy-scroll/page-load)]] is an edge case where there is no
associated event (no mouse click or history manipulation is involved), but where
the URL could still end with an anchor at the end.

Let's now examine [[f:weaken-anchor-links]] which also relies on
[[f:maybe-scroll-by-hash]].

#+name: f:weaken-anchor-links
#+begin_src clojure
(defn- weaken-anchor-links []
  (let [links (-> js/document (.querySelectorAll "a[href^=\"#\"]"))]
    (doseq [link links]
      (.addEventListener link "click"
        (fn [event]
          (let [href (.getAttribute link "href")
                id (href->id href)
                old-href (.-hash js/location)]
            (when-let [target-element (-> js/document (.getElementById id))]
              (.preventDefault event) ; (ref:prevent-default-jump)
              (if (= href old-href)
                (if (.contains (.-classList target-element) "active") ; (ref:toggle-active-element)
                  (deactivate-element target-element)
                  (activate-element target-element))
                (do
                  (.pushState (.-history js/window) nil nil href) ; (ref:history)
                  (maybe-scroll-by-hash nil))))))))))
#+end_src

[[(prevent-default-jump)]] disables the browser's default action which performs the
scrolling unconditionally. Instead, we invoke [[f:maybe-scroll-by-hash]] to only
scroll if we have to. [[(history)]] is necessary because otherwise the browser
history is not modified when clicking on an anchor link (in [[id:318d5b9d-b42b-4fe7-b44c-0b5a5452f3d8][Anchor link
history]] we made the browser treat anchor links as history-modifying events).

The check at [[(toggle-active-element)]] removes the ~active~ class if the user is
clicking on the same link twice in a row. This lets the user effectively
un-highlight the target of a link, just in case the highlighted CSS is too
jarring on the eyes. It does not affect the history, so it doesn't matter how
many times the user clicks on the same link pointing to the same target
(pressing the back button will get them immediately back to the other element
just before they started spamming the current target).

Let's finally look at [[f:maybe-scroll-by-hash]], which is the real workhorse. It
just tries to find the current anchor (aka /fragment identifier/, or the bit that
starts with a hash like ~#foo~ in ~href=#foo~), and then:

  1) activates it [[(activate)]] by calling into [[f:activate]] from [[ns:lilac.focus]], and

  2) calls [[f:maybe-scroll]] [[(call-maybe-scroll)]].

#+name: f:maybe-scroll-by-hash
#+begin_src clojure
(defn- maybe-scroll-by-hash [_popstate-event]
  (let [href (.-hash (.-location js/window))
        id (href->id href)] ; (ref:f:maybe-scroll-by-hash-get-anchor)
    (when-let [target-element (-> js/document (.getElementById id))]
      (activate target-element) ; (ref:activate)
      (maybe-scroll target-element)))) ; (ref:call-maybe-scroll)
#+end_src

[[f:href->id]] [[(f:maybe-scroll-by-hash-get-anchor)]] just retrieves the anchor.

#+name: f:href->id
#+begin_src clojure
(defn- href->id [href]
  (let [href (.-hash (.-location js/window))
        href-final (if str/blank? href "#top")
        id (.substring href-final 1)]
    id))
#+end_src

[[f:maybe-scroll]] only scrolls to the target element if it is out view (outside the
viewport).

#+name: f:maybe-scroll
#+begin_src clojure
(defn- maybe-scroll [elt]
  (when-not (visible? elt)
    (.scrollIntoView elt)))
#+end_src

The visibility check is done inside [[f:visible?]].

#+name: f:visible?
#+begin_src clojure
(defn- visible? [elt]
  (let [rect (.getBoundingClientRect elt) ; (ref:element-position)
        bch (get-breadcrumbs-height)
        rect-top (- (.-top rect) bch)
        rect-bottom (- (.-bottom rect) bch)
        window-height (.-innerHeight js/window)
        is-visible (and (< rect-top window-height) ; (ref:element-visibility)
                        (> rect-bottom 0))]
    is-visible))
#+end_src

At [[(element-position)]] we calculate the bounding box of the target element, and
perform a "is it visible" check at [[(element-visibility)]]. The [[id:649018db-d088-4a08-920c-0d64a0be27cd::css:breadcrumbs][css:breadcrumbs]]
element (in the navigation bar) hides whatever is underneath it from the human
user, but for purposes of the viewport (and ~.getBoundingClientRect~) it is
ignored. So we have to compensate for it with [[f:get-breadcrumbs-height]].

#+name: f:get-breadcrumbs-height
#+begin_src clojure
(defn- get-breadcrumbs-height []
  (or (some-> js/document
              (.querySelector ".breadcrumbs")
              (.-parentElement)
              (.-offsetHeight))
      0))
#+end_src

** Element activation

Activating the target element means adding the ~active~ HTML class to it, as seen
in [[ns:lilac.focus]].

#+name: ns:lilac.focus
#+header: :tangle src/fe/lilac/focus.cljs
#+begin_src clojure
(ns lilac.focus)

<<f:deactivate-element>>
<<f:deactivate-other-elements>>
<<f:activate-element>>
<<f:activate>>
#+end_src

The public function is [[f:activate]], which just calls [[f:deactivate-other-elements]]
and [[f:activate-element]].

#+name: f:activate
#+begin_src clojure
(defn activate [elt]
  (deactivate-other-elements (.-id elt))
  (activate-element elt))
#+end_src

[[f:activate-element]] is simple because it just adds the ~active~ class to the class
list (i.e., convert ~class="foo"~ to ~class="foo active"~ for a given HTML element).

#+name: f:activate-element
#+begin_src clojure
(defn activate-element [elt]
  (let [class-list (.-classList elt)]
    (.add class-list "active")))
#+end_src

The tricky part is [[f:deactivate-other-elements]]. If we don't do this, we'll end
up just activating new elements while leaving previously-activated ones still
active. Since all anchor links point to things inside the ~<main>~ HTML element,
we limit our search of elements to anchors somewhere along the hierarchy
underneath ~<main>~ [[(child-anchors)]].

#+name: f:deactivate-other-elements
#+begin_src clojure
(defn- deactivate-other-elements [active-id]
  (when-let [main-elt (-> js/document (.querySelector "main"))]
    (let [child-anchors (-> main-elt (.querySelectorAll "[id]"))] ; (ref:child-anchors)
      (doseq [elt child-anchors]
        (when (not= (.-id elt) active-id)
          (deactivate-element elt))))))
#+end_src

Deactivating an element just means removing the "active" class from its list of
classes.

#+name: f:deactivate-element
#+begin_src clojure
(defn deactivate-element [elt]
  (let [class-list (.-classList elt)]
    (.remove class-list "active")))
#+end_src

** Code block controls
:PROPERTIES:
:ID:       9c8e1074-edfb-4f89-bedf-07527981835d
:END:

Code blocks can have two possible buttons:

  1) ~M~ (for metadata): This is for displaying all raw metadata (most of which is
     uninteresting, and which by default is hidden). See [[id:55af9189-9fb5-4ed9-bbf6-eed970a2e0a5][Hidden (raw) metadata]].
     This button is available on all code blocks on hover.

     The button is generated [[id:4ae846e7-b95c-4996-99e8-8ce6a7e0fdc1::(f:weaveBlock-metadata-button)][here]].

  2) ~Expand contents~ (for expanding code block body text): This is for showing
     the body text, but only when it is hidden. This button is optional, and is
     only displayed if you have ~#+header: :collapsed true~ for your block.
     [[id:9078b9d4-b331-499c-89f8-4b3a355f3c72::fig:lilac-subcommands.pikchr][Example]].

     The button is generated [[id:3d4c0326-ee40-43d5-b49b-ab72081ae91a::(f:weaveInlineBlockControls-body-toggle-button)][here]].

The tricky part with these buttons is that they result in different elements
being hidden or displayed. There is additional complication in that the way
these buttons interact with each other results in how we round out borders
[[(f:render-block!-rounding-style)]].

[[ns:lilac.code-block-controls]] contains logic for dealing with the concerns raised
above. The key is that it keeps track of each code block's state (whether
something is visible or not, whether the code block is anonymous, etc) in an
atom in [[f:state]], and then every time that state changes it re-renders the
changed code block in [[f:render-block!]].

#+name: ns:lilac.code-block-controls
#+header: :tangle src/fe/lilac/code_block_controls.cljs
#+begin_src clojure
(ns lilac.code-block-controls)

<<f:state>>
<<f:calculate-initial-state>>
<<f:ensure-block-state>>
<<f:handle-click!>>
<<f:toggle-class!>>
<<f:rounding-styles>>
<<f:set-enum-class!>>
<<f:render-block!>>

(defn init []
  (add-watch state :render
    (fn [_ _ _ new-state]
      (when-let [block-id (:updated-block-id new-state)]
        (render-block! block-id)))) ; (ref:ns:lilac.code-block-controls-render-callback)
  (.addEventListener js/document "click" handle-click!)) ; (ref:ns:lilac.code-block-controls-init-addEventListener)
#+end_src

*** State handling

First let's discuss state handling, as it's the foundational piece. [[f:state]]
holds an atom which holds the mutable state. Each block gets its own entry in
the ~:block-ids~ map [[(f:state-block-ids)]]. The ~:updated-block-id~
[[(f:state-updated-block-id)]] stores the ID of the most-recently updated block
which needs to get re-rendered.

#+name: f:state
#+begin_src clojure
(defonce state
  (atom {:block-ids {} ; (ref:f:state-block-ids)
         :updated-block-id nil})) ; (ref:f:state-updated-block-id)
#+end_src

[[f:handle-click!]] is the entrypoint for state handling. It looks at the
~data-action=...~ attribute to the nearest code block, and then figures out which
exact button was clicked by looking at value of the ~data-action~ part. Depending
on the action, it toggles just the ~:meta-visible?~ or ~:body-visible?~ boolean
[[(f:handle-click!-toggle-boolean)]]. Then it performs the update to the ~state~ atom
[[(f:handle-click!-update-state-atom)]].

#+name: f:handle-click!
#+begin_src clojure
(defn- handle-click! [e]
  (when-let [btn (.closest (.-target e) "[data-action]")]
    (when-let [block (.closest btn ".code-block-container")]
      (let [block-id (keyword (.-id block))
            action  (.getAttribute btn "data-action")]

        (case action
          ("toggle-code-block-meta-other" "toggle-code-block-body")
          (let [state-key (if (= action "toggle-code-block-meta-other") ; (ref:f:handle-click!-toggle-boolean)
                            :meta-visible?
                            :body-visible?)]
            (swap! state #(-> % ; (ref:f:handle-click!-update-state-atom)
                              (ensure-block-state block-id block)
                              (update-in [:block-ids block-id state-key] not)
                              (assoc :updated-block-id block-id))))

          (js/console.warn "[WARN] Unrecognized action:" action))))))
#+end_src

[[f:ensure-block-state]] just makes sure that we have an entry for the specific
block that has been clicked on. If we don't have an entry for it, it creates the
initial state for it with [[f:calculate-initial-state]]. The primary reason behind
using these functions is to lazily load each block's state is it is clicked on
by the user; if the user doesn't click on anything then the ~state~ atom will
remain empty. If we were to eagerly load each block's state, that would
introduce unnecessary computation on page load.

#+name: f:ensure-block-state
#+begin_src clojure
(defn- ensure-block-state [st block-id block-el]
  (if (contains? (:block-ids st) block-id)
    st
    (assoc-in st [:block-ids block-id] (calculate-initial-state block-el))))
#+end_src

[[f:calculate-initial-state]] examines the initial state of the block to determine
the boolean state values we will use to keep track of it.

#+name: f:calculate-initial-state
#+begin_src clojure
;; Pure data calculation function: returns initial map from HTML markers
(defn- calculate-initial-state [container]
  (let [body (.querySelector container ".code-block-body")
        is-collapsed? (.contains (.-classList body) "collapsed")
        has-collapse-button? (.contains (.-classList body) "collapsible")
        is-anonymous? (.contains (.-classList body) "anonymous")]
    {:meta-visible?        false
     :body-visible?        (not is-collapsed?)
     :has-collapse-button? has-collapse-button?
     :anonymous?           is-anonymous?}))
#+end_src

Finally, we associate the change of the [[f:state]] atom with a callback to
[[f:render-block!]] at [[(ns:lilac.code-block-controls-render-callback)]], before wiring
up the click event lister on the document to [[f:handle-click!]]
[[(ns:lilac.code-block-controls-init-addEventListener)]].

Now we are ready to talk about rendering the block based on the state.

*** Rendering

[[f:render-block!]] is the main entrypoint for rendering a changed code block. It
examines the state of the block in the ~state~ atom by dereferencing it
[[(f:render-block!-atom-deref)]], then modifies the CSS classes depending on the
situation [[(f:render-block!-modify-classes)]].

There are some intricate CSS class selection rules involved, mainly due to how
we round the border corners of the various pieces involved
[[(f:render-block!-rounding-style)]].

#+name: f:render-block!
#+begin_src clojure
(defn- render-block! [block-id]
  (if-let [container (.getElementById js/document (name block-id))]
    (let [block-state (get-in @state [:block-ids block-id]) ; (ref:f:render-block!-atom-deref)
          anon?            (:anonymous? block-state)
          body-vis?        (:body-visible? block-state)
          collapse-button? (:has-collapse-button? block-state)
          meta-vis?        (:meta-visible? block-state)

          other-meta (.querySelector container ".code-block-meta-other")
          body (.querySelector container ".code-block-body")
          controls (.querySelector container ".code-block-controls-inline")

          body-needs-full-rounding?
            (and anon? (not meta-vis?) (not collapse-button?) body-vis?)

          rounding-style ; (ref:f:render-block!-rounding-style)
            (cond
              (and anon? meta-vis? body-vis?) "not-rounded"
              (and anon? (not meta-vis?) (not body-vis?)) "fully-rounded"
              (and anon? meta-vis? (not body-vis?)) "bottom-rounded"
              (and anon? (not meta-vis?) body-vis?) "top-rounded"
              (and (not anon?) meta-vis? body-vis?) "not-rounded"
              (and (not anon?) (not meta-vis?) (not body-vis?)) "bottom-rounded"
              (and (not anon?) meta-vis? (not body-vis?)) "bottom-rounded"
              (and (not anon?) (not meta-vis?) body-vis?) "not-rounded"
              :else nil)]

      ; (ref:f:render-block!-modify-classes)
      (toggle-class! other-meta "hidden" (not meta-vis?))
      (toggle-class! body "collapsed" (not body-vis?))
      (toggle-class! body "fully-rounded" body-needs-full-rounding?)
      (toggle-class! controls "hide-border-bottom" body-vis?)
      (set-enum-class! controls rounding-styles rounding-style))

    (js/console.warn "[WARN] Render target not found for ID:"
                     (name block-id))))
#+end_src

[[f:toggle-class!]] guards the ~.toggle~ object method with a nil check. This is
important because not all blocks have all controls.

#+name: f:toggle-class!
#+begin_src clojure
(defn- toggle-class! [el class-name enable?]
  (when el
    (.toggle (.-classList el) class-name enable?)))
#+end_src

[[f:rounding-styles]] captures all possible rounding styles for the
~.code-block-controls-inline~ DIV. In a sense this is like an ~enum~ data type found
in other programming languages. In our case it's a Clojure set ~#{...}~.

#+name: f:rounding-styles
#+begin_src clojure
(def rounding-styles
  #{"fully-rounded" "top-rounded" "bottom-rounded" "not-rounded"})
#+end_src

[[f:set-enum-class!]] is the set-wise version of [[f:toggle-class!]]. It turns off all
values first, before adding the one we want to enable.

#+name: f:set-enum-class!
#+begin_src clojure
(defn- set-enum-class! [el all-variants target-variant]
  (when el
    (let [class-list (.-classList el)]
      (doseq [variant all-variants]
        (.remove class-list variant))
      (when target-variant
        (.add class-list target-variant)))))
#+end_src
