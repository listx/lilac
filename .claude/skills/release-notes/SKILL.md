# Release notes

This file is tangled from `build.org`, so make changes to it there.

## Adding an entry

- Add new entries to the `** WIP` heading at the top of `release-notes.org`,
  under a group such as `Changes:` or `Fixes:`. Create the heading if it doesn't
  exist.
- When you fix a TODO item in `plan.org`, mark it as `DONE` there instead of
  adding an entry here. It moves here when we draft the notes for a release.
- End the entry with the word `COMMIT`, as a placeholder for the commit that makes
  the change. Don't write a hash yourself, because it isn't final yet. Keep the
  word at the end of its line, because that is where `stamp-new-version.sh` looks
  for leftover placeholders.

For example:

    - Make the files generated by ~lilac init~ work with ~make~. COMMIT

## Drafting the notes for a release

1. Move every `DONE` item out of `plan.org` and into the `WIP` section. Use the
   heading without its `DONE` prefix and the item's description as the text of the
   entry, and end it with `COMMIT` for the commit that fixed it. If the `WIP`
   section already covers the same change, merge the two.
2. Find the latest annotated tag with `git describe --abbrev=0`, and read all
   commits since then with `git log <tag>..HEAD`. Make sure that the `WIP` section
   covers every change that matters to users, not just the entries already there.
3. Choose the new version according to the
   [Haskell PVP](https://pvp.haskell.org), whose version numbers are `A.B.C.D`:
   - Bump `A.B` for breaking changes. This includes documents that used to
     compile but now fail to, and changes to the CLI that break existing usage.
   - Otherwise, bump `C` for backward-compatible additions.
   - Otherwise, bump `D`.
4. Rename the `WIP` heading to the new version, such as `** v0.2.0.3`, and replace
   each `COMMIT` placeholder.
5. Commit only `release-notes.org` and `plan.org`, with the title
   `release notes: prepare for 0.2.0.3 release` (using the new version).
6. Update the `Lilac version` block in `index.org` to the new version, and run
   `make tangle`, but leave this uncommitted. `stamp-new-version.sh` commits this
   diff as `Lilac 0.2.0.3` and creates the annotated tag, and it fails if there is
   nothing to commit. Only run this script if asked to.

## Replacing the placeholder

Replace each `COMMIT` once the commit's hash is final, and before removing the
`WIP` heading. Use the output of this command, rewrapping the entry as needed:

    git show <commit> --no-patch --format=reference

This gives text like:

    ac858305 (cli: fix files generated by lilac init, 2026-11-01)

Lilac parses these notes as prose, so escape any underscore in a commit title
(`\_`). Otherwise the file fails to compile.
