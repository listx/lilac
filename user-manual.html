User Manual

1 Introduction

Lilac originally started out as an extension to Emacs Orgmode, to fix most of the nondeterminism issues of Orgmode's weaving (aka "export") process.

Sometime later, it was determined that Orgmode's HTML export was simply too slow (it could take 10+ seconds on large documents). This project was then rewritten in Haskell, mainly for performance but also for maintainability.

2 Major differences with vanilla Org

This section may be useful for existing Orgmode users, to see at a glance what is and isn't supported.

Orgmode is quite complex. Some features have been purposely left out, mainly for simplicity or readability.

2.1 Compilation step

Orgmode tangles and weaves from Org files directly. There is no intermediate compilation step.

Lilac adds a compilation step in order to cache some computations. Basically, an Org doc must be compiled into a Lilac Object (*.lobj), and then one or more of these objects are archived into a Lilac Archive (*.larc). It is this archive file which is then tangled or woven as needed.

2.2 Stricter list syntax

Lilac is much pickier about lists than Orgmode. Indentation is exact, and is deeper than you might be used to. These requirements were determined to be necessary in order to maximize readability in raw Org (plaintext) form. In exchange, every list in a Lilac document has the same shape, and most mistakes are reported as compilation errors.

Here is a list which follows all of these rules:

🔗

Other metadata key/value pairs:

  • __anon_block_number = 1

  • __block_type = src

  • __src_language = org

  1) The text of this item starts after 5 spaces, and so if we wrap this line,
     the next line also needs 5 spaces.

     A second paragraph in the same item also uses 5 spaces.

       - A child item goes 2 spaces beyond the text of its parent, so this dash
         comes after 7 spaces and this wrapped line needs 9.

     This paragraph has 5 spaces again, so it belongs to item 1, and not to the
     child item above it.

  2) Items are separated by a blank line.

2.2.1 Working out the indentation

The text of a list item starts just after its bullet and a single space. All wrapped lines and other paragraphs in that item must start at that same position. A child item's bullet then goes exactly 2 spaces beyond it.

Note how the extra digit in 10) pushes the text over by one space, unlike in items 1) through 9). So a list which grows to 10 items has wrapped lines and children which are indented differently starting with its tenth item.

In particular, lining up a child's bullet with its parent's text is an error, even though this is common in Orgmode:

🔗

Other metadata key/value pairs:

  • __anon_block_number = 2

  • __block_type = src

  • __src_language = org

  - parent

    - child (error: invalid indentation; this dash needs 6 spaces)

2.2.2 Other things to look out for

  • No indentation means no list. If you forget the two leading spaces, you don't get an error. Instead, each - foo or 1) foo becomes a plain paragraph with the bullet showing as literal text. If your list looks wrong in the woven output, check this first.

  • The numbers don't get fixed up for you. Unlike in Orgmode (or Markdown), an out-of-sequence number is an error, so reordering items means renumbering them by hand.

  • A list ends at anything with less indentation that doesn't belong to one of its items, such as an unindented paragraph, a heading, or a block. A list after that point is a new list, so it starts again from 1). This means that you cannot put a block in the middle of a list.

  • Ordered and unordered items can't be mixed in the same list, although either can be a child of the other. To use both at the same indentation, put something else between them (such as a paragraph).

  • Tables and equations inside a list item go on their own lines (lined up with the item's text), not on the same line as the bullet.

  • To allow deeper nesting, put a #+lilac_maxListLevel line with the desired number of levels (or 0 for no limit) in the metadata at the top of the document, next to #+title.

  • Glossary terms (- term :: definition) are only recognized in unordered lists; in an ordered list the :: is plain text. Every item at that level must be a glossary term, each term must be unique, and terms can't be nested inside other terms.

For the full set of rules with links to test cases, see List items.

2.3 Noweb links can reference blocks from other files

You can reference blocks in other files, as long as those files are also compiled (into objects) and become part of the archive. For example, see module:Lilac.Types where many of the Noweb links point to blocks in other files.

2.4 No #+include support

The ability to declaratively copy/paste chunks of other files is not supported, because doing so results in unreadable raw Org files (you would have to open up the linked page separately to see what was actually included).

2.5 Headings must be linked via their ID (UUID)

You cannot link to headings by their name, or by a "search" of a file path. You must instead always use UUID links. See ti:0004-properties-drawer-not-empty for an example (or, if you are reading this document from the raw Org file, just grep for :ID:)

By the same token, all documents require a UUID, so that even if you don't have a heading, other documents can still reference a named block in your doc via the top-level document UUID.

You probably don't want to type these ID values by hand. In Emacs, you can use M-x org-store-link to get the heading or document's ID (or create one automatically in the process if one doesn't exist yet).

2.6 No implicit concatenation of multiple blocks sharing the same name when tangling

Orgmode allows multiple blocks all sharing the same #+header: :noweb-ref bar metadata, where during tangling these blocks will be concatenated together, in the order that they appear in the doc. However, we do not allow this style for the following reasons:

  1. Orgmode doesn't have good navigation support for it. org-babel-goto-named-src-block only supports #+name: ... metadata.

  2. Using this style can lead to anonymous blocks that don't have a name. IOW, avoiding this style forces us to provide a name for all blocks, and naming everything is generally not a bad thing, because explicit is better than implicit.

  3. The order of concatenation is implicitly hardcoded to be top-to-bottom. When we only use #+name: ..., we can choose any order we want, not just top-to-bottom (by naming the children and choosing how to order the exposition of these child blocks).

2.7 Expandable blocks

If you set #+header: :collapsed true for a block, it will be collapsed in the woven output. You can then click on a button to expand it. This is useful when you have source code that generates figures (drawing), and you don't want the code to steal the attention away from the figure. fig:lilac-subcommands.pikchr is an example of this.

2.8 Other unsupported Org features

The features below are not supported (and are not planned to be supported).

  • Radio links

  • Links to other Org documents by filename. Lilac only supports linking to other Org documents by their ID (see Links).

  • TeX export. Lilac only supports HTML export.

  • Strike-through formatting. Lilac does not support +strike-through+ formatting (the + signs are just plain text).

  • Syntax highlighting of blocks based on the Emacs theme being used (if one were to export an Org file to HTML from Emacs). Lilac uses a variation of the kate theme (see Syntax highlighting theme).

4 Basic initial setup

The main requirement is that you must author Org files, because that's what Lilac understands. Emacs is perhaps the most popular application for authoring Org files, so using Emacs is highly recommended.

4.1 Nix setup (declarative installation)

The Lilac build pipeline uses Cachix to cache the builds, so that you don't have to build from scratch (without it, the configuration below will make you compile Lilac from the sources). After installing Cachix, run

🔗

Other metadata key/value pairs:

  • __anon_block_number = 4

  • __block_type = src

  • __src_language = bash

cachix use funloop

to get access to the cached builds (every release tag, and every push to the main and next branches, is cached).

And then from your project's Nix configuration, you can bring Lilac into your project's scope with:

🔗

Other metadata key/value pairs:

  • __anon_block_number = 5

  • __block_type = src

  • __src_language = nix

  • noweb = off

lilacSrc = builtins.fetchGit {
  url = "https://github.com/listx/lilac";
  ref = "refs/tags/<<lilac-version>>";
  name = "lilac";
  submodules = true;
};

lilacPkg = import "${lilacSrc}/nix/release.nix" { rev = lilacSrc.rev; };

where <<lilac-version>> is the version string vX.X.X.X you want to use. The current version is defined at Lilac version, so you should use that one (with a leading v added, to match the Git tag).

Pass rev = lilacSrc.rev; exactly as above, because the version string is part of the build, and so is part of what Nix looks up in the cache. The cached build of each release tag uses the same rev that fetchGit gives you for that tag (see GitHub CI builds). If you pass lilacGitVersion instead, or pass release.nix some other rev, then Nix won't find your build in the cache and will compile Lilac from source.

If you would rather build Lilac at a particular commit, replace ref with rev = "<sha>"; in the fetchGit call. Builds of commits that were at the tip of a push to main or next are cached too (see Build lilac).

4.1.1 Summary

Pros:

  • Delegate most housekeeping things to Nix, so that you really only need to bump the version string to get the latest Lilac version.

Cons:

  • Every time you bump the version, you have to re-download the Lilac sources.

4.2 Manual setup (imperative installation)

The instructions below are useful for developing Lilac, if you want to submit patches.

Clone this repo. There are 2 ways to install Lilac. The first is with Nix and Cachix. You can just download from the funloop Cachix cache, by running

🔗

Other metadata key/value pairs:

  • __anon_block_number = 6

  • __block_type = src

  • __src_language = bash

cachix use funloop
make build-release
make install-release

The build-release target will end up pulling from the funloop cache (unless CI on main branch is broken).

You can also build with Cabal, by running make install to have Cabal install the lilac binary to disk. For end-users, this is not as desirable because it takes longer.

4.2.1 Summary

Pros:

  • Only need to download Lilac once.

  • More precise control of how you're building Lilac.

Cons:

  • More manual housekeeping. You have to use git pull to get the latest versions, and then remember to run make build-release, etc. This is not declarative at all.

4.3 Using Lilac

Now go to your repo where you want to use Lilac. Run

🔗

Other metadata key/value pairs:

  • __anon_block_number = 7

  • __block_type = src

  • __src_language = sh

lilac init

to generate a starter Lilac.toml and index.org. This will also give you a Makefile, which you can use to run make to start tangling and weaving. You can also do watch -cn 1 make to constantly run make so that you don't have to keep running it yourself.

lilac init ends by running make tangle weave, but it doesn't run the lint step, because that step fails until the generated files are tracked by Git. Run git add on the generated files, and then run make to do all three steps.

At this point your index.org is your source of truth, so have a read through it, and adjust as needed.

5 Using Lilac as a static site generator

Because Lilac weaves output to HTML, it makes it suitable for use as a static content generator. An example is https://funloop.org/build.html (source code at https://github.com/listx/personal-website).

There are a couple flags for the weave subcommand which are worth mentioning for using Lilac as an SSG:

  • --out-dir flag f:weaveOptsHandler → 17: Use this to put all generated assets to a dedicated subdirectory. This makes publishing easier, because the site is then just that one directory. For example, Lilac weaves itself into site and pushes only that directory to GitHub Pages (see Publish to lilac.funloop.org).

  • --root-relative-prefix flag f:weaveOptsHandler → 18: Use this if you don't have control over the server's root folder in production. That is, by default Lilac will make every HTML page pull CSS and JS from top-level css and js folders. However it may be the case that you need to pull these from a subdirectory from the root. This subdirectory, then, is what you'd specify for this flag.
