* Lilac
:PROPERTIES:
:ID:       a8d786d5-8522-454b-971d-fa1b46c5aecc
:END:

Lilac is a [[https://en.wikipedia.org/wiki/Literate_programming][literate programming]] [cite:@knuth_literate_1984] (LP) tool.
Specifically it can read Orgmode files to tangle (i.e., extract) code blocks
using [[https://orgmode.org/manual/Noweb-Reference-Syntax.html][Noweb]] [cite:@ramsey_literate_1994] references, and also weave (i.e.,
publish) the same files to HTML for a more pleasant reading experience.

This document is mainly concerned with how Lilac is implemented. If you simply
want to learn how to /use/ Lilac, read the [[id:75bea01b-b487-4709-978b-2156f4233ebb][User Manual]].

** Project configuration for Lilac
:PROPERTIES:
:ID:       4375ba0d-b917-4d32-92f4-884be63659fe

We define the [[id:df128041-ada8-4d77-a373-111416002dae][Project configuration]] for Lilac itself in here, as a JSON file.

#+name: json:RawProjectConfig
#+header: :tangle .lilac.json
#+begin_src json
{
    "name": "Lilac",
    "homepage": "<<lilac-repo-url>>",
    "repo": "<<lilac-repo-url>>",
    "version": "<<Lilac version>>",
    "nonTangledPathspecs": [ (ref:json:RawProjectConfig-nonTangledPathspecs)
        ":(exclude,top).gitmodules", (ref:tracked_files-generated-by-git)
        ":(exclude,top)LICENSE",
        ":(exclude,top)*.html",
        ":(exclude,top,glob)image/*.svg",
        ":(exclude,top,glob)*.org",
        ":(exclude,top)hello-world/*.org",
        ":(exclude,top)image/PNG-Gradient.png", (ref:tracked_files-images)
        ":(exclude,top)js/lilac.js.injectme", (ref:tracked_files-generated-js)
        ":(exclude,top)bib.json", (ref:tracked_files-bibliographical-refs)
        ":(exclude,top)csl-styles", (ref:tracked_files-csl-styles-repo)
        ":(exclude,top)nix/sources.json", (ref:tracked_files-generated-by-niv)
        ":(exclude,top)nix/sources.nix",
        ":(exclude,top)resources/public" (ref:tracked_files-figwheel-serve-path)
    ],
    "bibliography": ["bib.json"],
    "citationStyle": "csl-styles/ieee.csl"
}
#+end_src

The ~nonTangledPathspecs~ are passed to Git to filter out some paths from
~git-ls-files~, because these files are intentionally not tangled from Org files.
See [[id:a0b8abe5-5b1c-4dc4-b482-5dbd4b233471][Linting tangled paths]] to see how this is used. The magic words ~exclude~ and
~top~ are documented under [[https://git-scm.com/docs/gitglossary#Documentation/gitglossary.txt-pathspec][=gitglossary=]].

[[(tracked_files-generated-by-git)]] skips ~.gitmodules~ because it's generated by
Git.

[[(tracked_files-generated-by-niv)]] skips files generated by Niv.

Image files are never tangled from Org files, so they're skipped
[[(tracked_files-images)]]. (Technically we could support translating text-based
image descriptions into tangled image file outputs, but that's not supported.)

[[(tracked_files-generated-js)]] skips the generated JS file (built from
ClojureScript).

[[(tracked_files-bibliographical-refs)]] skips the raw list of bibliographical
references (written in CSL JSON format).

[[(tracked_files-csl-styles-repo)]] skips the CSL styles submodule repo.

[[(tracked_files-figwheel-serve-path)]] skips the symlink which points back to the
project root. This is used for convincing Figwheel that it's OK to serve files
from the project root (it insists on only serving web assets from
~resources/public~).

*** Literate programming and Noweb

This is a literate document, so prose explanations are mixed in with code.
Typically, all of the content of a code block will be explained by nearby prose.
Code blocks will typically make use of Noweb references.

For example, in

#+header: :noweb off
#+begin_src txt
Foo
<<Lilac version>>
#+end_src

the reference ~Lilac version~ (enclosed within ~<<~ and ~>>~) is a
Noweb reference. When the above is woven to HTML with Noweb enabled (the
default), we get

#+begin_src txt
Foo
<<Lilac version>>
#+end_src

which, if you're viewing this in HTML, should show a link for the ~Lilac version~
part.

If a Noweb reference is not explained nearby, search for it to find where it is
defined. A Noweb reference is a single code block with the ~#+name: foo~ metadata
where ~foo~ is the name of the Noweb reference (this is the name other blocks use
to refer to it).

* Release strategy

The ~next~ branch is where development happens. Time to time, ~main~ is brought up
to match ~next~. The process is:

  1) (On ~next~) [[id:1b7255d6-5d8a-4082-8d84-4852f66333dc][Release Notes]] are updated for the as-yet unreleased version.

  2) (On ~next~) The [[Lilac version]] is bumped, and a commit is created. A Git
     tag is created to point to the above commit. See [[id:1fe40405-2fc3-4cf8-8352-974e5cfee33b][Release commit and
     tagging]].

  3) ~main~ is fast-forwarded to HEAD of ~next~.

  4) (On ~next~) Some things are moved from the [[id:b27d3e53-ada2-4f9e-9f38-18e9252b8229][Backlog]] into [[id:f3c2a043-2d0f-4d6c-a6d5-ce5f58a924c4][Prioritised TODOs]], to
     be worked on for the next release cycle.

~next~ is expected to be unstable (force-pushes will be the norm).

** Release commit and tagging
:PROPERTIES:
:ID:       1fe40405-2fc3-4cf8-8352-974e5cfee33b
:END:

[[stamp-new-version.sh]] takes the Lilac version by searching for it from this Org file, and creates a commit.

#+name: stamp-new-version.sh
#+header: :tangle stamp-new-version.sh
#+header: :shebang #!/usr/bin/env bash
#+begin_src bash
set -euo pipefail

version="$(awk \
	'/^#\+name: Lilac version$/{getline; getline; print}' index.org)"

git commit -am "Lilac ${version}"
git tag -a "v${version}" -m "Lilac ${version}"
#+end_src
