* Org parser

We use [[https://github.com/mrkkrp/megaparsec][Megaparsec]] to parse an Org document. The parsing requires us to read in
everything in a single Org file.

** =Lilac.Parse= module

The parsing mechanism is in [[file:src/Lilac/Parse.hs]], which we describe below. We
discuss each parser and interleave some tests for the smaller parsers. If you
are curious about the overall testing framework itself (where and how these
interleaved tests are executed), take a look at the [[Testing framework]].

** Whitespace and comments

Before writing our first parsers, we have to consider the problem of whitespace
and comments.

Any syntax that is expected to be used by humans have some designation for
whitespace to separate meaningful tokens from each other. One way to deal with
(necessary) whitespace is to bake in whitespace parsers into each token we want
to parse. This gets cumbersome so we want to instead be able to teach parsers to
be able to skip over trailing whitespace. This way, these parsers will all know
how to deal with whitespace in a uniform way. For example, this is what we do in
[[f:cellParser]] where we wrap all of the major =Cell= parsers with a =lexeme=.

A slightly separate problem is how to deal with comments. In a sense they are
just like whitespace because they hold no meaningful information on their own.
Luckily, =Text.Megaparsec.Char.Lexer= provides a =space= helper which can create a
parser that skips over whitespace as well as comments. This is what we use below
to define =skipNewlinesAndComments=. See [[https://markkarpov.com/tutorial/megaparsec.html#lexing][the Megaparsec tutorial]] for more
information.

#+name: f:skipNewlinesAndComments
#+begin_src haskell
skipNewlinesAndComments :: OrgParser ()
skipNewlinesAndComments =
  L.space
    whiteSpaceParser
    singleLineCommentParser
    blockCommentParser
  where
    whiteSpaceParser :: OrgParser ()
    whiteSpaceParser = do
      _ <- MP.takeWhile1P (Just "newline") (== '\n')
      orgParserState <- get
      _ <-
        MP.optional
          . MP.label "indentation for next thing"
          $ MP.count orgParserState.continuationIndent (char ' ')
      pure ()
    singleLineCommentParser :: OrgParser ()
    singleLineCommentParser = L.skipLineComment "# "
    blockCommentParser :: OrgParser ()
    blockCommentParser = L.skipBlockComment "#+begin_comment\n" "#+end_comment\n"
#+end_src

The three arguments to =L.space= (where =L= stands for =Text.Megaparsec.Char.Lexer=)
are the parsers for whitespace, single-line comments, and block comments.
=L.space= will try to repeatedly apply the three given parsers; it only stops
parsing when faced with input where all three parsers fail.

We only parse newline characters in =whiteSpaceParser= above. We don't parse
spaces. This is because we do not want to skip over any /indentation/ --- that is,
space characters immediately following a newline. Such indentation could be an
error (for example, for headings or paragraphs), or a necessary part of a cell
(such as =CListItem= cells in [[f:listItemsEndParser]]), and so we leave that
determination up to other parsers.

It's important that we use =takeWhile1P= for =whiteSpaceParser= (where the =1= denotes
that it requires at least 1 newline character) because otherwise if it is
allowed to accept 0 newlines, it may loop forever upon seeing non-newline input.

The ="# "= for =singleLineCommentParser= signifies that single-line comments start
with a pound sign and a space. The =blockCommentParser= uses =L.skipBlockComment= to
denote a region of text which is considered a commented area. We include
explicit newlines in =blockCommentParser= because we want to ensure that block
comment markers are always on their own line (e.g., ~#+end_comment~ is valid, but
~#+end_comment foo~ is not).

=Text.Megaparsec.Char.Lexer= also defines a =L.skipBlockCommentNested= helper, which
is able to understand if the ending marker of a block (=#+end_comment\n= for us)
should be ignored because it's nested and instead skip past it to find the true
(non-nested) ending marker. That's a little too complicated (and it's probably
not very commonly needed). So we use the non-nested =L.skipBlockComment= to keep
the syntax simple.

Lastly we have =lexeme=, which wraps around any other parser to make it consume
trailing /newlines and comments/. This is used in [[f:cellParser]]. Note that it
does not consume any trailing spaces, because space characters are important for
detecting indentation and we wouldn't want to skip past them.

#+name: f:lexeme
#+begin_src haskell
lexeme :: OrgParser a -> OrgParser a
lexeme = L.lexeme skipNewlinesAndComments
#+end_src

** Parsing overview

We use two major data structures for parsing. The first is a *list of
/cells/[fn:1]*, where each cell can be things like

  - [[https://orgmode.org/worg/org-syntax.html#Headings][headings]] (aka [[https://orgmode.org/manual/Headlines.html][headlines]]),

  - [[id:272567ab-4077-4a47-ae78-dfe77243ccc0][paragraphs]] ([[id:c8616126-215d-49be-8874-c2aca7d93a54][prose]] text),

  - ordered and unordered [[id:58f69993-599d-4389-ba47-3056b1bb2350][list items]] (can be nested),

  - [[id:cae993e5-02bd-4f89-a6d3-20b41adaff8f][blocks]] (code blocks, quotations, examples, etc),

  - [[id:d0f60631-8b30-4ae1-992d-49c7b0ea38fb][tables]],

  - [[id:a090bf9c-0e52-422b-b0f0-51e3b1bf1698][figures]] (images), and

  - LaTeX math fragments ([[id:216e94b7-e037-4f3e-856a-2040d0d0a75a][inline]] and [[id:d1064535-5c98-4c80-a901-5cdc1fd5297f][standalone]]).

This scheme is good for quickly making sense of the overall document structure
in linear fashion, start to finish. It also simplifies the parsing data
structure --- we just parse one cell after the other. It's worth mentioning that
using a tree data structure for the headings could be useful for situations
where tree-based manipulations are desirable; however we will never need to do
such manipulations for purposes of weaving the Org input into HTML (or any other
format). Hence our preference for arranging the cells as a list instead of a
tree.

The second major data structure is a *directed acyclic graph (DAG) for tangled
code blocks*, which we call a *code graph*, for handling Noweb references. Noweb
code blocks can reference other Noweb code blocks, so we create a dependency
graph for each code block which will get tangled to a file. That is, each
would-be-tangled file has its own code graph. These code graphs are discussed
later in [[id:b449a097-d702-4fd6-98de-cb81f7e49177][Code graphs]].

In summary an Org document is made up of cells and code graphs, as well as some
metadata (the title, author name, etc).

~encode~ and ~encodeFile~ functions from =Data.Aeson=.

The top-level parsing function is =parseOrgDoc=, which takes some raw text input
and parses it into a rich =OrgDoc= type.

#+name: f:parseOrgDoc
#+begin_src haskell
parseOrgDoc :: T.Text -> Either T.Text OrgDoc
parseOrgDoc input = case MP.runParser
  (runStateT orgDocParser defaultOrgParserState)
  ""
  input of
  Left err -> Left . T.pack $ MP.errorBundlePretty err
  Right (orgDoc, _orgParserState) -> Right orgDoc
#+end_src

The [[f:orgDocParser]] is the main parser combinator; it is itself composed of other
parser combinators. All of these parsers live inside the =OrgParser= monadic type,
which is defined as a state monad transformer (=StateT=) with =OrgParserState=,
which wraps around the inner =Parsec Void T.Text= monad, where =Void= is the custom
error component and =T.Text= is the type of the text being parsed. Using =Void= for
the custom error component means that we'll be defaulting to the default error
handling mechanism that ships with Megaparsec.

#+name: type:OrgParser
#+begin_src haskell
type OrgParser :: Type -> Type
type OrgParser = StateT OrgParserState (<<Concrete type for Megaparsec>>)
#+end_src

The [[Concrete type for Megaparsec]] feeds the concrete ~T.Text~ type to use as the
stream for Megaparsec. Megaparsec defines a polymorphic API and expects users to
use concrete types like this for speed optimizations.

#+name: Concrete type for Megaparsec
#+begin_src haskell
MP.ParsecT Void T.Text Identity
#+end_src

The =OrgParserState= is the custom state we want to use while parsing. You can
think of it as a mutable variable we keep modifying as we make progress during
parsing.

The ~headingLevel~ is the last-seen heading level we parsed. See
[[t:0004-headings-cannot-skip-level]] for how we use it.

The ~headingSection~ is the last-generated heading section number. This is what we
use to assign each heading its section number.

The =styleMask= is discussed in [[id:b616c1e2-6b42-41cf-8e5d-c1832f95b59b][the section on parsing styled strings]].
The =listLevels= and =listMarkers= are discussed in [[id:58f69993-599d-4389-ba47-3056b1bb2350][List items]]. The
=continuationIndent= is used to keep track of how much indentation to expect
inside a single (contiguous) piece of content; see [[f:paragraphParser]] and
[[f:listHeadIndentLevelParser]] for a usage example.

** =orgDocParser=

The =orgDocParser= first needs to parse any metadata associated with the document,
such as the document ID, title and author. It starts by skipping any leading
whitespace\/comments. We have to do this first because all of the other parsers
we use will follow the pattern of parsing the thing we want, followed by
skipping over as much trailing whitespace as possible. In other words, none of
the parsers are able to deal with leading whitespace\/comments, so we have to
deal with it here separately.

#+name: f:orgDocParser
#+begin_src haskell
orgDocParser :: OrgParser OrgDoc
orgDocParser = do
  _ <- optional skipNewlinesAndComments
  meta <- docMetaParser
  _ <- lilacExtensionsParser
  cells <- many cellParser
  let meaningfulCell :: Cell -> Bool
      meaningfulCell = \case
        CListItem [] -> False
        CHeading {}
        CListItem {}
        CParagraph {}
        CBlock {}
        CMathFragment {}
        CFigure {}
        CTable {} -> True
  MP.eof
  pure
    $ OrgDoc
      { cells = filter meaningfulCell cells,
        meta = meta
      }
#+end_src

The =orgDocParser= delegates most of the work to the [[f:cellParser]], which in turn
delegates work again to the individual parsers that know how to parse different
cells. We have to filter out cells that look like =CListItem []= in ~meaningfulCell~
because that can happen when [[f:listItemsEndParser]] detects maximum indentation
that matches the most-deeply-nested item (in which case no list items end).

See [[f:docMetaParser]] to see how ~docMetaParser~ works.

** =docMetaParser=

An Org document's metadata is the first meaningful thing that could be parsed.
Metadata can be created with a ~:PROPERTIES:~ drawer, or with a line that looks
like =#+key: value= where =key= is a string and =value= is a series of tokens (it can
have multiple words in it). The key and value syntax is trickier, so we look at
that first with =docMetaEntryParser= below.

#+name: f:docMetaEntryParser
#+begin_src haskell
docMetaEntryParser :: OrgParser (T.Text, T.Text)
docMetaEntryParser = do
  avoidParsingBlockMetadata
  avoidParsingLilacExtensions
  _ <- string "#+"
  key <- MP.takeWhile1P (Just "(doc meta) keyword letter") isKeywordLetter
  _ <- MP.label "(doc meta) separator" $ string ": "
  _ <- many $ char ' '
  value <- MP.takeWhile1P (Just "(doc meta) value letter") (\c -> c /= '\n')
  pure (key, value)
  where
    isKeywordLetter c = or $ map ($ c) [isAsciiLower, (== '_')]
    avoidParsingBlockMetadata :: OrgParser ()
    avoidParsingBlockMetadata =
      MP.notFollowedBy
        $ MP.choice
          [ string "#+begin_",
            string "#+name: ",
            string "#+header: "
          ]
    avoidParsingLilacExtensions :: OrgParser ()
    avoidParsingLilacExtensions = MP.notFollowedBy $ string "#+lilac_"
#+end_src

Note how it also has to tiptoe around blocks by checking that it is not looking
at block-related syntax with =avoidParsingBlockMetadata=. This is important
because otherwise if an Org document begins with a [[id:cae993e5-02bd-4f89-a6d3-20b41adaff8f][code block]] as the first
thing (before [[id:16a68a74-d4cc-41a4-ac77-cbca77de2a31][headings]] or anything else), we may consume that as part of
~docMetaParser~ and fail because we think we are expecting ~: ~ followed by a
value.

Similarly, we also do not parse any [[id:84edd33a-a146-4a46-ac0a-cd1c3d0926d3][Lilac extensions]] because they can only be
parsed by the [[f:lilacExtensionsParser]].

The [[f:docMetaParser]] first checks for the top-level ~:PROPERTIES:~ drawer with
[[f:propertiesDrawerParser]]. Then it just parses =docMetaEntryParser= multiple times,
while consuming any trailing whitespace or comments with [[f:lexeme]].

#+name: f:docMetaParser
#+begin_src haskell
docMetaParser :: OrgParser (M.Map T.Text T.Text)
docMetaParser = do
  topLevelDrawerProps <- propertiesDrawerParser
  _ <- optional skipNewlinesAndComments
  metaKVs <- M.fromList <$> (many $ lexeme docMetaEntryParser)
  let conflictingKeys = M.keys $ M.intersection topLevelDrawerProps metaKVs
  when (not $ null conflictingKeys)
    $ fail
    $ "conflicting keys in the top-level PROPERTIES drawer and document metadata key/values: "
    <> (show conflictingKeys)
  case M.lookup "ID" topLevelDrawerProps of
    Nothing -> modify (\s -> s {orgId = one nil})
    Just uuidText -> do
      uuid <- validateUuidText uuidText
      modify (\s -> s {orgId = one uuid})
  pure $ M.union topLevelDrawerProps metaKVs
#+end_src

Note that using the properties drawer is the main way in which the ~ID~ field of a
document is created, which is then used by Orgmode (see
~org-id-link-to-org-use-id~, ~org-id-link-consider-parent-id~, and
~org-id-locations-file~). Using ID's for things (instead of the file name) allows
us to create links that are more resilient against file name changes (or
directory changes). See [[id:ca12051e-cd17-4d8d-996a-767695441d48][Drawers]] for more discussion about properties drawers and
[[t:0002-doc-metadata-properties-drawer]].

*** Lilac extensions
:PROPERTIES:
:ID:       84edd33a-a146-4a46-ac0a-cd1c3d0926d3
:END:

Lilac supports extensions to alter the behavior of the parser for the
document being parsed. These extensions are all prefixed by ~lilac_~ and are set
like other document metadata; they must come *after* the other (typical) Org metadata.

Below is a list of supported extensions:

  - ~lilac_maxHeadingLevel~ :: [[f:maxHeadingLevelParser]] This takes an integer as a
    value. Using ~-1~ means no headings are allowed at all. Using ~0~ means headings
    can have as many asterisks as desired. Using a positive integer means
    headings may only have that many (or less) asterisks; otherwise Lilac will
    fail the parse.

  - ~lilac_maxListLevel~ :: [[f:maxListLevelParser]] This has the same semantics as
    ~lilac_maxHeadingLevel~ but is for list items, not headings.

  { maxHeadingLevel :: Int,
    maxListLevel :: Int
  }
  deriving stock (Eq, Show)

    { maxHeadingLevel = 6,
      maxListLevel = 6
    }
#+end_src

Parsing Lilac extensions involves parsing known key\/value combinations, and
updating the ~OrgParserState~ accordingly.

#+name: f:lilacExtensionsParser
#+begin_src haskell
lilacExtensionsParser :: OrgParser ()

    . many

      [ maxHeadingLevelParser,
        maxListLevelParser
      ]
#+end_src

The [[f:maxHeadingLevelParser]] resembles the [[f:docMetaEntryParser]], but the main
difference is that it does not return anything (its type is ~OrgParser ()~).
Instead it just modifies the ~orgParserState~.

#+name: f:maxHeadingLevelParser
#+begin_src haskell
maxHeadingLevelParser :: OrgParser ()
maxHeadingLevelParser = do
  orgParserState <- get
  _ <- string $ "#+lilac_maxHeadingLevel: "
  _ <- many $ char ' '
  val <- signedIntParser
  let opc = orgParserState.orgParserConf {maxHeadingLevel = val}
  put orgParserState {orgParserConf = opc}
#+end_src

The ~signedIntParser~ knows how to parse a signed integer. The
~parserBetweenSignAndNumber~ is the parser for parsing the area between the sign
(~-~) and the number. Here we define it as ~pure ()~ meaning that nothing is
allowed. The usual use case here is to use a whitespace parser, so as to allow a
space between the sign and number, but we don't do this here for simplicity.

#+name: f:signedIntParser
#+begin_src haskell
signedIntParser :: OrgParser Int
signedIntParser = L.signed parserBetweenSignAndNumber number
  where
    number :: OrgParser Int
    number = L.lexeme skipNewlinesAndComments $ L.decimal
    parserBetweenSignAndNumber :: OrgParser ()
    parserBetweenSignAndNumber = pure ()
#+end_src

Although we don't "return" anything (the type signature of
[[f:lilacExtensionsParser]] is just ~OrgParser ()~), we still use ~put~ inside the
parsers so that they modify the [[data:OrgParserState]].

#+name: f:maxListLevelParser
#+begin_src haskell
maxListLevelParser :: OrgParser ()

  orgParserState <- get
  _ <- string $ "#+lilac_maxListLevel: "
  _ <- many $ char ' '
  val <- signedIntParser

  put orgParserState {orgParserConf = opc}
#+end_src

Unsurprisingly, [[f:maxListLevelParser]] closely resembles [[f:maxHeadingLevelParser]].

** Cells

The /cell/ is the main building block of an Org document --- it is roughly any
region of text surrounded by blank lines.

#+name: data:Cell
#+begin_src haskell
type Cell :: Type
data Cell
  = CHeading Heading
  | CListItem [ListMarker]
  | CParagraph Prose
  | CBlock Block
  | CMathFragment MathFragment
  | CFigure Figure
  | CTable Table
  deriving stock (Eq, Generic, Show)

instance ToJSON Cell
#+end_src

All of the different cell types describe some sort of content, except for one,
=CListItem=. The =CListItem= is purely structural because it only describes itself
and relies on /other cells/ for displaying any useful information. See
[[id:58f69993-599d-4389-ba47-3056b1bb2350][List items]] to see how this is used.

The =cellParser= is responsible for parsing these different recognized values of
[[data:Cell]].

#+name: f:cellParser
#+begin_src haskell
cellParser :: OrgParser Cell
cellParser =
  lexeme
    $ MP.choice
      [ listItemStartParser,
        listItemsEndParser,
        resetContinuationIndent headingParser,
        resetContinuationIndent blockParser,
        resetContinuationIndent figureParser,
        resetContinuationIndent tableParser,
        resetContinuationIndent mathFragmentStandaloneParser,
        resetContinuationIndent paragraphParser,
        detectInvalidIndentation
      ]
  where
    resetContinuationIndent :: OrgParser a -> OrgParser a
    resetContinuationIndent p = do
      a <- p
      modify (\s -> s {continuationIndent = 0})
      pure a
#+end_src

The =resetContinuationIndent= wrapper sets the =continuationIndent= attribute in the
[[data:OrgParserState]] back to =0=; this information is useful for parsers that need
to understand indentation precisely. See [[f:listItemsEndParser]] for how it's used
by that function.

The [[f:listItemStartParser]] and [[f:listItemsEndParser]] are the only parsers that can
consume leading indentation! The [[f:paragraphParser]] can consume leading
indentation, but /only/ on lines except the first one (so that it can ensure that
paragraphs that are part of a list item can have all of its lines line up
together). For example, the following paragraph is inside a list item

  - Hello
    world.

and will be parsed as a string ~Hello world~ and not as ~Hello    world~ (the
leading indent for ~world~ will be ignored).

Any other indentation should be detected as invalid. To enforce this, we put in
a =detectInvalidIndentation= parser which technically isn't a parser but which
will throw an error if it is able to successfully parse indentation. The idea is
that if none of the other parsers in the list are able to consume indentation,
then this will allow =detectInvalidIndentation= to see such indentation and fail
the overall parser.

#+name: f:detectInvalidIndentation
#+begin_src haskell
detectInvalidIndentation :: OrgParser Cell
detectInvalidIndentation = do
  _ <- MP.hidden $ MP.takeWhile1P (Just "indentation") (== ' ')
  void
    $ MP.fancyFailure
    . Set.singleton
    . MP.ErrorFail
    $ "invalid indentation"
  pure $ CListItem []
#+end_src

We signal the error with ~invalid ...~ so as to not shadow the typical ~unexpected
...~ language from Megaparsec's usual parse failures. Note also that the last
line in the function above (~pure $ CListItem []~) is only there to satisfy the
type checker --- we will always fail if the =takeWhile1P= succeeds (the
=MP.fancyFailure= will not be executed if =takeWhile1P= fails).

** Prose
:PROPERTIES:
:ID:       c8616126-215d-49be-8874-c2aca7d93a54
:END:

Prose is a series of contiguous prose text, which can have some styling (bold,
italic, etc) as well as links, citations, footnote links, etc, or /tokens/. So
it's just a list of these /prose/ tokens (~PToken~).

#+name: type:Prose
#+begin_src haskell
type Prose :: Type
type Prose = [PToken]
#+end_src

A =PToken= can be a string (styled or otherwise), a link of some sort, or a Latex
fragment. See [[id:b616c1e2-6b42-41cf-8e5d-c1832f95b59b][Styled strings]], [[id:f8254d58-7a3d-4595-a265-e0d6255e6ab5][Links]], and [[id:d1064535-5c98-4c80-a901-5cdc1fd5297f][Math fragments]] for details on how these
lower-level bits are parsed.

#+name: data:PToken
#+begin_src haskell
type PToken :: Type
data PToken
  = PTokenStyledText StyledText
  | PTokenLink Link
  | PTokenMathFragment MathFragment
  deriving stock (Eq, Generic, Show)

instance ToJSON PToken
#+end_src

The ~proseParser~ can parse a series of [[data:PToken]] values. It is used by both
[[f:headingParser]] and [[f:paragraphParser]], because they both allow prose text in
them.

#+name: f:proseParser
#+begin_src haskell
proseParser :: OrgParser T.Text -> OrgParser [PToken]
proseParser spaceConsumer = do
  a <- MP.choice baseParsers
  b <- MP.many $ MP.choice (spacePTokenParser : baseParsers)
  pure . filter nonEmpty $ a : b
  where
    spacePTokenParser = PTokenStyledText <$> whitespaceCompressor spaceConsumer
    baseParsers =
      [ PTokenLink <$> linkParser,
        PTokenMathFragment <$> mathFragmentInlineParser,
        PTokenStyledText <$> styleMarkerParser,
        PTokenStyledText <$> styledTextParser
      ]
    nonEmpty :: PToken -> Bool
    nonEmpty = \case
      PTokenStyledText styledText -> not $ T.null styledText.body
      PTokenLink {}
      PTokenMathFragment {} -> True
#+end_src

In [[f:proseParser]], we parse whitespace explicitly with =whitespaceCompressor= which
consumes whitespace based on the provided =spaceConsumer=. We first parse among
the non-whitespace parsers in =baseParsers=, then parse additional tokens that may
include whitespace with =spacePTokenParser=. This way, we force the prose to
initially start out without any indentation (because the preceding cell, if any,
would have swallowed up trailing whitespace automatically via =lexeme= in
[[f:cellParser]]); otherwise, [[f:detectInvalidIndentation]] would not get a chance to
detect this (invalid) indentation.

It may appear that we could alternatively skip past spaces inside prose text
by making a =lexeme=-like wrapper which skips newlines /and spaces/ for each parser
in =baseParsers=. However, that approach has a problem. Consider the case of
parsing something like

#+begin_src org
=foo=...
#+end_src

where the ~...~ will get parsed separately from the =foo=. We'll end up with two
=PTokenStyledText= objects, one for =foo= and another for ~...~. This is a problem
because we'll also parse

#+begin_src org
=foo= ...
#+end_src

exactly the same way as two =PTokenStyledText= objects. This is because the space
between the =foo= and ~...~ will get eaten up by the wrapper /and discarded/.
And now we're in the position where we have to, on export, guess (due to
information loss) if we need to insert whitespace between the =foo= and ~...~.

Instead, explicitly parsing the whitespace with =whitespaceCompressor= lets us
parse the two cases above differently, because we save all whitespace we parsed
as their own =PTokenStyledText= objects. We call it a "compressor" because no
matter how many spaces the =spaceConsumer= consumes, we construct only 0 or 1
space characters in the =StyledText= object.

#+name: f:whitespaceCompressor
#+begin_src haskell
whitespaceCompressor :: OrgParser T.Text -> OrgParser StyledText
whitespaceCompressor spaceConsumer = do
  orgParserState <- get

  let mask = orgParserState.styleMask

  _ <- spaceConsumer

  ws <-
    MP.lookAhead
      $ MP.choice
        [ MP.eof >> pure "",
          MP.anySingle >> pure " "
        ]

  pure
    StyledText
      { body = ws,
        style = mask
      }
#+end_src

This parser only succeeds if it finds at least one non-newline whitespace
character. Each time it succeeds, it "compresses" the whitespace to a single
space character --- unless it sees that the input stream ends, in which case we
use an empty string instead (0 space characters). Note that we also do a second
level of "compression" in [[f:compressProse]], where we will drop =StyledText= objects
with an empty string as the body.

** Styled strings
:PROPERTIES:
:ID:       b616c1e2-6b42-41cf-8e5d-c1832f95b59b
:END:

A =StyledText= is just some text that has one or more styles attached to it.  Here
are some examples: *bold*, /italic/, _underline_, =verbatim=, and ~code~.

#+name: data:StyledText
#+begin_src haskell
type StyledText :: Type
data StyledText = StyledText
  { body :: T.Text,
    style :: StyleMask
  }
  deriving stock (Eq, Generic, Show)

instance ToJSON StyledText
#+end_src

The [[newtype:StyleMask]] is a low-level bit mask that can store multiple boolean
values of each of the supported [[data:Style]] bits. If the string has no style,
then it's not stylized at all and the =StyleMask= will be 0 (no bits set). See
[[id:87cd7d62-1f5c-4442-87ff-e1f2a68a8e56][=StyleMask= details]] for a discussion of how this data structure is used and
transformed into a list of =Style= values. For now, we can just pretend that the
=StyleMask= is like a list of [[data:Style]] values.

The [[data:Style]] type is straightforward enough. For now we don't support all
possible styles supported by Orgmode (such as strike-through text), for both
simplicity but also prescriptive reasons. For example, strike-through text
should never be needed during exposition.

#+name: data:Style
#+begin_src haskell
type Style :: Type
data Style = Bold | Italic | Underline | Verbatim | Code
  deriving stock (Enum, Eq, Generic, Ord, Show)

instance ToJSON Style
#+end_src

The =styleMarkers= keeps track of the characters that activate and deactivate each
style. It has the syntactic characters we use to /mark/ text with the a supported
/style/. Hence the term /style markers/.

#+name: f:styleMarkers
#+begin_src haskell
styleMarkers :: M.Map Char Style
styleMarkers =
  M.fromList
    [ ('*', Bold),
      ('/', Italic),
      ('_', Underline),
      ('=', Verbatim),
      ('~', Code)
    ]
#+end_src

Characters in the =styleMarkers= can be escaped with a backslash. For example, the
slashes inside "1\/2" and "and\/or" should not be interpreted as style markers
but as slashes. If you want to write a literal backslash, you must use "\\".
This use of the backslash as an escape character deviates from Orgmode.

*** Parsing

Parsing styled strings is somewhat tricky, because of two main problems:

  1) the markers use the same character for both activation and deactivation,
     and

  2) the styles can be nested or interleaved.

You can have, for example, lines that are /italicized like this but also have
*bold text inside* of it/.

We approach these problems with a simple idea: use a *bit mask*
([[newtype:StyleMask]]) to keep track of markers. Every time we see a starting
marker, we turn on the bit in the mask to activate that style (if it's off), or
turn it off (if it's on), by calling [[f:styleMaskFlip]].

If the input is such that the markers are not balanced, such that by the time we
finish parsing a paragraph (or end of a heading) and the mask still has active
styles in it, we throw an error with [[f:failIfLeftoverActiveStyles]]. That is, we
expect style starting and ending markers to always be balanced by the end of
every paragraph or heading. This deviates from vanilla Org, which does not have
this restriction.

#+name: f:failIfLeftoverActiveStyles
#+begin_src haskell
failIfLeftoverActiveStyles :: OrgParser ()
failIfLeftoverActiveStyles = do
  orgParserState <- get
  let (StyleMask mask) = orgParserState.styleMask
  when (mask /= 0) $ do
    fail
      $ "leftover active styles: "
      ++ (show $ maskToStyles $ StyleMask mask)
#+end_src

We don't really care which styles are turned on or off at which point (the style
markers can be used at the beginning, middle, or end of a word --- where a word
is any sequence of non-whitespace characters). The only thing we check is that
by the end of the cell (heading or paragraph), all styles must be turned off.

#+end_src

Note that we don't wait until seeing the closing marker to see if we should
stylize the text at hand; the =StyleMask= is "strict" in this sense. This way, we
can start parsing stylized text without needing to see a corresponding ending
marker. This imperative style is easier to think about, and is one of the
reasons why we decided to go with having the =StyleMask= in the
[[data:OrgParserState]].

The algorithm for parsing [[data:StyledText]] requires parsing style markers (and
only style markers), or parsing other text that will be affected by style
markers. Let's first look at the simpler case, that of parsing style markers.

#+name: f:styleMarkerParser
#+begin_src haskell
styleMarkerParser :: OrgParser StyledText
styleMarkerParser = do
  orgParserState <- get

  let mask = orgParserState.styleMask
  c <- MP.satisfy $ isStyleMarker mask
  styleMask <- toStyleMask c

  let newMask = styleMaskFlip mask styleMask

  put orgParserState {styleMask = newMask}
  pure
    StyledText
      { body = "",
        style = newMask
      }
#+end_src

All we do is parse a single style marker character, and flip the bit for it as
either on or off, with [[f:styleMaskFlip]]. Ideally we wouldn't even bother
returning anything at the end of [[f:styleMarkerParser]] (because we've updated the
~orgParserState~ and that's the only essential thing we must do). But because of
the way it is used in [[f:proseParser]], we have to return a ~StyledText~. We return
an empty ~body~ field though, so that we can filter it out in the ~nonEmpty~ helper
in [[f:proseParser]].

We cannot parse multiple style markers in one go, because [[f:isStyleMarker]]
changes behavior depending on the current active style mask. If we are in a
verbatim or code style, we ignore all other style markers except for those that
will end the current (verbatim or code) style. Otherwise, we won't be able to
write stuff like ~*~ because we would think that the asterisk in there is starting
a bold style (which it is not because it is surrounded by =~= to mark code).

#+name: f:isStyleMarker
#+begin_src haskell
isStyleMarker :: StyleMask -> Char -> Bool
isStyleMarker styleMask c
  | isVerbatim styleMask = c == '='
  | isCode styleMask = c == '~'
  | otherwise = M.member c styleMarkers
#+end_src

Parsing actual styled text requires reading the state of the =StyleMask=, and then
reading some text. This is done in [[f:styledTextParser]]. It delegates essentially
all of the work to [[f:textParser]].

#+name: f:styledTextParser
#+begin_src haskell
styledTextParser :: OrgParser StyledText
styledTextParser = do
  orgParserState <- get

  let mask = orgParserState.styleMask

  text <- textParser mask

  pure
    StyledText
      { body = text,
        style = mask
      }
#+end_src

The [[f:textParser]] is careful not to step on other parsers' toes, because in a
sense it is the most "greedy" parser, as it can parse many different types of
input.

#+name: f:textParser
#+begin_src haskell
textParser :: StyleMask -> OrgParser T.Text
textParser styleMask
  | isVerbatim styleMask =
      MP.takeWhile1P (Just "verbatim text") isNotVerbatimMarker
  | isCode styleMask =
      MP.takeWhile1P (Just "code") isNotCodeMarker
  | otherwise = do
      ws <-
        MP.some
          $ MP.choice
            [ MP.label "normal characters" normalChars,
              escapedSymbolParser styleMask
            ]
      pure $ T.concat ws
  where
    isNotVerbatimMarker c = c /= '='
    isNotCodeMarker c = c /= '~'
    normalChars :: OrgParser T.Text
    normalChars = do
      cs <- MP.some $ normalChar
      pure $ T.pack cs
    normalChar :: OrgParser Char
    normalChar = do
      MP.notFollowedBy $ string "[["
      MP.satisfy isNormalChar
    isNormalChar c =
      M.notMember c styleMarkers
        && (not $ isSpace c)
        && (not $ c == '\\')
#+end_src

Because of the way =isStyleMarker= and =isProseWord= checks membership of the
characters used for activating (and deactivating) styles in [[f:styleMarkers]], we
take special care to escape these characters with [[f:escapedSymbolParser]]. If the
style markers are not escaped, using any of them will immediately try to
activate or deactivate a style (modulo the special consideration for verbatim
and code markers as discussed in [[f:isStyleMarker]]).

#+name: f:escapedSymbolParser
#+begin_src haskell
escapedSymbolParser :: StyleMask -> OrgParser T.Text
escapedSymbolParser styleMask = do
  _ <- char '\\'
  s <-
    MP.choice
      [ do
          c <- MP.satisfy (\c -> isStyleMarker styleMask c || c == '\\')
          pure $ T.singleton c,
        string "vert{}"
      ]
  if s == "vert{}"
    then pure "|"
    else pure s
#+end_src

The word =\vert{}= can be used to escape a pipe character inside [[data:Table][table]] cells,
because although our Megaparsec-powered parser is powerful enough to handle
escaping pipe characters with =\|= (for consistency with =\/= to escape the italic
style marker), Orgmode is unable to deal with this in Emacs (so pressing ~TAB~
will mess up the alignment of table cells). For this reason, we use =\vert{}=
instead. Of course, outside of tables the pipe character can be written raw like
this "|" without issue.

*** =StyleMask= details
:PROPERTIES:
:ID:       87cd7d62-1f5c-4442-87ff-e1f2a68a8e56
:END:

The previous section explained how we parse styled strings without getting into
the implementation behind the =StyleMask=. We now get into these implementation
details.

The =StyleMask= is an 8-bit word, which can hold boolean values for the 6
different =Style= data constructors, e.g. [[data:Style][Bold, Italic, etc]]. It's a
space-efficient type to replace an equivalent map or list of =[Style]= values. We
use a =newtype= around a =Word8= (an 8-bit word) so as to keep it distinct from
=Word8= itself.

#+name: newtype:StyleMask
#+begin_src haskell
type StyleMask :: Type
newtype StyleMask = StyleMask Word8
  deriving stock (Eq, Generic)

instance ToJSON StyleMask
#+end_src

We have a custom =Show= instance because the default =Show= would just treat the
=Word8= as a number. Instead we want to show what the binary bits (turned on
inside the =Word8=) would represent in terms of actual styles. We have to import
=Prelude= because of the way =Relude= redefines =show= (and we need to use the =show=
that =Prelude= uses; see [[https://github.com/snoyberg/basic-prelude/issues/67#issuecomment-221628073][this related discussion for the Basic Prelude library, a
Relude alternative, for reference]]).

#+name: instance:Show Stylemask
#+begin_src haskell
instance Show StyleMask where
  show (StyleMask a) = "styleMaskFrom " <> x
    where
      x =
        Prelude.show
          . catMaybes
          . map
            ( \(i, b) ->
                if b
                  then (Just $ (toEnum i :: Style))
                  else Nothing
            )
          . zip [0 ..]
          $ toListLE a
#+end_src

The shown text string is prefixed with [[f:styleMaskFrom]] because that function is
used as a constructor function to create a =StyleMask= easily from scratch;
otherwise we'd have to write magic-looking numbers to construct =StyleMask=
values, such as in test cases like [[t:0005-styled-strings-messy-boundaries]]. This
follows the tradition used in =Data.Map= where they also use a constructor
function (=fromList=) when =show=-ing a =Map= data structure.

#+name: f:styleMaskFrom
#+begin_src haskell
styleMaskFrom :: [Style] -> StyleMask
styleMaskFrom ss = StyleMask $ foldl' f (0 :: Word8) ss
  where
    f :: Word8 -> Style -> Word8
    f acc s = setBit acc (fromEnum s)
#+end_src

Similarly, we sometimes want to go the other direction --- that is, deconstruct
a =StyleMask= into =[Style]=. So we have [[f:maskToStyles]].

#+name: f:maskToStyles
#+begin_src haskell
maskToStyles :: StyleMask -> [Style]
maskToStyles (StyleMask mask) = foldl' f [] $ zip [0 ..] $ toListLE mask
  where
    f :: [Style] -> (Int, Bool) -> [Style]
    f acc (idx, b) =
      if b
        then (toEnum idx) : acc
        else acc
#+end_src

We have a helper function [[f:toStyleMask]] to convert =Char= into a =StyleMask=. This
is used to [[f:styleMarkerParser][construct a style mask from a style marker]] in the input Org doc. The
=toStyleMask= function runs inside a =MonadFail= monad, because the =Char= type could
hold a value that is not a valid style marker. The use of =MonadFail= is seamless
inside =ParsecT= (the monad we use inside =OrgParser=), because =ParsecT= has a
=MonadFail= instance.

#+name: f:toStyleMask
#+begin_src haskell
toStyleMask :: (MonadFail m) => Char -> m StyleMask
toStyleMask cs = pure =<< styleToStyleMask =<< charToStyle cs

charToStyle :: (MonadFail m) => Char -> m Style
charToStyle c = case EM.lookup c styleMarkers of
  Just style -> pure style
  Nothing -> fail $ "programmer error: unrecognized style marker " <> (show c)

styleToStyleMask :: (MonadFail m) => Style -> m StyleMask
styleToStyleMask s = pure $ StyleMask (setBit 0 $ fromEnum s)
#+end_src

[[f:styleMaskFlip]] is a helper to perform a binary XOR operation on two =StyleMask=
objects, so that callers don't have to perform the deconstruction and
reconstruction of the underlying =Word8= primitive themselves. This operation is
used to either turn on bits, or turn off bits if they're already on.

#+name: f:styleMaskFlip
#+begin_src haskell
styleMaskFlip :: StyleMask -> StyleMask -> StyleMask
styleMaskFlip (StyleMask a) (StyleMask b) = StyleMask $ a .^. b
#+end_src

We also have some helpers to check whether particular styles are active.

#+name: f:isVerbatim
#+begin_src haskell
isVerbatim :: StyleMask -> Bool
isVerbatim (StyleMask a) = testBit a (fromEnum Verbatim)

isCode :: StyleMask -> Bool
isCode (StyleMask a) = testBit a (fromEnum Code)
#+end_src

We stated earlier in [[t:0005-styled-strings-leftover-active-styles]] that we don't
have to wait to see the ending style marker to start parsing styled text. While
this is true, the downside is that by the time we construct a =StyledText=, we
have no knowledge of future =StyledText= objects that have not yet been parsed.
This can lead to a proliferation of =StyledText= objects that all share the same
style, but are still parsed into separate =PToken= objects. That is, instead of
just one =PToken= with a single =StyledText= object with a sizable ~body~ field, we
could end up with ~[PToken]~ where each of the elements has a small ~body~, but with
the same overall meaning.

Obviously, having a list of =PToken= objects when we can just have a single one is
problematic, if not wasteful. We want to join up sequences of styled text that
share the same style, and make them use a single =StyledText= object. For this
purpose, we have =compressProse=.

#+name: f:compressProse
#+begin_src haskell
compressProse :: [PToken] -> [PToken]
compressProse = reverse . dropUnnecessary . foldl' f []
  where
    f :: [PToken] -> PToken -> [PToken]
    f [] token = token : []
    f
      ((t1@(PTokenStyledText (StyledText body1 style1))) : rest)
      t2@(PTokenStyledText (StyledText body2 style2))
        | style1 == style2 =
            (PTokenStyledText $ StyledText (T.concat [body1, body2]) style1) : rest
        | otherwise = t2 : t1 : rest
    f acc token = token : acc
    dropUnnecessary [] = []
    dropUnnecessary (((PTokenStyledText (StyledText " " _))) : rest) = rest
    dropUnnecessary (((PTokenStyledText (StyledText "" _))) : rest) = rest
    dropUnnecessary tokens = tokens
#+end_src

This function works by looking at two consecutive ~PTokenStyledText~ elements at a
time (one that's already in the accumulator (~acc~) from the previous iteration
and one from the current ~token~ at hand), joining them if they share the same
style.

=compressProse= also eliminates trailing whitespace, with =dropUnnecessary=.
Trailing whitespace can occur if the last word of a paragraph at the end of the
file ends with an active =StyleMask= followed by a newline (trailing whitespace
between paragraphs can't occur because the =lexeme= in [[f:cellParser]] will skip past
them). For example, if the input text looks like

#+begin_src org
_foo
bar_
#+end_src

then the last underscore can be followed by a newline (assuming the editor used
to edit this file is UNIX-friendly and appends a trailing newline), in which
case that newline would get parsed by the =spaceConsumer= in [[f:paragraphParser]] as
its own separate =StyledText= object as a single space character. We want to
eliminate these objects because they don't add any useful information for Lilac
itself, and so we use =dropUnnecessary= above to filter them out.

=dropUnnecessary= also removes tokens with an empty string as the =StyledText=
object. This can occur when we parse trailing newlines at the end of the line
even without style markers, from [[f:whitespaceCompressor]].

** Links
:PROPERTIES:
:ID:       f8254d58-7a3d-4595-a265-e0d6255e6ab5
:END:

A link has

  - a name :: what's displayed to the reader, and

  - a target :: where we want to take the reader when the click on the link
    (including any metadata).

#+name: data:Link
#+begin_src haskell
type Link :: Type
data Link = Link
  { name :: [StyledText],
    target :: LinkTarget
  }
  deriving stock (Eq, Generic, Show)

instance ToJSON Link
#+end_src

The target is a rich definition of the kind of target we are linking to.
Currently we only recognize [[data:LinkNoweb]]. All other links are just captured in
the generic ~LinkTargetOther~ constructor.

#+name: data:LinkTarget
#+begin_src haskell
type LinkTarget :: Type
data LinkTarget
  = LinkTargetNoweb LinkNoweb
  | LinkTargetOther T.Text
  deriving stock (Eq, Generic, Show)

instance ToJSON LinkTarget
#+end_src

A Noweb link points to a code block with the given =name=, as well as the [[id:96f8cbda-abca-48bd-bb89-512aaac61ca8][Org ID
or =uuid= of the file]] the code block comes from. The UUID acts as a /namespace/, so
that each Org file is free to choose any name it wants for code blocks without
fear of other Org files that might have a code block with the same name.

#+name: data:LinkNoweb
#+begin_src haskell
type LinkNoweb :: Type
data LinkNoweb = LinkNoweb
  { uuid :: UUID,
    name :: T.Text
  }
  deriving stock (Eq, Generic, Show)

instance ToJSON LinkNoweb
#+end_src

In summary we support the following link types:

  - ~LinkTargetNoweb~ :: a link to a Noweb reference inside another code block.
    These use angle brackets (e.g., ~<<foo>>~), where the text inside the brackets
    refers to a code block in the current file. This can reference code blocks
    in other files by UUID, where the syntax is ~<<id:...::foo>>~ where ~...~ is the
    UUID and ~<<foo>>~ is the name of the code block at that UUID. We have to use
    a UUID-to-file map data structure (which is parsed [[id:96f8cbda-abca-48bd-bb89-512aaac61ca8][here]]).

  - ~LinkTargetOther~ :: all other links. Typical ways to define such links are
    with uses square brackets (e.g., ~[[target]]~ or ~[[target][name]]~) where
    ~target~ is just a plain text string (such as a URL or some other entity in
    the document), and ~name~ is what is displayed to the user when the link is
    rendered.

There are also [[Raw links]] which is prose text that looks like a URL. For example,
https://www.haskell.org is an example of a raw link. This is a convenience
facility because ~[[https://www.haskell.org]]~ behaves the same way as
~https://www.haskell.org~.

*** Standalone link parser

The standalone link parser [[f:linkParser]] can parse links that can be embedded
inside prose text.

#+name: f:linkParser
#+begin_src haskell
linkParser :: OrgParser Link

  failIfVerbatimOrCode

  MP.choice
    [ MP.try bracketedLinkParser,
      MP.try rawLinkParser
    ]
#+end_src

The call to [[f:failIfVerbatimOrCode]] fails the parser if either the [[f:isVerbatim][verbatim or
code style is active]]. This is because the verbatim and code styles take
precedence over parsing links. See, for example
[[t:0005-styled-strings-verbatim-precedence]] of the sort of behavior we expect.

#+name: f:failIfVerbatimOrCode
#+begin_src haskell
failIfVerbatimOrCode :: OrgParser ()
failIfVerbatimOrCode = do
  orgParserState <- get
  let mask = orgParserState.styleMask
  when (isVerbatim mask || isCode mask)
    $ fail "aborting because verbatim or code style is active"
#+end_src

By conditionally failing [[f:linkParser]] with [[f:failIfVerbatimOrCode]], we also allow
other parsers (such as [[f:styledTextParser]]) to succeed (see [[f:proseParser]] for the
interaction of this parser with these other parsers).

Note that in [[f:linkParser]] we don't parse [[Noweb links]] here because they can only
exist inside [[id:cae993e5-02bd-4f89-a6d3-20b41adaff8f][code blocks]].

*** Other links

All other links are simply called ~LinkTargetOther~. For now, these links are any
links found in double brackets. They can target both external resources, such as
a web page on the internet or a file on disk, or internal ones (to some other
point in the Org document). In the future it is expected that we will enrich the
different kinds of links in [[data:LinkTarget]], such that the percentage of
~LinkTargetOther~ is very low when we finish parsing an Org file.

A URL link looks [[https://kernel.org][like this]]. A link to a file can look [[./README.org][like this]]. Note that their
format allows them to be named differently than the raw address. That's why the
two links earlier in this paragraph are displayed as "like this". The format is

#+begin_src org

#+end_src

where ~[name]~ is optional. If it is omitted, then the ~target~ part is used as the
name.

*** Raw links

The [[f:rawLinkParser]] parses text that look like URLs into ~LinkBracketed~.

#+name: f:rawLinkParser
#+begin_src haskell
rawLinkParser :: OrgParser Link
rawLinkParser = do
  protocol <- MP.takeWhile1P (Just "raw link protocol") isAsciiLower
  separator <- string "://"
  remainder <- T.pack <$> MP.some (MP.try remainderChar)
  let url = protocol <> separator <> remainder
  pure
    Link
      { target = LinkTargetOther url,
        name =
          [ StyledText
              { body = url,
                style = styleMaskFrom []
              }
          ]
      }
  where
    remainderChar :: OrgParser Char
    remainderChar = do
      c <- MP.satisfy N.isAllowedInURI
      when (isPunctuation c) $ do
        MP.notFollowedBy (char ' ')
        MP.notFollowedBy (char '\n')
      pure c
    isPunctuation :: Char -> Bool
    isPunctuation = not . isAlphaNumChar
    isAlphaNumChar :: Char -> Bool
    isAlphaNumChar c = isAlphaChar c || isDigitChar c
    isAlphaChar :: Char -> Bool
    isAlphaChar c = (c >= 'A' && c <= 'Z') || (c >= 'a' && c <= 'z')
    isDigitChar :: Char -> Bool
    isDigitChar c = c >= '0' && c <= '9'
#+end_src

The tricky part is in the =remainderChar=. Essentially, if we see a raw link
followed by some punctuation, like https://funloop.org, then we want the
punctuation plus the whitespace immediately after it to be excluded from the
link. The punctuation may or may not be part of the allowed characters in
=N.isAllowedInURI=. We fix this problem by running some additional checks if we
ever encounter punctuation, with =isPunctuation=. The =isAlphaNumChar= helper is
taken from [[https://hackage.haskell.org/package/network-uri][network-uri]].

** Paragraphs
:PROPERTIES:
:ID:       272567ab-4077-4a47-ae78-dfe77243ccc0
:END:

The [[f:paragraphParser]] is similar to [[f:headingParser]] because it's also powered
mostly by [[f:proseParser]]. However a key difference is that it is aware of the
nuances between newlines, indentation, and spaces.

The main concern is to understand where the paragraph starts. Paragraphs can
start in three ways:

  1) without indentation,

  2) after a list head (which is essentially indentation), or

  3) with indentation (as part of a list).

In all three cases, we would like to check whether a paragraph's inner lines
have consistent indentation. This way, a paragraph's lines all line up
vertically on the same column, and is visually pleasing. Doing this check means
understanding what is the expected indentation (if at all) for lines inside the
paragraph.

#+name: f:paragraphParser
#+begin_src haskell
paragraphParser :: OrgParser Cell
paragraphParser = do
  orgParserState <- get
  prose <- proseParser $ spaceConsumer orgParserState.continuationIndent
  failIfLeftoverActiveStyles
  pure . CParagraph $ compressProse prose
  where
    spaceConsumer :: Int -> OrgParser T.Text
    spaceConsumer expectedIndentLen =
      MP.choice
        [ newlineAndIndentParser expectedIndentLen,
          spaces
        ]
    spaces :: OrgParser T.Text
    spaces = MP.takeWhile1P (Just "space") (\c -> c == ' ')
#+end_src

The tricky bit is with ~spaceConsumer~ here. It chooses between either a newline
followed by an indent of length ~expectedIndentLen~ (in [[f:newlineAndIndentParser]]),
or just ~spaces~ which we define to be one or more space characters.

#+name: f:newlineAndIndentParser
#+begin_src haskell
newlineAndIndentParser :: Int -> OrgParser T.Text
newlineAndIndentParser expectedIndentLen = do
  MP.notFollowedBy cellBoundary
  _ <- string "\n"
  maybeIndent
  pure " "
  where
    cellBoundary :: OrgParser T.Text
    cellBoundary = string "\n\n"
    maybeIndent =
      if (expectedIndentLen == 0)
        then nonSpace
        else MP.eof <|> exactIndent
    nonSpace :: OrgParser ()
    nonSpace = MP.notFollowedBy (char ' ')
    exactIndent :: OrgParser ()
    exactIndent = do
      _ <-
        MP.label "indentation for paragraph continuation"
          $ MP.count expectedIndentLen (char ' ')
      MP.notFollowedBy (char ' ')
      MP.notFollowedBy (char '\n')
      pure ()
#+end_src

The ~MP.notFollowedBy cellBoundary~ bit is required to stay clear of cell
boundaries (paragraph cells are separated from each other by a blank line, or in
other words a sequence of two consecutive newlines). If we don't do this, our
parser will see a newline and immediately think that there should follow some
spaces for the indent portion, which may not be true if the newline was part of
a cell boundary.

The ~maybeIndent~ handles the case where there is no indentation (with ~nonSpace~),
or where there is indentation (with ~MP.eof <|> exactIndent~). The first case does
not need ~MP.eof <|>~ because it's redundant --- ~MP.notFollowedBy (char ' ')~ will
succeed for ~MP.eof~ as well, as [[t:0005-notFollowedBy-behavior-for-empty-input]]
demonstrates.

The number of asterisks determine the nesting level. There can be any number of
levels, although there should be probably no more than 6 in a section that will
be exported as a single HTML page (because the heading tags ~<h1>~, ~<h2>~, etc only
go up to ~<h6>~). This Org document itself only uses 3 sections.

The heading may also have some metadata associated with it. In practice this
will be keys and values from a =:PROPERTIES:= [[https://orgmode.org/manual/Drawers.html][drawer]], although other drawers are
possible. We store drawer information inside the =meta= hashmap, with the drawer
name acting as a key prefix (this way we can store multiple drawers, if there
are any, in a single hashmap).

Other than the level, each heading is made up of =Prose= text, which we consider
in the next section.

#+name: data:Heading
#+begin_src haskell
type Heading :: Type
data Heading = Heading
  { level :: Int,
    section :: [Int],
    body :: Prose,
    meta :: M.Map T.Text T.Text
  }
  deriving stock (Eq, Generic, Show)

instance ToJSON Heading
#+end_src

The ~section~ field is generated during the parse, and is the section number like
"1.1.2" or "5.3". The numbering matches the behavior of [[https://orgmode.org/manual/Dynamic-Headline-Numbering.html][org-num-mode]]. This is a
list of ~Int~ values, and the value at the head of the list represents the deepest
level (it's reversed); for example, section "5.3" is represented as ~[3, 5]~.

The parser for a heading is straightforward as the strict requirements make it
easy to have simple rules for it.

#+name: f:headingParser
#+begin_src haskell
headingParser :: OrgParser Cell
headingParser = do
  orgParserState <- get
  _ <- MP.try $ MP.lookAhead (starsParser >> char ' ')
  let opc = orgParserState.orgParserConf
  stars <- starsParser
  when (opc.maxHeadingLevel < 0) $ do
    fail
      $ "headings prohibited because lilac_maxHeadingLevel < 0"
  let lenStars = T.length stars
      currentHeadingLevel = orgParserState.headingLevel
  when (opc.maxHeadingLevel > 0 && lenStars > opc.maxHeadingLevel) $ do
    fail
      $ "found "
      <> show lenStars
      <> " asterisks found for this heading, but "
      <> "lilac_maxHeadingLevel = "
      <> show opc.maxHeadingLevel
  failIfHeadingNestsWithoutDirectParent currentHeadingLevel lenStars
  _ <- char ' '
  prose <- proseParser spaceConsumer
  _ <- char '\n'
  failIfLeftoverActiveStyles
  props <- propertiesDrawerParser
  let newHeadingSection = genHeadingSection lenStars orgParserState.headingSection
      newOrgId = genOrgIdStack (EM.lookup "ID" props) lenStars orgParserState.orgId
  put
    orgParserState
      { headingLevel = lenStars,
        headingSection = newHeadingSection,
        orgId = newOrgId
      }
  pure
    $ CHeading
      Heading
        { level = lenStars,
          section = newHeadingSection,
          body = compressProse prose,
          meta = props
        }
  where
    spaceConsumer :: OrgParser T.Text
    spaceConsumer = MP.takeWhile1P (Just "space") (== ' ')
    starsParser :: OrgParser T.Text
    starsParser = MP.takeWhile1P (Just "heading star") (\c -> c == '*')
#+end_src

We fail if the heading level is not compliant with the setting of
~lilac_maxHeadingLevel~, which is accessed via ~opc.maxHeadingLevel~ (see [[id:84edd33a-a146-4a46-ac0a-cd1c3d0926d3][Lilac
extensions]]).

We also fail if we try to nest the heading too much in
[[f:failIfHeadingNestsWithoutDirectParent]]. See [[t:0004-headings-cannot-skip-level]]
for an example.

#+begin_src haskell
failIfHeadingNestsWithoutDirectParent :: Int -> Int -> OrgParser ()
failIfHeadingNestsWithoutDirectParent current found =
  when (found > current + 1) $ do
    fail
      $ "headings may not skip levels (expected to see level "
      <> show current
      <> " or "
      <> (show $ current + 1)
      <> ", not "
      <> show found
      <> ")"
#+end_src

The body text of a heading is a series of prose tokens, or =PToken= values, which
we call =Prose=.

We consider prose in detail in [[id:c8616126-215d-49be-8874-c2aca7d93a54][Prose]], where we also discuss
[[f:failIfLeftoverActiveStyles]] and also [[f:compressProse]]. Drawers are discussed
separately [[id:ca12051e-cd17-4d8d-996a-767695441d48][here]].

*** Section number generation

Generating the section number relies on the previous section, and the current
level of the heading for which we want to generate the section number.

#+name: f:genHeadingSection
#+begin_src haskell
genHeadingSection :: Int -> [Int] -> [Int]
genHeadingSection level prevSection
  | null prevSection = 1 : (take (level - 1) $ repeat 0)
  | length prevSection == level = bumpDeepestSection prevSection
  | length prevSection > level =
      bumpDeepestSection
        $ drop (length prevSection - level) prevSection
  | otherwise =
      let levelDiff = (level - length prevSection - 1)
       in (1 : (take levelDiff $ repeat 0)) <> prevSection
  where
    bumpDeepestSection :: [Int] -> [Int]
    bumpDeepestSection [] = []
    bumpDeepestSection (x : xs) = x + 1 : xs
#+end_src

The algorithm starts with the base case where we have no previous section (~null
prevSection~), where we assign "0" section numbers for the missing levels, if
any. The same thing applies for the case where we nest too deeply than a
previously seen level (the stuff with ~levelDiff~).

Although [[f:genHeadingSection]] takes into account these edge cases where we have a
"0" section number, the parser itself fails if we skip any levels (if we nest
too deeply at any point), in [[f:failIfHeadingNestsWithoutDirectParent]]. We decided
to engineer it this way because it makes the algorithm behave more intuitively
even when faced with messy input.

#+name: t:Generate headings
#+begin_src haskell

*** Generating the current Org ID

[[f:genOrgIdStack]] is quite similar to [[f:genHeadingSection]]. The point of it is to
store the Org IDs up to the current point. This is ultimately used to assign the
Org ID of the first non-nil parent heading for an implicitly-defined code block,
in [[f:blockOriginSignatureParser]].

#+name: f:genOrgIdStack
#+begin_src haskell
genOrgIdStack :: Maybe T.Text -> Int -> NonEmpty UUID -> NonEmpty UUID
genOrgIdStack maybeId level prevOrgId
  | length prevOrgId == 1 = newId NE.<| prevOrgId
  | length prevOrgId == depth = newId :| tail prevOrgId
  | length prevOrgId < depth =
      let nils = take (levelDiff - 1) $ repeat nil
       in (newId :| nils) <> prevOrgId
  | otherwise = newId :| (NE.drop (abs levelDiff + 1) prevOrgId)
  where
    depth = level + 1
    levelDiff = depth - length prevOrgId
    newId
      | Just uuidText <- maybeId,
        Just uuid <- fromText uuidText =
          uuid
      | otherwise = nil
#+end_src

** Drawers
:PROPERTIES:
:ID:       ca12051e-cd17-4d8d-996a-767695441d48
:END:

In vanilla Orgmode, drawers look like

#+begin_example
:DRAWER_NAME:
...contents...
:END:
#+end_example

and the contents may be anything but another [[id:16a68a74-d4cc-41a4-ac77-cbca77de2a31][heading]] or another (nested) drawer.
In Lilac, we only parse the =:PROPERTIES:= drawer, which is a special drawer that
can contain key\/value pairs that Org recognizes. One of these is the =:ID:= key,
which can have a UUID as the value, and which can be used as a link target from
elsewhere in the document (in Orgmode this can be done with ~org-id-store-link~).

#+name: f:propertiesDrawerParser
#+begin_src haskell
propertiesDrawerParser :: OrgParser (Map T.Text T.Text)
propertiesDrawerParser = propertiesParser <|> (pure $ M.fromList [])
#+end_src

The [[f:propertiesDrawerParser]] tries to parse a =:PROPERTIES:= drawer with
[[f:propertiesParser]], but if it fails it returns an empty ~Map~.

#+name: f:propertiesParser
#+begin_src haskell
propertiesParser :: OrgParser (Map T.Text T.Text)
propertiesParser =
  M.fromList
    <$> MP.between
      (lexeme $ string ":PROPERTIES:\n")
      (string ":END:\n")
      (many $ lexeme propertiesEntryParser)
#+end_src

The [[f:propertiesParser]] is just a thin wrapper around [[f:propertiesEntryParser]]
which does the heavy lifting of figuring out the key value parts.

The uses of [[f:lexeme]] allow this parser to ignore comments it finds inside the
drawer area. There is no need to use [[f:lexeme]] for the closing ~:END:~ bit because
we already wrap all cells with [[f:lexeme]] in [[f:cellParser]], and the last thing
[[f:headingParser]] parses is [[f:propertiesParser]] (if [[f:headingParser]] parsed
something else after calling [[f:propertiesParser]], we would need to wrap ~:END:~
with [[f:lexeme]] as well).

#+name: f:propertiesEntryParser
#+begin_src haskell
propertiesEntryParser :: OrgParser (T.Text, T.Text)
propertiesEntryParser = do
  MP.notFollowedBy $ string ":END:"
  _ <- char ':'
  key <- MP.label "property key" . MP.some $ MP.noneOf ['\n', ':', ' ']
  _ <- char ':'
  _ <- MP.takeWhile1P (Just "space") (== ' ')
  value <-
    MP.manyTill
      (MP.label "property value" MP.anySingle)
      (char '\n')
  pure (T.pack key, T.pack value)
#+end_src

The main tricky bit is ~MP.notFollowedBy $ string ":END:"~; we need this because
otherwise we will think that the string ~:END:~ is just another key.

*** Metadata

Blocks can have associated metadata, as we can see from the test case above. The
metadata is made up of any number of special key\/value pairs that are written
in the form of =#+header: :key value= lines. The special line =#+name: foo= gives
the block a unique name (if it's not globally unique, we'll complain about it
[[f:assertUniqueBlockName]]), which can be the target of an internal link.

Vanilla Org allows you to place these key\/value pairs on the same line as the
=#+begin_...= line, but we don't allow this. This enforces a cleaner style and
also simplifies the parser.

#+name: f:blockMetaEntryParser
#+begin_src haskell
blockMetaEntryParser :: OrgParser (T.Text, T.Text)
blockMetaEntryParser = do
  _ <- string "#+header: :"
  key <- MP.takeWhile1P (Just "(block meta) keyword letter") isKeywordLetter
  _ <- char ' '
  value <- MP.takeWhile1P (Just "value letter") (\c -> c /= '\n')
  _ <- char '\n'
  assertUniqueTanglePath key value
  pure (key, value)
  where
    isKeywordLetter c = or $ map ($ c) [isAsciiLower, (== '-')]

metaNameParser :: OrgParser (T.Text, T.Text)
metaNameParser = do
  _ <- string "#+name: "
  name <- T.pack <$> MP.someTill (MP.label "name of block" MP.anySingle) (char '\n')
  assertUniqueBlockName name
  pure ("name", name)
#+end_src

*** Body

The contents or ~body~ of a [[data:Block]] is list of =BToken= values, which are quite
similar to =Prose= (a list of =PToken= types). A =BToken= can be either some raw piece
of text, or a link. The link is only for the case of Noweb references. For
example, if a block contains a Noweb reference, then it needs to be a link such
that the Noweb reference can be dereferenced, and its contents replaced with the
source of the referenced code block during tangling.

#+name: data:BToken
#+begin_src haskell

  = BTokenString T.Text
  | BTokenPadding
  | BTokenLink Link
  deriving stock (Eq, Generic, Show)

instance ToJSON BToken

*** Overall parser

Let's see how we parse the block itself with =blockParser=.

#+name: f:blockParser
#+begin_src haskell
blockParser :: OrgParser Cell
blockParser = do
  (blockName, metaKVs, blockType, srcLang) <- blockStartParser
  let nowebOff =
        (== Just "off")
          . EM.lookup "noweb"
          $ M.fromList metaKVs
  bTokens <-
    MP.choice
      [ zeroBTokensParser blockType,
        someBTokensParser blockType (not nowebOff)
      ]
  orgParserState <- get
  let newAnonBlockNumber = case blockName of
        Just _ -> orgParserState.anonBlockNumber
        Nothing -> orgParserState.anonBlockNumber + 1
      anonBlockMeta = case blockName of
        Just _ -> Nothing
        Nothing -> Just ("__anon_block_number", T.show newAnonBlockNumber)
      blockMeta = ("__block_type", blockType)
      closestUuidMeta =
        ( "__closest_UUID",
          T.show
            . firstNonNilParent
            $ NE.toList orgParserState.orgId
        )
      block =
        Block
          { meta =
              M.fromList
                $ (blockMeta : closestUuidMeta : metaKVs)
                <> concatMap maybeToList [blockName, srcLang, anonBlockMeta],
            body =
              ignoreSpecialCommas
                . compressBTokens
                $ padConsecutiveNowebLinks bTokens
          }
  put
    orgParserState
      { anonBlockNumber = newAnonBlockNumber
      }
  pure $ CBlock block
  where
    firstNonNilParent [] = nil
    firstNonNilParent (oid : oids)
      | oid == nil = firstNonNilParent oids
      | otherwise = oid
#+end_src

The first thing is to get the start of the block with [[f:blockStartParser]].
The ~nowebOff~ bit controls how we perceive text that looks like ~<<foo>>~; see the
discussion for [[t:0007-blocks-noweb]] and [[t:0007-blocks-noweb-off]].

Blocks that don't have a name are assigned a ~__anon_block_number~ metadata
property, so that we can use this information to generate a link anchor for it
during weaving.

The tricky part is finding out the end of the block. We cannot use a single
parser and must parse the two cases of whether there is or isn't any content
inside the block separately, via =zeroBTokensParser= and =someBTokensParser=. We
need this distinction because we require blocks to end with ="\n#+end_..."= (that
is, the =#+end_...= must occur at the beginning of a line). This means that for
empty blocks, this newline character just preceding the =#+end_...= will come from
the newline at the end of the =#+begin_...= part. This then interferes with the
=char '\n'= parser we already have in [[f:blockStartParser]] just before we start
parsing for =bTokens=.

In other words, there is no easy way to tell Megaparsec to ensure that we are at
the beginning of a line. To work around this, we check whether the block is
empty with =zeroBTokensParser=.

#+name: f:zeroBTokensParser
#+begin_src haskell
zeroBTokensParser :: T.Text -> OrgParser [BToken]

  _ <- string $ T.concat ["#+end_", blockType, "\n"]
  pure []
#+end_src

If =zeroBTokensParser= fails, then =someBTokensParser= must succeed (hence the use
of ~MP.choice~ in [[f:blockParser]]).

#+name: f:someBTokensParser
#+begin_src haskell
someBTokensParser :: T.Text -> Bool -> OrgParser [BToken]
someBTokensParser blockType nowebOn =
  MP.someTill
    (bTokenParser (blockType == "src") nowebOn)
    (string $ T.concat ["\n#+end_", blockType, "\n"])
#+end_src

See [[t:0007-blocks-ending]] which checks the various edge cases around making sure
we can detect the ="\n#+end_..."= bit.

Note that because we treat the trailing newline as a part of the =#+end_...=
marker, we leave it out of the parsed contents. This actually helps us when we
have to tangle blocks in [[id:b449a097-d702-4fd6-98de-cb81f7e49177::f:expandBlock][f:expandBlock]]. If we parsed in the trailing newlines,
these newlines would build up every time we nested into a block (e.g.,
[[t:0101-block-expansion-deeply-nested]]).

Going back to [[f:blockParser]], there are three transformations we do for the
parsed ~bTokens~ --- [[f:ignoreSpecialCommas]], [[f:compressBTokens]], and
[[f:padConsecutiveNowebLinks]].

The [[f:compressBTokens]] function is similar to [[f:compressProse]], but it's simpler
because it doesn't have to deal with styled text. Instead it only deals with raw
=T.Text= values directly. We need to use =compressBTokens= because otherwise we'll
end up with many separate =BToken= values (because [[f:bTokenParser]] uses multiple
separate parsers that all use the same =BTokenString= constructor for parsing text
tokens).

#+name: f:compressBTokens
#+begin_src haskell
compressBTokens :: [BToken] -> [BToken]
compressBTokens = reverse . foldl' f []
  where
    f :: [BToken] -> BToken -> [BToken]
    f [] token = token : []
    f ((BTokenString text1) : rest) (BTokenString text2) =
      (BTokenString $ T.append text1 text2) : rest
    f acc token = token : acc
#+end_src

The [[f:ignoreSpecialCommas]] function ignores commas at the beginning of a line
(with or without indentation), when they are used to escape asterisks (~*~) and
hash signs followed by a plus character (~#+~). This is because the =org-mode= major
mode in Emacs is unable to cope with these special characters, and requires
users to put in leading commas to help the parser in that mode. Our Haskell
implementation does not need such help; however we teach our parser about this
behavior here so that we can remain compatible with =org-mode= (otherwise when
users tangle their Org file using Lilac, they might get confused why we don't
escape such leading commas).

#+name: f:ignoreSpecialCommas
#+begin_src haskell
ignoreSpecialCommas :: [BToken] -> [BToken]
ignoreSpecialCommas = reverse . foldl' f []
  where
    f acc (BTokenString text) = (BTokenString $ removeSpecialCommas text) : acc
    f acc BTokenPadding = BTokenPadding : acc
    f acc link = link : acc
    removeSpecialCommas text =
      T.intercalate "\n"
        . map removeSpecialComma
        $ T.split (== '\n') text
    removeSpecialComma line
      | hasSpecialComma line = dropLeadingComma line
      | otherwise = line
    hasSpecialComma line
      | (indentAndCommas, rest) <- T.breakOnEnd "," line,
        (indent, commas) <- T.breakOn "," indentAndCommas,
        T.stripStart indent == "",
        not $ T.null commas,
        T.all (== ',') commas,
        T.take 1 rest == "*" || T.take 2 rest == "#+" =
          True
      | otherwise = False
    dropLeadingComma line =
      let (indent, commas) = T.breakOn "," line
       in indent <> T.drop 1 commas
#+end_src

*** =bTokenParser= (code block contents)

Now let's dig into the actual block tokens (~[BToken]~) which form the contents of
the code block. These ~BToken~ values can be either text (~BTokenString~) or a Noweb
link (~BTokenLink~). Essentially all of the complexity around [[f:bTokenParser]] is
due to the need to detect Noweb references in a robust way.

#+name: f:bTokenParser
#+begin_src haskell
bTokenParser :: Bool -> Bool -> OrgParser BToken
bTokenParser isSrcBlock nowebOn = MP.choice parsers
  where
    baseParsers :: [OrgParser BToken]
    baseParsers =
      [ BTokenString
          <$> (MP.takeWhile1P (Just "block token") (`notElem` ['\n', ' ', '<'])),
        BTokenString
          . T.singleton
          <$> (MP.label "left angle bracket" $ MP.satisfy (== '<')),
        BTokenString
          . T.singleton
          <$> (MP.label "space inside block" $ MP.satisfy isSpace)
      ]
    parsers =
      if isSrcBlock && nowebOn
        then ((BTokenLink <$> MP.try nowebLinkParser) : baseParsers)
        else baseParsers
#+end_src

The need to detect Noweb references is why ~baseParsers~ has individual (separate)
parsers; having these smaller separate parsers breaks up the parsing of block
tokens into multiple separate steps. That way, no single parser is too greedy
and we can handle the edge cases such as in [[t:0007-blocks-noweb-intraline]].

Along the same vein, it's important that the space parser (~MP.satisfy isSpace~)
in ~baseParsers~ in [[f:bTokenParser]] does /not/ use ~MP.takeWhile1P~. Otherwise, it'll
greedily consume all spaces including newlines, robbing it from the ending
condition in ~someBTokensParser~ (where we expect a newline before ~#+end_~). The
parser for the ~left angle bracket~ is there to take care of an edge case where a
Noweb reference is immediately preceded by another left angle bracket ~<~; see
[[t:0007-blocks-noweb-intraline]] for details.

*** =nowebLinkParser=

The last piece is the business of parsing Noweb references. A Noweb reference is
surrounded by the double-angle-bracket delimiters =<<= and =>>=. The name itself can
be anything other than a newline or angle brackets. We wrap this with =MP.try= in
[[f:bTokenParser]], because we need to backtrack if we fail (after parsing, and
consuming, the initial =<<= bit). Backtracking allows the other parsers in
=baseParsers= to parse the remaining text that failed to be parsed as a valid
Noweb link.

The [[f:blockOriginSignatureParser]] parses information about the origin of the
block being referenced, which we call the block origin signature. For now the
origin can have an optional UUID, along with the name of the code block itself.

running some validation checks. Otherwise we assign the UUID that was parsed at
the beginning of the document in [[f:docMetaParser]], because although the link may
refer to a block that has a parent heading which has its own UUID, we don't have
that information at hand.

*** Add padding between consecutive Noweb links
:PROPERTIES:
:ID:       51f2edd8-5f8e-4c63-841f-da6c5c41680a
:END:

When we eventually tangle blocks, we want to inject some padding (a newline)
between Noweb links because each Noweb block is its own "unit" and it makes
sense to add some separation between consecutive Noweb blocks, to get some
visual separation in the final output.

We only want to add this padding for cases where there are /consecutive/ Noweb
links. For example, in

#+header: :noweb off
#+begin_src txt
<<a>>

<<b>>
<<c>>
<<d>>

  <<e>>
  <<f>>

<<g>>
#+end_src

only ~<<b>>~ ~<<c>>~ ~<<d>>~ and ~<<e>>~ ~<<f>>~ are consecutive. And in the final tangled
output we would want to make it as if we had originally written

#+header: :noweb off
#+begin_src txt
<<a>>

<<b>>

<<c>>

<<d>>

  <<e>>

  <<f>>

<<g>>
#+end_src

This allows us to write in a bit more compact manner in the Org source document,
while still giving each Noweb link (and associated block) some separation from
the other blocks in the tangled output.

The way we do this automatic padding is by injecting newlines into the parsed
block's body ~BToken~ values, as ~BTokenString "\n"~. This is what we do by calling
[[f:padConsecutiveNowebLinks]] in [[f:blockParser]].

The high-level algorithm is as follows:

  1) Concatenate the ~BToken~ values together (using the ~T.Text~ representation).
     For ~BTokenString~ values we use the inner text information as is. For
     ~BTokenLink~ we use the target, but also inject a special [[link-marker]] which
     uses an ASCII ~NUL~ character.

  2) Split the contents by newline.

  3) Group together the lines that have Noweb links. In other words, consecutive
     lines that have Noweb links are grouped together.

  4) Within each group, only mark the links at the end of the line (because
     there may be more than one link in a line) as needing a newline. By marking
     links as needing (or not needing) a newline, we can easily inject newlines
     at the right spots in the next step.

     We can't add a newline for the very last line in the group though, because
     that would be superfluous (we want to add newlines *between* consecutive
     blocks, not after every consecutive block).

  5) Using the information from the previous step, iterate through all ~BToken~
     values and whenever we see a ~BTokenLink~, inject the newline (if the link
     was marked as needing a newline).

The markers are just simple boolean values (one for each Noweb link found in the
block).

Now let's look at the implementation in detail. Step 1 is done in
[[f:getBlockContents]].

#+name: f:getBlockContents
#+begin_src haskell
getBlockContents :: [BToken] -> T.Text
getBlockContents blockBody = T.concat $ map bTokenToText blockBody
  where
    bTokenToText :: BToken -> T.Text
    bTokenToText = \case
      BTokenString text -> text
      BTokenPadding -> ""
      BTokenLink (Link _name (LinkTargetNoweb (LinkNoweb uuid targetName))) ->
        <<link-marker>> <> (LU.prefixWithId uuid targetName)
      BTokenLink {} -> ""
#+end_src

The ~<<link-marker>>~ is just a special marker we use to keep track of where the
links are inside the concatenated (single) ~T.Text~ value representing all of the
block contents.

#+name: link-marker
#+begin_src haskell
"\NUL_link"
#+end_src

Steps 2, 3, and 4 are all done inside [[f:getLinkPaddingBools]]. This function
returns a list of booleans that correspond to each of the Noweb links found. If
~True~, this means the link needs a trailing newline (padding) added to it.

The line ~map (reverse . (zip $ False : repeat True) . reverse)~ says to only pad
the lines except for the last one, and ~distributeBools~ only pads the very last
link found in the line.

#+name: f:getLinkPaddingBools
#+begin_src haskell
getLinkPaddingBools :: [BToken] -> [Bool]
getLinkPaddingBools blockBody =
  concatMap (concatMap distributeBools)
    . map (reverse . (zip $ False : repeat True) . reverse)
    . groupBy consecutiveNowebLines
    . T.lines
    $ getBlockContents blockBody
  where
    consecutiveNowebLines :: T.Text -> T.Text -> Bool
    consecutiveNowebLines a b = (countLinks a > 0) && (countLinks b > 0)
    distributeBools (False, line) =
      replicate (countLinks line) False
    distributeBools (True, line) =
      case countLinks line of
        1 -> [True]
        n -> reverse $ True : replicate (n - 1) False
    countLinks = T.count <<link-marker>>
#+end_src

Now that we have a list of booleans to mark whether a link needs a newline
appended to it, all we have to do is go through all of the links in the block,
adding a ~BTokenPaddding~ every time we see a ~True~ boolean (~padLink~).

#+name: f:padConsecutiveNowebLinks
#+begin_src haskell
padConsecutiveNowebLinks :: [BToken] -> [BToken]
padConsecutiveNowebLinks blockBody =
  reverse
    . fst
    $ foldl' f ([], getLinkPaddingBools blockBody) blockBody
  where
    f (acc, bools) text@(BTokenString _) = (text : acc, bools)
    f (acc, bools) BTokenPadding = (acc, bools)
    f (acc, bools) link@(BTokenLink _) =
      case bools of
        (padLink : rest)
          | padLink -> (BTokenPadding : link : acc, rest)
          | otherwise -> (link : acc, rest)
        [] -> (link : acc, [])
#+end_src

See [[id:b449a097-d702-4fd6-98de-cb81f7e49177::t:0102-pad-between-consecutive-links][t:0102-pad-between-consecutive-links]] for an example of this padding
behavior.

** List items
:PROPERTIES:
:ID:       58f69993-599d-4389-ba47-3056b1bb2350
:END:

A /list item/ is made up of a /list head/ and /list body/. Consider the following
list:

  1) a

     b

     - c

     d

  2) e

Here the =1)= and =2)= are list heads for an /ordered/ list. The single dash =-= before
"c" is also a list head, but for an /unordered/ list. The list body for =1)=
includes the paragraphs =a=, =b=, the nested list item =c=, and the paragraph =d=. There
are two list items for the top-level ordered list =1)= and =2)=.

List heads encode the structure of cells that sit in the list bodies. So list
items encode both structure and content. In this manner they are similar to
[[id:16a68a74-d4cc-41a4-ac77-cbca77de2a31][headings]]. However unlike headings, a list item can have multiple other cells
(paragraphs, tables, or even code blocks) in its body, whereas a heading can
only have a single line of prose.

Another difference is that a list item can have content for it /after/ backing out
of a nested list item. For example in the list shown above the ~d~ paragraph is
part of the ordered list item ~1)~ even though the nested item ~c~ is just above it;
this sort of structure is now allowed for headings. For example, in the
following situation

#+begin_src org
,* a
,** b
#+end_src

anything that comes after ~** b~ will be part of the ~** b~ heading; there is no way
to make it belong to ~* a~ (any such content must be placed /before/ ~** b~).

Below we have a look at some more detailed rules around how lists may be written
in an Org file.

*** Detailed rules
:PROPERTIES:
:ID:       32d34523-2148-4f2f-b2f3-2a2543a7d57c
:END:

Below are some detailed rules around /ordered/ list items, themselves expressed as
ordered list items, which are important for parsing:

  1) List items start out with 2-space indentation. This makes them easier to
     read from the raw Org file. The amount of additional indentation (in order
     to have nested list items) depends on where the text began in the parent
     item. See items "5)" and "10)" below for examples.

     - [[t:0009-list-indentation-no-indent]]

     - [[t:0009-list-indentation-proper-indent]]

  2) List items must be separate from each other with a blank line. This makes
     them easier to read when reading the Org file in plain text.

     - [[t:0009-list-items-need-blank-line-separator]]

  3) Additional hard-wrapped lines for a list item must be aligned with the text
     of the first line. This list item is an example of such a line.

     - [[t:0005-paragraph-indentation-mismatch-over-list-body]]

     - [[t:0005-paragraph-indentation-mismatch-over]]

     - [[t:0005-paragraph-indentation-mismatch-under-list-body]]

     - [[t:0005-paragraph-indentation-mismatch-initial-indent-invalid]]

     - [[t:0005-paragraph-indentation-mismatch-initial-indent-invalid-between-indent-levels]]

  4) List items can have more than one paragraph associated with them.

     This is an example of another paragraph which is still part of the "4)"
     list item, and has 5 spaces of indentation.

     - [[t:0009-list-content-simple]]

  5) List items can be nested.

     1) This is a nested item, underneath "5)". It has 5 spaces of initial
        indentation, where the "1" in "1)" lines up with the column where the
        "L" in "5) List" in the parent item. Subsequent lines of this paragraph
        have 8 spaces of indentation to line up with the text above it.

     See:

     - [[t:0009-list-indentation-nested]]

     - [[t:0009-list-indentation-nested-with-text]]

     - [[t:0009-paragraph-can-close-deeper-levels]]

  6) Unlike Markdown, the numbers of the list item must increase by one if there
     are additional items at the same level. The first number of a level may
     start from any non-negative number; for example, 0, 1, 5, 12 are all valid
     starting numbers.

     - [[t:0009-ordered-lists-require-increment]]

     - [[t:0009-ordered-lists-start-from-0-or-1]]

  7) The format for ordered list items requires a closing parenthesis
     immediately after the number. So =1)= is valid, but =1.= is invalid.

     - [[t:0009-ordered-list-head-needs-parenthesis]]

  8) Only numbers may be used to denote item position. You cannot use letters or
     Roman numerals.

     - [[t:0009-ordered-list-head-cannot-use-letters]]

  9) There is no limit to the number of consecutive list items at the same
     level (technically, we use an =Int= type to encode the number, so it will
     eventually max out, but you'd need millions of items to hit this limit).

  10) The indentation of text changes slightly depending on the number of the
      item. For example, this line has 6 spaces of indentation, unlike the
      paragraphs in item "4)" above, which uses 5 spaces.

      1) Similarly, this child item has text which has 9 spaces of indentation,
         unlike the 8 spaces of indentation in the ordered child item under item
         "5)" above.

      See:

      - [[t:0009-lists-require-precise-indentation]]

  11) There can only be up to 5 additional levels of nesting (for a total of 6
      levels of items). This is because excessive nesting is an anti-pattern.
      See the ~lilac_maxListLevel~ [[id:84edd33a-a146-4a46-ac0a-cd1c3d0926d3][Lilac extension]] for customizing this behavior.

      - [[t:0009-list-nesting-max]]

      - [[t:0009-list-nesting-max-8]]

      - [[t:0009-lists-prohibited]]

  12) Ordered list items may have unordered list items (discussed next) as
      children, and vice versa. However you may not mix the two types of items
      at the same level.

      - [[t:0009-paragraph-can-separate-mixed-lists]]

      - [[t:0009-lists-cannot-be-mixed-on-their-own]]

      - [[t:0009-lists-cannot-be-mixed-on-their-own-ordered]]

  13) A list item may include a table. However the table cannot be on the same
      line as the list item head. Below is an example of such a table:

      | foo | bar |
      |-----+-----|
      | x   | y   |

      - [[t:0012-tables-inside-lists]]

  14) Similarly, a list item may include mathematical equations. However, such
      an equation must be on a separate line from the list item head, just like
      for tables (see Rule 13 above).

      \[
         a + b = c
      \]

      The equation above (and this paragraph) are still part of Rule 14.

      - [[t:0010-standalone-math-inside-lists]]

  15) Lists may be empty. For example, the following child list is valid even
      though it does not have any content:

      1)

      2)

      3)

      See:

      - [[t:0009-list-indentation-nested]]

Unordered list items use a single dash character =-=, and always use 2-space
indentation (if you are only using unordered list items for nesting). Below is
an example:

  - one

  - two

    - foo

    - bar

  - three

Here's an example of mixing ordered and unordered lists:

  - foo

  - bar

    1) one

    2) two

       - baz

       - quux

       Note how this paragraph is under item "2", because it is indented the
       same way as "two", not "quux", above.

    3) three

  - dog

You may mix ordered and unordered lists at the same indentation level, as long
as they are not consecutive (you need some intervening cells, such as the "quux"
paragraph below):

  - foo

    1) one

    2) two

    quux

    - a

    - b

*** Indentation and =ListMarker=

Parsing list items is tricky because of meaningful indentation (whitespace).
Keeping track of the current level of indentation requires additional state
during parsing, which we encode with =Level= (used by =listLevels= in
[[data:OrgParserState]]).

#+name: data:Level
#+begin_src haskell
type Level :: Type
data Level = Level
  { indent :: Int,
    number :: Maybe Int
  }
  deriving stock (Eq, Show)
#+end_src

This keeps track of the indentations and the last seen number of each (nested)
level of indentation thus far during parsing. Whenever we see a list head like
=1)= or ~-~, we record the number used as well as the indentations we expect for the
list head and list body. The main point of =listLevels= is to ensure that the
input is correctly formatted, as well as to detect whenever we start nesting an
additional level, or if we back out (finish) one or more levels of nesting (when
we see dedented text).

As we observe how these =listLevels= change during parsing, we create "start" and
"end" markers for list items at a particular level, which are the values of the
[[data:ListMarker]] type. The =ListMarker= objects are parsed as their own cell as a
=CListItem= (see [[data:Cell]]).

#+name: data:ListMarker
#+begin_src haskell
type ListMarker :: Type
data ListMarker
  = LOrderedStart
  | LOrderedEnd
  | LUnorderedStart
  | LUnorderedEnd
  | LItemStart
  | LItemEnd
  deriving stock (Eq, Generic, Show)

instance ToJSON ListMarker
#+end_src

We take this model from HTML, which uses =<ol>= and =</ol>= to encode the start and
end of ordered lists (=<ul>= and =</ul>= for unordered lists), and =<li>= and =</li>= to
mark the start and en of a single list item.

#+name: tbl:List markers
| ListMarker      | HTML equivalent |
|-----------------+-----------------|
| LOrderedStart   | ~<ol>~            |
| LOrderedEnd     | ~</ol>~           |
| LUnorderedStart | ~<ul>~            |
| LUnorderedEnd   | ~</ul>~           |
| LItemStart      | ~<li>~            |
| LItemEnd        | ~</li>~           |

In summary when we parse a list item, we parse it as a combination of =CListItem=
and other cell types for the list structure and content, respectively. This lets
us parse things into a single global list of cells in [[f:cellParser]], without a
need to nest them inside a recursive data structure (as shown in
https://markkarpov.com/tutorial/megaparsec.html#nested-indented-list).

*** Parsing initial indentation to close list items
:PROPERTIES:
:ID:       5990dd7f-2f37-4a9e-96ea-6cc6b2e20dc0
:END:

Before getting into parsing the list items and taking into account all of the
[[id:32d34523-2148-4f2f-b2f3-2a2543a7d57c][detailed rules]], let's first consider case where we just want to /close off/ the
list items, as this is simpler than creating list items. We want to do this
every time we parse initial indentation where there is no list head. For
example, in the following

  1) a

     - b

     c

the indentation for paragraph =c= should by itself close off the preceding
unordered list item (~- b~). We can close off existing list items depending on the
amount of indentation:

  1) if there is no indentation, we close off /all/ list items;

  2) if there is maximum (already-seen) indentation (to line up with the
     most-nested list item), we don't close off any list items because we're
     just continuing the most-nested list item;

  3) otherwise, we have some amount of indentation and we only want to close off
     some list levels, depending on how much indentation we detect.

If there is more indentation than the maximum, then we are nesting another level
and don't need to close off anything. That's why this situation is not listed
above.

Point 1 is captured by =zeroIndent= in [[f:listItemsEndParser]]. Points 2 and 3 are
captured by =someIndent= in the same function.

#+name: f:zeroIndent
#+begin_src haskell
zeroIndent :: OrgParser (Int, Int)
zeroIndent = do
  orgParserState <- get
  _ <- MP.eof <|> MP.notFollowedBy (char ' ')
  let listLevelsToClose = length orgParserState.listLevels
      continuationIndent = 0 :: Int
  pure (listLevelsToClose, continuationIndent)
#+end_src

In [[f:zeroIndent]] we return the number of list levels to close off (in this case
all levels that we've detected so far), and the continuation indent. The
continuation indent is used by other parsers such as the [[f:paragraphParser]] to
see how to join up multiple lines into the same cell, assuming those lines have
the same continuation indent (the lines /continue/ if it's the same indent, hence
the name). For the case of [[f:zeroIndent]], we set the continuation indent to 0
because there is no indentation, and any subsequent lines belonging to the same
cell should /not/ have any indentation (it is considered invalid input if we see
surprise indentation; see [[t:0005-paragraph-indentation-mismatch-over]]).

For =someIndent=, we just try to line up the amount of indentation found with the
existing list levels we have and how much indentation they expect.

#+name: f:someIndent
#+begin_src haskell
someIndent :: OrgParser (Int, Int)
someIndent = do
  orgParserState <- get
  indentFound <- T.length <$> MP.takeWhile1P (Just "indentation") (== ' ')
  let levelsToDropPerIndentationIncrement :: [(Int, Int)]
      levelsToDropPerIndentationIncrement =
        zip [0 ..]
          . map getContinuationIndentForLevel
          $ orgParserState.listLevels
      matchingIndent =
        find
          (\(_, continuationIndent) -> indentFound == continuationIndent)
          levelsToDropPerIndentationIncrement
  case matchingIndent of
    Nothing -> fail "indentation does not fit into existing levels"
    Just x -> pure x
#+end_src

It should be noted that the ~orgParserState.listLevels~ is grown by prepending to
the list in [[f:listItemNester]]. So the most-deeply-nested level will be at the
head of the list in ~orgParserState.listLevels~. That's why we use ~zip [0 ..]~ ---
we want to drop 0 levels if we see indentation matching the most deeply-nested
list item.

The [[f:getContinuationIndentForLevel]] just computes the total indentation for a
list level. For example, in

#+begin_src org
  1) foo
#+end_src

we compute the initial 2 spaces before the ~1)~, the ~1)~ itself (two characters),
plus a space character, or a total continuation indent of 5. The dynamic portion
here is the number, which will grow as the list grows (e.g., ~10)~ will have a
total continuation indent of 6), which is why we use a function here instead of
a constant.

#+name: f:getContinuationIndentForLevel
#+begin_src haskell
getContinuationIndentForLevel :: Level -> Int
getContinuationIndentForLevel level = level.indent + maybeNum + punctuation + space
  where
    punctuation :: Int
    punctuation = 1
    space :: Int
    space = 1
    maybeNum :: Int
    maybeNum = case level.number of
      Just n -> length $ (show n :: String)
      Nothing -> 0
#+end_src

Once we determine the amount of levels we need to close off (by parsing
[[f:zeroIndent]] or [[f:someIndent]]), we just go through the list markers we've already
seen in =listMarkers= and close them off via [[f:getEndingListMarkers]]. This is what
we do in [[f:listItemsEndParser]].

#+name: f:listItemsEndParser
#+begin_src haskell
listItemsEndParser :: OrgParser Cell
listItemsEndParser = do
  orgParserState <- get
  when (null orgParserState.listMarkers) $ do
    fail "no pending ListMarker objects to close off"
  when (orgParserState.continuationIndent /= 0) $ do
    fail "not at beginning of line"
  (levelsToDrop, continuationIndent) <- zeroIndent <|> someIndent
  let markers = getEndingListMarkers levelsToDrop orgParserState.listLevels
  put
    orgParserState
      { listLevels = drop levelsToDrop orgParserState.listLevels,
        listMarkers = drop (levelsToDrop * 2) orgParserState.listMarkers,
        continuationIndent = continuationIndent
      }
  pure $ CListItem markers
#+end_src

In [[f:listItemsEndParser]], note that we initially fail the parser if there are no
pending =ListMarker= objects (no list levels to close off), or if we're not at the
beginning of the line (because otherwise we cannot measure indentation
accurately), by checking =orgParserState.continuationIndent=. This check of
=orgParserState.continuationIndent= is required because there is no easy way to
check for the just-parsed token (or character) in Megaparsec --- all parsers
only see what's in front of it. So then it's up to other parsers to set this to
some value greater than =1= (we do this in [[f:listHeadIndentLevelParser]] which is
part of [[f:listItemStartParser]])

The =markersToDrop= is always twice the number of =levelsToDrop= because we always
add 2 for each level (see [[f:listItemNester]]).

If we detect the maximum allowed indentation, then there are no levels to drop,
and hence, we'll end up returning =CListItem []= which doesn't hold any meaning.
Avoiding this is a bit difficult; if we just fail the parser outright, then the
amount of parsed indentation will have to be parsed by another downstream parser
(this can get messy). So instead we just return =CListItem []= and then filter
these out in [[f:orgDocParser]]. This way we decide once and for all how to deal
with leading indentation (and how this closes off existing list items) in
[[f:listItemsEndParser]].

The [[f:getEndingListMarkers]] function understands how to close off list levels
based on whether the level uses an ordered or unordered list item.

#+name: f:getEndingListMarkers
#+begin_src haskell
getEndingListMarkers :: Int -> [Level] -> [ListMarker]
getEndingListMarkers levelsToDrop = concatMap f . take levelsToDrop
  where
    f :: Level -> [ListMarker]
    f level = case level.number of
      Nothing -> [LItemEnd, LUnorderedEnd]
      Just _ -> [LItemEnd, LOrderedEnd]
#+end_src

*** Parsing list heads

In the [[id:5990dd7f-2f37-4a9e-96ea-6cc6b2e20dc0][previous section]] we considered how to close off list items based purely
on indentation. Parsing list heads is similar (because list heads can also close
off list items), but more complicated because we also have to take into account
how to create list items (list levels). This means we have to deal with all of
the possible values of [[data:ListMarker]] here.

Parsing the list head (and therefore the [[data:Level]] of a list item) is
straightforward. For unordered lists we just want to see a dash.

#+name: f:unorderedHeadParser
#+begin_src haskell
unorderedHeadParser :: OrgParser (Maybe Int)
unorderedHeadParser = do
  _ <- char '-'
  pure Nothing
#+end_src

For ordered lists we want to see the number and closing parenthesis.

#+name: f:orderedHeadParser
#+begin_src haskell
orderedHeadParser :: OrgParser (Maybe Int)
orderedHeadParser = do
  num <- MP.takeWhile1P (Just "ordered list number") isDigit
  _ <- char ')'
  let n = readMaybe (T.unpack num) :: Maybe Int
  when (isNothing n) $ do
    fail $ "could not parse " <> show (T.unpack num) <> " as Int"
  pure n
#+end_src

We check if the number looks like an =Int= with =readMaybe=.

For both cases we also parse leading indentation and also an additional space at
the end to separate the list head from the body. These considerations are
encoded in =listHeadIndentLevelParser= below.

#+name: f:listHeadIndentLevelParser
#+begin_src haskell
listHeadIndentLevelParser :: OrgParser Level
listHeadIndentLevelParser = do
  minimalIndentation
  spaces <- MP.takeWhile1P (Just "indentation") (== ' ')
  listHead <- unorderedHeadParser <|> orderedHeadParser
  let level =
        Level
          { indent = T.length spaces,
            number = listHead
          }
  afterListHead level
  pure level
  where
    minimalIndentation :: OrgParser ()
    minimalIndentation =
      void
        . MP.try
        . MP.lookAhead
        . MP.label "minimal indentation"
        $ MP.count 2 (char ' ')
    afterListHead :: Level -> OrgParser ()
    afterListHead level =
      void
        $ MP.choice
          [ MP.eof,
            void $ string "\n",
            void $ seeingContentAfterListHead level
          ]
    seeingContentAfterListHead :: Level -> OrgParser ()
    seeingContentAfterListHead level = do
      _ <- char ' '
      MP.notFollowedBy (char ' ')
      modify (\s -> s {continuationIndent = getContinuationIndentForLevel level})
#+end_src

The ~minimalIndentation~ expects there to be at least 2 spaces preceding a list
item. This follows Rule 1 from [[id:32d34523-2148-4f2f-b2f3-2a2543a7d57c][Detailed rules]].

The =afterListHead= parser preemptively checks what's in the input /after/ parsing
the list head. In the case where it sees some other non-empty content, it
expects some other parser to continue parsing. So inside
=seeingContentAfterListHead= we set the =continuationIndent= attribute to
indentation of the current level, because we expect another parser to help us
finish parsing the line. Then at the [[f:cellParser]] level, we set this back to =0=
for any parser that is expected to consume content and end with a newline. This
lets [[f:listItemsEndParser]] know whether it is looking at EOF or at the beginning
of a line when it inspects =continuationIndent=. If Megaparsec can let us easily
check the previous character that was parsed, this scheme of using a stateful
=continuationIndent= field wouldn't be necessary.

Note, however, that [[f:listHeadIndentLevelParser]] only checks for textual
correctness. It doesn't check whether what's parsed is semantically correct. For
example, we wouldn't want to blindly parse the number of spaces in the indent
(instead we would want to check which indents are expected, given any previous
list items). Similarly we would want to check whether the list head number (for
ordered lists) is the expected (incremented) number from the previously-seen
list head number, if any (or if there is no previous number, that this number is
0 or 1).

We have to perform these additional checks by comparing the output of
=listHeadIndentLevelParser= against the existing [[data:OrgParserState]] (=listLevels=).
This is what we do in =listItemStartParser= below.

#+name: f:listItemStartParser
#+begin_src haskell
listItemStartParser :: OrgParser Cell
listItemStartParser = do
  _ <- MP.try $ MP.lookAhead listHeadIndentLevelParser
  orgParserState <- get
  let levels = orgParserState.listLevels
  level <- listHeadIndentLevelParser
  listMarkers <-
    if nestsBeyond levels level
      then listItemNester level levels
      else listItemFitter level levels
  pure $ CListItem listMarkers
  where
    nestsBeyond :: [Level] -> Level -> Bool
    nestsBeyond [] _ = True
    nestsBeyond (deepestLevel : _) level =
      getContinuationIndentForLevel deepestLevel == level.indent
#+end_src

The first line ~_ <- MP.try $ MP.lookAhead listHeadIndentLevelParser~ is needed
because otherwise as soon as Megaparsec sees any indentation (as part of
invoking [[f:listHeadIndentLevelParser]]) it will expect to see a list head;
obviously this is not always the case as not all indentation leads to a list
head. This is why we have to perform this look-ahead preemptively.

The ~nestsBeyond~ function just checks whether the indentation we found in the
(just-parsed) level is the same as the continuation indent of the
most-deeply-nested level we have so far. This is how we nest one level deeper
than the current level. If this is the case, we delegate to [[f:listItemNester]].

Otherwise the list item is merely continuing some existing list, for which we
delegate to [[f:listItemFitter]].

*** Nesting the list item beyond the current level

=listItemNester= appends starting markers to =listMarkers=. We use this information
in other places when we want to know how to un-nest an item (close it off),
such as in [[f:listItemsEndParser]] where we add corresponding closing markers with
=getEndingMarker=. The other place we use =listMarkers= is in [[f:listItemFitter]].

#+name: f:listItemNester
#+begin_src haskell
listItemNester :: Level -> [Level] -> OrgParser [ListMarker]
listItemNester level levels = do
  case level.number of
    Just 0 -> pure ()
    Just 1 -> pure ()
    Just n -> fail $ "starting list head number must be 0 or 1; got " <> show n
    Nothing -> pure ()
  orgParserState <- get
  let newMarker = case level.number of
        Just _ -> LOrderedStart
        Nothing -> LUnorderedStart
      opc = orgParserState.orgParserConf
  when (opc.maxListLevel > 0 && length levels == opc.maxListLevel) $ do
    fail
      $ "max nesting depth exceeded: cannot have more than "
      <> show opc.maxListLevel
      <> " levels of list items"
  put
    orgParserState
      { listLevels = level : levels,
        listMarkers = LItemStart : newMarker : orgParserState.listMarkers
      }
  pure [newMarker, LItemStart]
#+end_src

We enforce some additional rules here, such as forcing the nesting list head to
start off with either 0 or 1 (see [[t:0009-ordered-lists-start-from-0-or-1]]). The
rest of the function just updates the ~orgParserState~ to have the additional
~level~ as the new most-deeply-nested level, and also grows the ~listMarkers~
accordingly.

*** Fitting the list item into an existing level

The goal of [[f:listItemFitter]] is twofold:

  1) continue an existing list, and

  2) close off (finish) pending levels which are still open.

The first task is easy --- we just append =[LItemEnd, LItemStart]= to signal that
we are closing off the existing list item (at the same level), and starting a
new list item (also at the same level).

The second task is a bit more involved. We have to "close" any existing levels
that are more deeply nested, just like in [[f:listItemsEndParser]]. For example, in
the following list

  1) foo

     - bar

       1) baz

  2) quux

when we hit "quux" we have to close off the list environments for "baz", then
"bar". However, unlike [[f:listItemsEndParser]], we have to /continue/ the list level
that we fit into. For ordered list items, this means keeping the latest
incremented ordered list item at the current level. This is why we have to drop
an extra level in ~listLevels~ in the ~fitter~ function, and then replace it with
the current level; if we don't do this then our ordered list items will never
get incremented.

#+name: f:listItemFitter
#+begin_src haskell
listItemFitter :: Level -> [Level] -> OrgParser [ListMarker]
listItemFitter level levels =
  case find (\(_, l) -> l.indent == level.indent) (zip [0 ..] levels) of
    Nothing -> fail "list item: invalid indentation"
    Just (levelsToDrop, lvl)
      | isJust level.number && isJust lvl.number ->
          let expectedNum = fmap (+ 1) lvl.number
           in if level.number == expectedNum
                then fitter levelsToDrop
                else
                  fail
                    $ "expected incremented list head "
                    <> (show . fromJust $ expectedNum)
                    <> " but got "
                    <> (show . fromJust $ level.number)
      | isNothing level.number && isNothing lvl.number -> fitter levelsToDrop
      | isJust lvl.number -> fail "expected ORDERED list item at this level"
      | otherwise -> fail "expected UNORDERED list item at this level"
  where
    fitter :: Int -> OrgParser [ListMarker]
    fitter levelsToDrop = do
      orgParserState <- get
      let markers = getEndingListMarkers levelsToDrop orgParserState.listLevels
      put
        orgParserState
          { listLevels = level : drop (levelsToDrop + 1) orgParserState.listLevels,
            listMarkers = drop (levelsToDrop * 2) orgParserState.listMarkers
          }
      pure $ markers <> [LItemEnd, LItemStart]
#+end_src

We use [[f:listItemStartParser]] and [[f:listItemsEndParser]] inside
[[f:cellParser]]; the former identifies and the beginnings of list items, while
the latter recognizes their (complete) end when there is no more indentation.

=\end{<ENVIRONMENT>}=, where =<ENVIRONMENT>= can be anything. Presumably you could
inject images and illustrations; however those other non-mathematical facilities
are already supported by other Org features such as external links, so we don't
support them here.

Instead Lilac only supports Latex fragments for typesetting math. Because we
only support math, we call them /math/ fragments.

#+name: data:MathFragment
#+begin_src haskell
type MathFragment :: Type
data MathFragment = MathFragment
  { meta :: M.Map T.Text T.Text,
    body :: T.Text
  }
  deriving stock (Eq, Generic, Show)

instance ToJSON MathFragment
#+end_src

There are three ways to write math fragments: using =\begin{equation}= and
=\end{equation}=, =\[ ... \]=, or =\( ... \)=. The first two ways requires them to
start at the beginning of the line, while the third way allows them to be
embedded inside prose text (and displayed inside the paragraph). The third way
has already been discussed in [[f:mathFragmentInlineParser]], where it is used in
[[f:proseParser]]. So we limit our discussion here to parsing the first two ways,
which are /standalone/ math fragments. They are called standalone because they are
their own [[data:Cell][cells]] (as ~CMathFragment~ in [[f:mathFragmentStandaloneParser]]) and don't
need to be part of another cell.

Use the first form for a standalone equation like this

\begin{equation}
2 + 2 = 4.
\end{equation}

where the equation will get numbered and centered on its own. Use

\[2 + 2 = 4\]

to achieve the same effect, but without numbering. Finally, use inline math
delimiters like this: \(1 - 1 = 0\) which can be placed inside prose text (and
displayed inside the paragraph).

When using the standalone form, you can assign a =#+name= keyword to it to refer
to the equation using a human-friendly name, like this:

#+name: eq:Pythagorean Theorem
\begin{equation}
a^2 + b^2 = c^2
\end{equation}

and you can link back to it using an internal link like [[eq:Pythagorean Theorem]].

Let's first see how to parse =\begin{equation}=.

#+name: f:mathFragmentNumberedParser
#+begin_src haskell
mathFragmentNumberedParser :: OrgParser MathFragment
mathFragmentNumberedParser = do
  orgParserState <- get
  let number = orgParserState.equationNumber + 1

  metaKVs <- metaParser
  _ <- lexeme $ string "\\begin{equation}"
  latex <-
    MP.someTill
      (MP.label "LaTeX standalone numbered math input" MP.anySingle)
      (string "\\end{equation}")

  modify (\s -> s {equationNumber = number})
  pure
    MathFragment
      { meta =
          M.insert "__equation_number" (T.pack $ show number) metaKVs,
        body = trimTrailingWhitespace $ T.pack latex
      }
#+end_src

The call to [[f:trimTrailingWhitespace]] cleans up any trailing whitespace we parsed
into ~latex~.

#+name: f:trimTrailingWhitespace
#+begin_src haskell
trimTrailingWhitespace :: T.Text -> T.Text
trimTrailingWhitespace = T.dropWhileEnd (\c -> T.elem c " \n\r\t")
#+end_src

Parsing unnumbered equations is almost the same.

#+name: f:mathFragmentUnnumberedParser
#+begin_src haskell
mathFragmentUnnumberedParser :: OrgParser MathFragment
mathFragmentUnnumberedParser = do
  metaKVs <- metaParser
  _ <- lexeme $ string "\\["
  latex <-
    MP.someTill
      (MP.label "LaTeX standalone unnumbered math input" MP.anySingle)
      (string "\\]")
  pure
    MathFragment
      { meta = metaKVs,
        body = trimTrailingWhitespace $ T.pack latex
      }
#+end_src

We simply combine the numbered and unnumbered parsers together in the top-level
[[f:mathFragmentStandaloneParser]].

#+name: f:mathFragmentStandaloneParser
#+begin_src haskell
mathFragmentStandaloneParser :: OrgParser Cell
mathFragmentStandaloneParser =
  CMathFragment
    <$> (MP.try mathFragmentNumberedParser <|> mathFragmentUnnumberedParser)
#+end_src

Unlike [[f:tableLineParser]] and [[f:tableRowParser]], we don't use
~orgParserState.continuationIndent~ to check which lines are part of the math
fragment; we simply parse everything up until the end marker (~\end{equation}~ or
~\]~). This simplifies the parsing implementation. The downside is that we may
accept input where the indentation across multiple math lines looks messy, but
this is something the user should take care of anyway.

A [[data:Figure][Figure]] is just a link to an image file, with some metadata.

#+name: data:Figure
#+begin_src haskell
type Figure :: Type
data Figure = Figure
  { meta :: M.Map T.Text T.Text,
    link :: Link
  }
  deriving stock (Eq, Generic, Show)

instance ToJSON Figure
#+end_src

Below is an example of a figure:

#+name: fig:Portable Network Graphics sample image
#+attr_html: :width 100%
[[./image/PNG-Gradient.png]]

First we have parse for the metadata, and then the link.

#+name: f:figureParser
#+begin_src haskell
figureParser :: OrgParser Cell
figureParser = do
  _ <- MP.try $ MP.lookAhead (metaParser >> bracketedLinkParser >> endOfCell)
  metaKVs <- metaParser
  link <- bracketedLinkParser
  pure
    . CFigure
    $ Figure
      { meta = metaKVs,
        link = link
      }
  where
    endOfCell :: OrgParser ()
    endOfCell =
      MP.choice
        [ void . MP.try $ string "\n\n",
          char '\n' >> MP.eof
        ]
#+end_src

It's important that we expect the end of the cell (double newline or newline and
~MP.eof~), because otherwise we'll end up parsing the link at the start of a
paragraph cell as a figure. This parser can be even more strict with the input
(as it should be the case anyway for figures), but for now we keep things
simple with this ~endOfCell~ rule.

The metadata is parsed with =metaParser= which relies on =metaEntryParser=.

#+name: f:metaParser
#+begin_src haskell
metaParser :: OrgParser (M.Map T.Text T.Text)
metaParser = do
  metaKVs <- many $ lexeme metaEntryParser
  pure $ M.fromList metaKVs
#+end_src

The [[f:metaEntryParser]] is similar to [[f:docMetaEntryParser]]. In the latter, we use
=avoidParsingBlockMetadata= to avoid touching on the toes of =blockMetaEntryParser=,
but here we don't need to do that because we use =lookAhead= in [[f:figureParser]] to
look for a link that follows metadata --- so we are guaranteed (after we parse
some metadata) that it will only be for a link (figure), not a [[data:Block]] or
some other type.

We still have to check that each metadata line does not start with =#+begin_=
because otherwise this will also succeed for blocks (even inside the =lookAhead=
in [[f:figureParser]]).

#+name: f:metaEntryParser
#+begin_src haskell
metaEntryParser :: OrgParser (T.Text, T.Text)
metaEntryParser = do
  _ <- MP.notFollowedBy $ string "#+begin_"
  _ <- string "#+"
  key <- MP.takeWhile1P (Just "(meta) keyword letter") isKeywordLetter
  _ <- MP.label "(meta) separator" $ string ": "
  _ <- many $ char ' '
  value <- MP.takeWhile1P (Just "(meta) value letter") (\c -> c /= '\n')
  pure (key, value)
  where
    isKeywordLetter c = or $ map ($ c) [isAsciiLower, (== '_')]
#+end_src

[[Tables][Tables]] are like [[data:Figure][figures]] in that they have some metadata. Unlike a figure which
is just a link, a table has a two-dimensional grid with some information in each
row\/column. The requirement is that the first non-whitespace character starts
with a vertical bar (=|=), also known as the pipe character in UNIX.

#+name: data:Table
#+begin_src haskell
type Table :: Type
data Table = Table
  { meta :: M.Map T.Text T.Text,
    grid :: M.Map (Int, Int) Prose
  }
  deriving stock (Eq, Generic, Show)

instance ToJSON Table
#+end_src

Below is an example of a table:

#+name: tbl:Programming languages
| Language | Typing          |
|----------+-----------------|
| LISP     | dynamic, strong |
| C        | static, weak    |
| Haskell  | static, strong  |

Because we named the above with a ~#+name~ keyword, we can refer to it as
[[tbl:Programming languages]].

The very first line of the table determines the number of expected columns. Org
syntax allows for horizontal lines inside the table like ~|---+-----|~, but these
are ignored.

#+name: f:tableParser
#+begin_src haskell
tableParser :: OrgParser Cell
tableParser = do
  _ <- MP.try $ MP.lookAhead (metaParser >> tableRowParser)
  metaKVs <- metaParser
  rows <- MP.some $ tableLineParser <|> tableRowParser
  pure
    . CTable
    $ Table
      { meta = metaKVs,
        grid = M.fromList $ rowsToTuples rows
      }
#+end_src

The [[f:tableLineParser]] skips over horizontal rules that typically separate the
table heading (column names) from the rest of the rows that hold the actual
data. It also skips over any leading indentation in the subsequent line, based
on the ~continuationIndent~ which is set by [[f:listHeadIndentLevelParser]]. This way,
we can parse tables inside list items.

#+name: f:tableLineParser
#+begin_src haskell
tableLineParser :: OrgParser [Prose]
tableLineParser = do
  _ <- string "|-"
  _ <- MP.takeWhile1P (Just "table line characters") isTableLineChar
  _ <- char '\n'
  orgParserState <- get
  _ <-
    MP.label "indentation for next table line"
      $ MP.count orgParserState.continuationIndent (char ' ')
  pure []
  where
    isTableLineChar c = c == '-' || c == '+' || c == '|'
#+end_src

The [[f:tableRowParser]] parses rows with data in them. It also skips over
indentation found in the subsequent line (if any). Unlike ~tableLineParser~, we
wrap this indentation parsing with ~MP.optional~ because we cannot tell if there
are more table rows after this or not. Contrast this with the ~tableLineParser~,
which is never expected to be the last line of a table.

#+name: f:tableRowParser
#+begin_src haskell
tableRowParser :: OrgParser [Prose]
tableRowParser = do
  _ <- char '|'
  _ <- MP.takeWhile1P (Just "table whitespace") (== ' ')
  tableCells <- MP.some tableCellParser
  _ <- char '\n'
  orgParserState <- get
  _ <-
    MP.optional
      . MP.label "indentation for next table line"
      $ MP.count orgParserState.continuationIndent (char ' ')
  pure tableCells
#+end_src

The [[f:tableCellParser]] just parses text inside a single row and column
combination --- which we call a "table cell". The main idea is that we parse
each table cell, which may not contain pipe characters in it (otherwise it
confuses =org-mode= in Emacs, which results in the table becoming formatted with
extra columns that we don't want).

#+name: f:tableCellParser
#+begin_src haskell
tableCellParser :: OrgParser Prose
tableCellParser = do
  prose <- proseParser spacesInsideProse
  _ <- MP.optional spaces
  _ <- char '|'
  _ <- MP.optional spaces
  pure $ compressProse prose
  where
    spaces :: OrgParser T.Text
    spaces = MP.takeWhile1P (Just "table whitespace") (== ' ')
    spacesInsideProse :: OrgParser T.Text
    spacesInsideProse = do
      _ <- MP.try $ MP.lookAhead (spaces >> tableCellContent)
      spaces
    tableCellContent :: OrgParser ()
    tableCellContent = void $ MP.noneOf (" \n|" :: String)
#+end_src

The ~spacesInsideProse~ is a special space consumer inside table cells, where
newlines and pipe characters are prohibited. This way, when [[f:proseParser]] uses
it to find some contiguous amount of text, it will know to stop when it sees the
pipe character (as that function does not treat pipe characters differently than
any other non-space character).

After the rows are parsed, we need to convert them to a =grid= (as part of
[[data:Table]]. We do this with [[f:rowsToTuples]].

#+name: f:rowsToTuples
#+begin_src haskell
rowsToTuples :: [[Prose]] -> [((Int, Int), Prose)]
rowsToTuples rows = concatMap rowToTuples $ zip [1 ..] rows
#+end_src

We assign each row its row index with ~zip [1 ..]~, then delegate most of the work
to [[f:rowToTuples]] where each row's table cells are given its column index to form
a completed table cell. These are simply accumulated and returned as a list. The
order of accumulation (consing) does not matter because this is ultimately fed
into a =M.Map= type, an unordered container.

#+name: f:rowToTuples
#+begin_src haskell
rowToTuples :: (Int, [Prose]) -> [((Int, Int), Prose)]
rowToTuples (rowIndex, row)
  | null row = [((rowIndex, 1), [])]
  | otherwise = fst $ foldl' f ([], 1) row
  where
    f :: ([((Int, Int), Prose)], Int) -> Prose -> ([((Int, Int), Prose)], Int)
    f (acc, colIndex) tableCell =
      ( ((rowIndex, colIndex), tableCell) : acc,
        colIndex + 1
      )
#+end_src

** Testing framework
:PROPERTIES:
:ID:       ebf0d269-79d3-408a-a6e7-baf720d73837
:END:

The tests here are all designed to read from Org source documents. There are
some benefits of writing tests this way:

  1) The raw input file (on disk) for test cases can be looked at if necessary.
     This is especially useful if the input has any special Org characters in it
     we have to escape. See the inputs for [[t:0007-blocks-ending]] and
     [[t:0004-drawers-empty]] where we need to escape some parts of the input with a
     leading comma (so as to distinguish between the Org syntax of this document
     vs the nested Org syntax of the input file we are defining).

  2) We can organize the input files in a systematic way. We use a
     ~NNNN-<description>~ naming scheme for the inputs, which all live under
     [[file:test/Lilac/ParseSpec]]. Each unique ~NNNN~ number groups together files
     meant to test similar functionality. This makes it easy to see at a glance
     what sorts of things we test.

The downside is that we have to perform lots of small read operations (IO) to
run the unit tests. But this cost is small enough that we can ignore it (we
spend far more time compiling the tests themselves).

* GOIDs file parse
:PROPERTIES:
:ID:       96f8cbda-abca-48bd-bb89-512aaac61ca8
:END:

Lilac relies on Org files that are written in Emacs (Emacs is the best
environment for writing Org files). When the ~org-id-locations-file~ and
~org-id-track-globally~ variables are set, Emacs remembers which files have which
Org IDs (where the "ID" is the UUID generated by ~org-id-get-create~ and
~org-id-store-link~).

The information stored in this file is global, because Emacs will update it
whenever it encounters Org files. For this reason we call the information
contained within this file as the "global Org IDs" or =GOIDs= for short.

We want to be able to read this file because it is automatically updated by
Emacs for us. Then we can have a good idea of where each ID comes from, so that
we know how to dereference ID links when we come across them later. Some
examples of this are:

  - Whenever we see a link with the ~id:~ as the "protocol". This can happen for
    regular links to headings or anything else.

  - When we come across a Noweb link that uses an ID to reference a code block
    located in another file.

The ability for Noweb links to reference other files is not part of Orgmode and
is Lilac's own extension. This allows source code blocks to be defined across
multiple Org files if needed. One simple example is version information that
we might want to define only in a single place, but which might be referenced
in other places, across multiple Org files.

** GOIDs parser

The syntax is of a list of list of strings, in Emacs lisp. The inner lists have
the relative file path of the Org file as the first element, followed by the
UUIDs. The UUIDs are in reverse order (probably because Emacs grows the list
right-to-left, just like Haskell's ~:~ (aka "cons") function).

Below is an example, with newlines inserted for better presentation (Emacs does
not use newlines here, and so in the wild everything is in one line):

#+begin_src emacs-lisp
(("note/raw/recreation.org" "a1e6d0d5-4540-423b-864e-b96ad06c56eb")
 ("../prog/lilac/lilac.org" "3c576a02-418b-431b-ab96-e4936e977fb7"
                            "ce9af5ef-6559-4ffb-82c1-a439214eda6d"
                            "8f5752c0-6162-4de6-9ceb-f78ba584722c"
                            "b449a097-d702-4fd6-98de-cb81f7e49177"))
#+end_src

Each Org ID is just a UUIDv4 string.

For the monad transformer stack, we don't use the [[type:OrgParser]] because we're
not parsing an Org file. Instead we use a separate ~GOIDsParser~ type.

#+name: type:GOIDsParser
#+begin_src haskell
type GOIDsParser :: Type -> Type
type GOIDsParser = StateT GOIDsParserState (<<Concrete type for Megaparsec>>)
#+end_src

When we're parsing these UUIDs, we want to check that we're not parsing in
duplicate UUIDs that have been seen elsewhere. Presumably Emacs performs this
check, but it's easy enough to do it ourselves here, so design a stateful type
we can use during the parser as we see each UUID.

#+name: data:GOIDsParserState
#+begin_src haskell
type GOIDsParserState :: Type
data GOIDsParserState = GOIDsParserState
  { seenUuids :: M.Map UUID P.OsPath
  }
  deriving stock (Eq, Show)

defaultGOIDsParserState :: GOIDsParserState
defaultGOIDsParserState =
  GOIDsParserState
    { seenUuids = M.fromList []
    }
#+end_src

You may be wondering why ~seenUuids~ is a map, not a set of UUIDs. That's because
we incrementally build up the final data structure (~M.Map UUID P.OsPath~) during
the parsing stage, and because the map can also check for membership queries
just like a set. This way we can simplify the data structures involved.

The overall [[f:goidsParser]] returns a map of UUIDs to file paths. We reset the
embedded state before returning, because we don't want to complicate tests by
keeping around the seen UUIDs.

We take care of optional whitespace because we want to be able to parse both the
native Emacs-styled UUIDs that are all on a single line of text, as well as the
output from [[f:extractGOIDs]] which adds newlines for human-friendliness.

#+name: f:goidsParser
#+begin_src haskell
goidsParser :: P.OsPath -> GOIDsParser (M.Map UUID P.OsPath)
goidsParser sourceFile = do
  _ <- ws
  _ <-
    MP.optional
      $ MP.between
        (string "(" >> ws)
        (string ")" >> ws)
        ( MP.label "Org Ids entries"
            $ MP.many
            $ goidsEntryParser sourceFile
        )
  goidsParserState <- get
  put defaultGOIDsParserState
  pure goidsParserState.seenUuids
  where
    ws :: GOIDsParser ()
    ws = void . MP.many $ char ' ' <|> char '\n'
#+end_src

Within each "entry", we need to parse the file path, and any number of UUIDs.

#+name: f:goidsEntryParser
#+begin_src haskell
goidsEntryParser :: P.OsPath -> GOIDsParser (P.OsPath, [UUID])
goidsEntryParser sourceFile = betweenParens $ do
  filepath <-
    P.unsafeEncodeUtf
      <$> MP.between
        (string "\"")
        (string "\"" >> ws)
        (MP.label "filepath" $ MP.some $ MP.anySingleBut '"')
  let fp =
        if P.isAbsolute filepath
          then filepath
          else P.combine (P.takeDirectory sourceFile) filepath
  uuids <- MP.some $ do
    uuid <- uuidParser
    _ <- ws
    goidsParserState <- get
    when (M.member uuid goidsParserState.seenUuids)
      $ fail
      $ "duplicate UUID: \""
      <> show uuid
      <> "\""
    put
      goidsParserState
        { seenUuids = M.insert uuid fp goidsParserState.seenUuids
        }
    pure uuid
  pure (fp, uuids)
  where
    betweenParens :: GOIDsParser a -> GOIDsParser a
    betweenParens =
      MP.between
        (string "(" >> ws)
        (string ")" >> ws)
    ws :: GOIDsParser ()
    ws = void . MP.many $ char ' ' <|> char '\n'
#+end_src

** GOIDs writer

Normally, Lilac users can just reuse the existing Org ID locations file that
Emacs updates directly. However, for purposes of developing Lilac itself, we
want to have this file inside the Lilac code repository's root directory. This
way, we don't have to pollute the Lilac repository with knowledge about
developer-specific settings of the value of the ~org-id-locations-file~.

So for internal, Lilac development purposes, we want to be able to write out the
~org-id-locations-file~ ourselves. The [[f:extractGOIDs]] function extracts all given
Org IDs from a list of Org files and their contents, generating a single text
string that can be written to disk. The actual reading and writing of files from
disk is done in the CLI layer.

#+name: f:extractGOIDs
#+begin_src haskell
extractGOIDs :: [(P.OsPath, T.Text)] -> T.Text
extractGOIDs orgFilesAndContents =
  let goids = foldl' buildGOIDs M.empty orgFilesAndContents
      lines = foldl' goidEntryToLines [] $ M.toDescList goids
   in "(\n" <> (T.unlines $ map ("  " <>) lines) <> ")\n"
  where
    buildGOIDs acc (orgFile, orgFileContents)
      | Right str <- P.decodeWith utf8 utf8 orgFile = case MP.runParser
          (runStateT orgDocParser defaultOrgParserState)
          str
          orgFileContents of
          Left _err -> acc
          Right (orgDoc, _orgParserState) -> M.insert orgFile (getOrgIds orgDoc) acc
      | otherwise = acc
    getOrgIds od =
      let docOrgId = getOrgId od
          acc =
            if docOrgId == nil
              then []
              else [Just docOrgId]
       in catMaybes $ foldl' f acc od.cells
    extractOrgId :: M.Map T.Text T.Text -> Maybe UUID
    extractOrgId meta
      | Just uuidText <- EM.lookup "ID" meta = fromText uuidText
      | otherwise = Nothing
    f acc cell = case cell of
      CHeading heading -> extractOrgId heading.meta : acc
      CBlock block -> extractOrgId block.meta : acc
      CMathFragment mathFragment -> extractOrgId mathFragment.meta : acc
      CFigure figure -> extractOrgId figure.meta : acc
      CTable table -> extractOrgId table.meta : acc
      CListItem {}
      CParagraph {} -> acc
    goidEntryToLines :: [T.Text] -> (P.OsPath, [UUID]) -> [T.Text]
    goidEntryToLines acc (orgFile, goids)
      | goids == [] = acc
      | Right str <- P.decodeWith utf8 utf8 orgFile,
        orgFileText <- T.pack $ show str,
        goidsLines <- map (\goid -> "    \"" <> (T.pack $ show goid) <> "\"") goids =
          ("(\n    " <> orgFileText <> "\n" <> (T.unlines goidsLines) <> "  )") : acc
      | otherwise = acc
#+end_src
