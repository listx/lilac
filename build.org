* Introduction

Originally this project started out as a fork of the [[https://github.com/pwm/nixkell][Nixkell]] project skeleton at
commit 29e78ce (Some tidying (#36), 2024-03-18), which gave us a working Haskell
development environment with many of the infrastructural issues sorted out with
Nix. The Nixkell project encourages wiping the Nixkell-specific history, but we
decided to keep that history for additional context.

* Nix
:PROPERTIES:
:ID:       74ae3eda-4656-4e07-ba5a-77fbbb704f31
:END:

Using [[https://github.com/NixOS/nix][Nix]] helps us set up a reproducible development environment, as well as
package up Lilac as a full-fledged Nix package (so that anyone with Nix can
install it by just cloning the repo and then running a Nix command to build and
install it).

** Sources (Nix dependencies)

The file [[file:../nix/sources.json]] (generated by [[https://github.com/nmattia/niv][Niv]]) declares the Nix packages
snapshot we use for reproducibility. We have to update this snapshot
periodically (for example, to use a newer [[GHC version]]).

#+name: make:Update Nix dependencies
#+begin_src makefile
update-nix:
	niv init
	niv update nixpkgs --branch <<Nixpkgs version>>
#+end_src

The ~niv~ tool is available in our [[id:73b60692-f369-4707-a7ee-434cc7a4549f][development shell]].

#+name: nix:tool-niv
#+begin_src nix
pkgs.niv
#+end_src

The ~niv init~ updates the ~niv~-generated [[file:nix/sources.nix]]. The ~niv update~
updates the [[file:nix/sources.json]].

In =niv='s terminology, the =nixpkgs= above is a "package" ([[file:nix/sources.json]]
declares all /packages/ we want to use). The =--branch ...= flag tells =niv= to use a
particular Git branch for the update (because [[https://github.com/NixOS/nixpkgs][Nixpkgs]] is a Git repository, we
can use Git branches to track a particular version). Of course, the branch is
mutable, so we have to also track the particular Git SHA that the branch was
pointing to at the time of running the =niv update= command; this information is
also stored in [[file:nix/sources.json]]. For now we track the ~nixos-YY.MM~ release
branch because it's the stable branch.

#+name: Nixpkgs version
#+begin_src txt
nixos-25.11
#+end_src

The [[file:nix/]] folder houses Nix files for our development environment. The
most important is [[file:nix/sources.nix]] which is the starting point, as it
defines the universe of imported Nix functions and packages we want to use in
order to set up our environment for Lilac.

The [[file:nix/sources.nix]] references [[file:nix/sources.json]].

#+begin_example
nix-repl> sources = import ./nix/sources.nix

nix-repl> sources
{ __functor = «lambda @ /Users/l/prog/lilac/nix/sources.nix:198:43»; "git-hooks.nix" = { ... }; "gitignore.nix" = { ... }; nixpkgs = { ... }; }
#+end_example

Importing =sources.nix= gives us ~git-hooks.nix~, ~gitignore.nix~, and ~nixpkgs~ (we can
ignore ~__functor~ as that appears to be an internal thing). This is because
[[file:nix/sources.json]] has those three entries (you use ~niv add~ to add new
entries). The latter is in quotes because it has a dot in its name (and the Nix
language normally treats the dot as an attribute access operator).

The ~nixpkgs~ is a tarball of the set of all Nixpkgs packages we have access to.

#+begin_example
nix-repl> builtins.attrNames sources.nixpkgs
[ "branch" "description" "homepage" "outPath" "owner" "repo" "rev" "sha256" "type" "url" "url_template" ]

nix-repl> sources.nixpkgs.type
"tarball"

nix-repl> sources.nixpkgs.description
"Nix Packages collection"
#+end_example

If you evaluate ~sources.nixpkgs.branch~ in the =nix-repl= you will get the same
Nixpkgs branch name as the one in [[Nixpkgs version]].

The ~gitignore.nix~ is a tarball of the [[https://github.com/hercules-ci/gitignore.nix][gitignore.nix]] project, which is just a
collection of Nix functions that allows us to ignore files in ~.gitignore~ when
packaging up our own source code repositories (in our case, Lilac itself).

Lastly, ~git-hooks.nix~ allows us to integrate https://pre-commit.com Git hooks
with Nix. See [[nix:pre-commit-checks]] to see how it's used.

** Build entrypoint
:PROPERTIES:
:ID:       2804111e-fa41-4cbe-9480-2666dd4a02e5
:END:

Let's look at =nix/release.nix= because this is our "entrypoint" for building
Lilac.

#+name: nix/release.nix
#+header: :tangle nix/release.nix
#+header: :line-label tangle
#+begin_src nix
{ lilacGitVersion ? "unknown" }:
let
  pkgs = import ./default.nix { inherit lilacGitVersion; }; # (ref:default.nix)
in pkgs.lilacPkgs.lilac
#+end_src

# We have to use ":line-label tangle" above because otherwise the linter at
# [[id:48313f7e-be73-4c22-8f97-406b3d416b52::hook-nixfmt][hook-nixfmt]] will complain about a trailing comment character (because the
# "(ref:default.nix)" above will get stripped by default during tangling, as
# described at [[id:8a920078-c090-42c4-8894-1b1cacaf0e15][Tangling behavior]]).

This file is used for creating our release builds. It ultimately
resolves to a single derivation we define in [[nix:Lilac derivation]]. So building
this with [[make:Build lilac with Nix]] results in just a single package. If we were
to put ~pkgs.lilacPkgs~ instead of ~pkgs.lilacPkgs.lilac~, Nix will build all
derivations it finds under ~pkgs.lilacPkgs~, not just the ~pkgs.lilacPkgs.lilac~ one
(this may be useful for debugging, for example).

The =default.nix= at [[(default.nix)]] is the default file used when invoking
~nix-build .~ (just as how =shell.nix= is the file for =nix-shell=). This behavior is
just how Nix behaves; for our purposes we won't be using =default.nix= directly,
because =nix/release.nix= pulls it in.

#+name: nix/default.nix
#+header: :tangle nix/default.nix
#+header: :line-label tangle
#+begin_src nix
{ lilacGitVersion ? "unknown" }:
let sources = import ./sources.nix; # (ref:import sources.nix)
in import sources.nixpkgs {
  system = builtins.currentSystem;
  config = { };
  overlays = [
    (final: prev: {
      lilacPkgs = import ./packages.nix { # (ref:import packages.nix)
        pkgs = prev;
        fetchFromGitHub = prev.fetchFromGitHub;
        inherit lilacGitVersion;
      };
    })
  ];
}
#+end_src

Anyway, =default.nix= imports our =sources.nix= (generated by =niv=) at [[(import
sources.nix)]], and also defines our overlays.

/Overlays/ are a standard Nix pattern for modifying existing Nix packages. In our
case, we are importing the universe of all Nixpkgs packages from
[[file:nix/sources.nix]], and then injecting our own =lilac= package into it.

The overlay in turn imports [[nix/packages.nix]] at [[(import packages.nix)]], which is
where most of the heavy lifting is done. In the overlay, we inject a new Haskell
package called ~lilacPkgs~ by evaluating the function in =nix/packages.nix=, which
returns what's known as an /attrset/ in Nix, which is just a key/value map.

* =packages.nix=
:PROPERTIES:
:ID:       e7a371e9-b96f-402d-9ae3-d33ee6a6a48f
:END:

We call this file =packages.nix= because it is a function which returns two very
important derivations, ~devShell~ [[(devShell drv)]] and ~lilac~ [[(lilac drv)]].

#+name: nix/packages.nix
#+header: :tangle nix/packages.nix
#+header: :line-label tangle
#+begin_src nix
{ pkgs, fetchFromGitHub, lilacGitVersion }:
let
  <<nix:devShellEnv>>
  <<nix:scripts>>
  <<nix:tools>>
  <<nix:ghc>>
  <<nix:ourHaskell>>
  <<nix:ghcVersion>>
  <<nix:Haskell overlays>>
  <<nix:projectRoot>>
  <<nix:lilacSource>>
  <<nix:buildForCI>>
  <<nix:buildFaster>>
  <<nix:pre-commit-checks>>
in {
  <<nix:devShell derivation>> # (ref:devShell drv)
  <<nix:Lilac derivation>> # (ref:lilac drv)
}
#+end_src

# We have to put two spaces before the "#" for "(ref:devShell drv)" because this
# line will get expanded to be at the start of its own line upon tangling, and
# it needs to have 2-space, not 1-space, indentation for the linter.

There's a lot to unpack here; see [[id:65e5513b-2167-44d6-bd3a-50fdd9ee020e][=ghc=]] for most of the discussions around
taming the Haskell ecosystem with Nix and [[id:73b60692-f369-4707-a7ee-434cc7a4549f][=devShell=]] for additional environment
setup concerns for local development.

** =devShell=
:PROPERTIES:
:ID:       73b60692-f369-4707-a7ee-434cc7a4549f
:END:

The ~devShell~ is the development environment, and is based on the ~pkgs.mkShell~
function.

#+name: nix:devShell derivation
#+header: :line-label tangle
#+begin_src nix
devShell = pkgs.mkShell {
  buildInputs = [ devShellEnv ]; # (ref:devShellEnv)
  shellHook = ''
    # Create a local cabal config that points to Nix store. This prevents
    # cabal from downloading and instead uses the GHC package DB.
    export CABAL_CONFIG="$PWD/cabal.config.nix"
    echo "package-db: $(ghc --print-libdir)/package.conf.d" > cabal.config.nix
    echo "with-compiler: $(which ghc)" >> cabal.config.nix

    export LD_LIBRARY_PATH=${devShellEnv}/lib:$LD_LIBRARY_PATH
    # Used when building with cabal.
    export LILAC_PROJECT_ROOT=$PWD
    # Set up Git pre-commit hooks.
    ${pre-commit-check.shellHook}
    logo
  '';
};
#+end_src

The ~devShellEnv~ at [[(devShellEnv)]] is another derivation, which is just a
collection of symlinks of all build dependencies for Lilac, plus some additional
scripts and tools, and GHC (~ghc~). This is the main "magic" of a Nix dev
environment, where suddenly you gain access to certain binaries --- all thanks
to these symlinks on the path.

#+name: nix:devShellEnv
#+begin_src nix
devShellEnv = pkgs.buildEnv {
  name = "lilac-devShellEnv";
  paths = scripts ++ tools ++ [ ghc ];
};
#+end_src

There are three main things we want to add to the ~PATH~: scripts, tools, and GHC.

The ~scripts~ are the custom shell scripts we defined earlier in [[nix/scripts.nix]].

#+name: nix:scripts
#+begin_src nix
scripts = import ./scripts.nix { inherit pkgs; };
#+end_src

The ~tools~ are packages from Nixpkgs that we want available in our development
environment. Some tools are categorized as Haskell packages (under the
=haskellPackages= prefix). We use ~ourHaskell~ to specify these tools, to make Nix
compile these tools with the same version of GHC that we are using in the [[GHC
version]].

#+name: nix:tools
#+begin_src nix
tools = [
  <<id:473e9718-2454-43d9-9f17-c895ec1b9de5::nix:tools-fe>>
  <<nix:tool-niv>>
  <<nix:tool-cabal>>
  # (ref:nix:tools-hspec-discover)
  ourHaskell.hspec-discover
  <<nix:tool-editorconfig-checker>>
  <<nix:tool-shellcheck>>
  <<nix:tool-shfmt>>
  <<nix:tool-nixfmt>>
  <<nix:tool-ormolu>>
  <<nix:tool-vale>>
];
#+end_src

[[(nix:tools-hspec-discover)]] is needed to run our tests.

This leaves us with ~ghc~, which we cover in the next section.

** =ghc=
:PROPERTIES:
:ID:       65e5513b-2167-44d6-bd3a-50fdd9ee020e
:END:

In [[nix:ghc]] (referenced by [[nix/packages.nix]]) we use ~ghc~ that Nixpkgs provides,
but teach it about the Haskell dependencies (libraries) that Lilac uses. This
means you can invoke ~ghci~, and then load any library you want (needed by Lilac)
into it. See the file ~.ghc.environment.<arch>-<GHC version>~ (written by Cabal at
the project root) for a list of such dependencies.

#+name: nix:ghc
#+begin_src nix
hlib = pkgs.haskell.lib;
ghc = ourHaskell.ghc.withPackages
  (_: hlib.getHaskellBuildInputs ourHaskell.lilac);
#+end_src

The ~ourHaskell~ bit is the [[GHC version]] we want to use from Nixpkgs, but with a
few overlays to tweak it a bit.

#+name: nix:ourHaskell
#+begin_src nix
lib = pkgs.lib;

# (ref:nix:ourHaskell-ourHaskell)
ourHaskell = pkgs.haskell.packages.${ghcVersion}.extend
  (lib.composeManyExtensions haskellOverlays);
#+end_src

The ~ghcVersion~ ultimately comes from [[GHC version]]. It's just the string =ghc= plus
the numeric bits of [[GHC version]] without the dots in it, because this is how
Nixpkgs names GHC versions.

#+name: nix:ghcVersion
#+begin_src nix
ghcVersionWithoutDots = lib.replaceStrings [ "." ] [ "" ] "<<GHC version>>";
ghcVersion = "ghc" + ghcVersionWithoutDots;
#+end_src

Going back to ~ourHaskell~, the ~haskellOverlays~ are straightforward enough. The
first overlay ~injectLilac~ adds a new Haskell package called ~lilac~. The other one
is ~tweakLilacBuild~ which adjusts the build process so that the [[id:3c576a02-418b-431b-ab96-e4936e977fb7][Template
Haskell code]] can use the ~LILAC_GIT_VERSION~ environment variable to use as the
output for the ~--version~ flag.

#+name: nix:Haskell overlays
#+header: :line-label tangle
#+begin_src nix
haskellOverlays =
  [ heavyDeps jailbreaks injectExternalPackages injectLilac tweakLilacBuild ];

heavyDeps = final: prev:
  let
    heavyPackages = [
      "skylighting"
      "skylighting-core"
      "skylighting-format-ansi"
      "skylighting-format-blaze-html"
      "skylighting-format-latex"
      "unicode-collation"
      "unicode-transforms"
      "pandoc-types"
    ];
  in lib.genAttrs heavyPackages (name: buildForCI prev.${name});

jailbreaks = final: prev: {
  <<jailbreaks:unicode-data>>
};

injectExternalPackages = final: prev: {
  <<injectExternalPackage:citeproc>>
};

injectLilac = final: prev: { # (ref:injectLilac)
  lilac = buildFaster (prev.callCabal2nix "lilac" lilacSource { });
};

tweakLilacBuild = final: prev: {
  lilac = prev.lilac.overrideAttrs (drv: {
    buildPhase = ''
      export LILAC_GIT_VERSION=${lilacGitVersion}
      echo "Using LILAC_GIT_VERSION $LILAC_GIT_VERSION"
    '' + drv.buildPhase;
  });
};
#+end_src

The ~lilacSource~ at [[(injectLilac)]] is the source code needed to build Lilac, and
~buildFaster~ is some Haskell build configuration options we pass in to
configure the Lilac build process.

** =lilacSource=
:PROPERTIES:
:ID:       ae7b1a31-970d-41e4-b15a-8d7f383e1502
:END:

We want to tell Nix to use the local directory path of the project root as the
starting point (this way, we can build Lilac without having to make a Git commit
first --- that is, we could choose to create a Git commit, then pull this repo
back down from Git at that commit to start building it, but for now we just
build from disk regardless of Git).

#+name: nix:projectRoot
#+begin_src nix
projectRoot = ../.;
#+end_src

We have to use the parent directory because the ~projectRoot~ is relative to the
location of [[nix/packages.nix]], which is itself in a child folder (=nix=)
in the actual project root.

Anyway, we are now confronted with a new problem: this means Nix will use /all/
files in the project root. We have to pare it down to only those bits that
actually matter for ~cabal~.

We use the [[https://github.com/hercules-ci/gitignore.nix/blob/637db329424fd7e46cf4185293b9cc8c88c95394/docs/gitignoreFilter.md][gitignoreFilterWith]] function to filter out all paths that are already
defined inside the existing [[.gitignore]]. We also filter out additional
files that are not needed for building Lilac, such as the woven HTML files in
[[(nix:lilacSource-extraRules)]].

#+name: nix:lilacSource
#+header: :line-label tangle
#+begin_src nix
gnf =
  import (import ./sources.nix)."gitignore.nix" { inherit lib; }; # (ref:gnf)
lilacSource = lib.cleanSourceWith {
  src = projectRoot;
  name = baseNameOf projectRoot + "-src"; # (ref:lilacSource name)
  filter = let # (ref:gnf-memoization)
    filterFunc = gnf.gitignoreFilterWith {
      basePath = projectRoot;
      # (ref:nix:lilacSource-extraRules)
      extraRules = ''
        .*
        ,*.html
        ,*.nix
        ,*.sh
        ,*.toml
        image
        Makefile
        nix
      '';
    };
  in path: type: filterFunc path type;
};
#+end_src

The ~gnf~ at [[(gnf)]] stands for "gitignore Nix functions". As for the actual
[[.gitignore]] itself, we prefer to use a single ~.gitignore~ file at the root
of the project.

Using ~nix repl~ we can inspect the ~gnf~ function directly:

#+begin_example
nix-repl> nixpkgs = (import ./sources.nix).nixpkgs

nix-repl> gnf = import (import ./sources.nix)."gitignore.nix" { lib = nixpkgs.pkgs.lib; }

nix-repl> builtins.attrNames gnf
[ "gitignoreFilter" "gitignoreFilterWith" "gitignoreSource" "gitignoreSourceWith" ]
#+end_example

Back to ~lilacSource~, it has a ~name~ at [[(lilacSource name)]] consisting of the
project root folder, plus a =-src= suffix. When building Lilac, this name will be
used for generating a Nix store entry for all of the source code used for
building the project:

#+begin_example
...
Running phase: unpackPhase unpacking source archive /nix/store/z4lzldnnna5ghxqs84s8r87gxvr4bwnj-lilac-src
...
#+end_example

It's important that we use a ~let~ binding for ~filterFunc~ at [[(gnf-memoization)]].
This memoizes the expensive part of the computation. If we don't do this, it
will re-parse the ~.gitignore~ files it finds (recursively, from the project root)
all over again each time it is called.

** Optimized Haskell packages

*** ~buildFaster~ function

The ~buildFaster~ function customizes the first argument ~haskellPkg~ which
is a Haskell package, which should be the output of calling ~callCabal2nix~.

#+name: nix:buildFaster
#+begin_src nix
buildFaster = haskellPkg:
  let
    confFns = [
      hlib.dontHyperlinkSource
      hlib.dontCoverage
      hlib.dontHaddock
      hlib.disableExecutableProfiling
      hlib.disableLibraryProfiling
      hlib.dontBenchmark
    ];

  in lib.pipe haskellPkg confFns;
#+end_src

The general idea is to speed up the build by opting out of some things. We want
to optimise the build for speed when developing locally, because we want to
build Lilac as quickly as possible to tighten the feedback loop when working
with [[tangle-loop.sh]].

You may want to consult the GHC documentation to make sense out of some of these
flags. For example, see [[https://downloads.haskell.org/ghc/latest/docs/users_guide/runtime_control.html][runtime system (RTS) options]] for the RTS flags.

*** ~buildForCI~ function

This is similar to [[nix:buildFaster]], but is slightly different. It was created
because SourceHut CI kept failing with OOM errors (Haddock being the main
culprit). We had to /enable/ library profiling because some packages failed to
build without it.

#+name: nix:buildForCI
#+begin_src nix
buildForCI = haskellPkg:
  let
    confFns = [
      hlib.dontHyperlinkSource
      hlib.dontCoverage
      hlib.dontHaddock
      hlib.disableExecutableProfiling
      hlib.dontCheck
      hlib.dontBenchmark
    ];

  in lib.pipe haskellPkg confFns;
#+end_src

** =lilac= attribute

Recall that the [[nix:Haskell overlays]] added the Lilac package to the top-level
Nixpkgs set of packages, which we named ~ourHaskell~ [[(nix:ourHaskell-ourHaskell)]].
We expose it now as just ~lilac~.

#+name: nix:Lilac derivation
#+begin_src nix
lilac = ourHaskell.lilac;
#+end_src

So this means any Nix expression that imports [[nix/packages.nix]] will be able to
refer to the Lilac Haskell build as ~lilac~. This is what we do in [[nix/default.nix]]
where we decide to name the attribute set from the evaluation of
[[nix/packages.nix]] as ~lilacPkgs~ (so it would be ~lilacPkgs.lilac~). And
consequently, [[nix/release.nix]] references ~lilacPkgs.lilac~ so that only this
particular package gets built if we choose to feed this file into ~nix-build~.

You can inspect the ~lilacPkgs.lilac~ derivation by running =nix repl= from the
project root, then typing into the REPL the following example:

#+begin_example
x = import ./nix/default.nix { lilacGitVersion = "someversion"; }
x.lilacPkgs.lilac
#+end_example

The first line calls the expression in =default.nix= with the argument for
~lilacGitVersion~. The next line =x.lilacPkgs.lilac= accesses the ~lilac~ attribute
which is just a derivation (an installable Nix package).

** External Haskell packages from beyond Nixpkgs

Sometimes we might want to use a Haskell package that's not in Nixpkgs (for
example, if the version in Nixpkgs is broken and the fix for that package is
already in upstream but not yet in Nixpkgs). And so we allow users to optionally
specify packages by the GitHub commit.

To add something directly from GitHub (such as if the latest version on Hackage
is still too old for us), we can put the following inside the
~injectExternalPackages~ section in [[nix:Haskell overlays]].

#+begin_src nix
  foo-bar =
    pkgs.haskell.lib.dontCheck (
      prev.callCabal2nix "foo-bar" (
        builtins.fetchFromGitHub {
          owner = "x";
          repo = "y";
          rev = "0000000000000000000000000000000000000000";
          sha256 = "00000";
        }
      ) {}
    );
#+end_src

For example, the above will override the default version of ~foo-bar~ with the one
defined via Git.

** Removing version bounds

You can remove version bound checks on package ~foo-package~ like this inside the
~jailbreaks~ section of [[nix:Haskell overlays]].

#+begin_src nix
foo-package = pkgs.haskell.lib.doJailbreak(prev.foo-package);
#+end_src

Jailbreaking is a common technique to work around packages that sometimes have
unnecessarily strict version bounds.

* Known issues and workarounds

Here we document various breakages and our workarounds for them.

** =citeproc=

The version of =citeproc= on Nixpkgs 25.04 is 0.8.1.1, which is too old. So pull
in a newer one.

citeproc = buildFaster (prev.callCabal2nix "citeproc" (let
  repo = fetchFromGitHub {
    owner = "jgm";
    repo = "citeproc";
    rev = "e5f22f0b0f7662524ff52883582d883316f4c113";

in "${repo}") { });
#+end_src

** Sentinels
:PROPERTIES:

In a =Makefile=, given a rule

#+begin_src makefile
thing: dep1 dep2
	do-something
#+end_src

=make= will assume that the output of ~do-something~ will be a file named =thing= and
will only run ~do-something~ if either =dep1= =dep2= have a newer timestamp than
=thing=.

For cases where ~do-something~ does /not/ result in generating the file =thing=, we
use "sentinel" files (files that we ~touch~ at the end of a build rule) so that
=make= won't re-run the rule if it sees that the sentinel file is still newer than
the listed dependencies.

#+end_src

** Compile Lilac with Lilac

Lilac can compile Org files into object files (=*.lobj=) and use those object
files to create archive files (=*.larc=). Compilation helps us catch errors within
object files, especially for finding broken (internal) links to other Org file
headings, code blocks, etc. See [[id:b9c034c1-5499-44e6-855c-6c16e1693cb8][Compile]] for a deeper discussion.

*** Object files

#+name: make:Compile sources
#+begin_src makefile
obj_files = $(org_files:%.org=%.lobj)

<<make:Batch compile Org files>>
<<make:Build archive>>
#+end_src

The naive way of building object files involves a rule like this:

#+begin_src makefile
%.lobj: %.org
	lilac compile $<
#+end_src

But this doesn't work well, because it will invoke the ~lilac~ CLI multiple times,
once for each Org file that needs to be compiled because the ~:~ creates
individual targets. This is why we have [[make:Batch compile Org files]] instead:

#+name: make:Batch compile Org files
#+begin_src makefile
$(obj_files) &: $(org_files)
	lilac compile $?
	touch $(obj_files) # (ref:touch obj_files)
#+end_src

This batch compilation works by specifying the ~&:~ ([[https://www.gnu.org/software/make/manual/html_node/Multiple-Targets.html][grouped targets]]). This way,
if any object file is outdated (older than the ~org_files~), we can invoke ~lilac
compile ...~ just once on all needing-to-be-compiled Org files (specified with
the ~$?~ [[https://www.gnu.org/software/make/manual/html_node/Automatic-Variables.html][automatic variable]]). This doesn't matter too much when running the
[[id:77786b08-6211-47b8-940d-6aaefc17ec47::tangle-loop.sh][tangle-loop.sh]] because that reacts as soon as one of the Org files is saved, but
it does matter more when we compile everything from scratch (such as when we
wipe the object files as a sanity check).

We have to update the timestamps of all object files at the end of the batch
compilation at [[(touch obj_files)]]. To see why this is needed, consider the
following. Suppose the timestamps could be like this for the Org files:

| File   | Time |
|--------+------|
| a.org  |    0 |
| a.lobj |    0 |
| b.org  |    1 |
| b.lobj |    0 |

If we now see that ~b.org~ is newer, and then run ~lilac compile b.org~, we'll only
update the ~b.lobj~ timestamp (say, to 2).

| File   | Time |
|--------+------|
| a.org  |    0 |
| a.lobj |    0 |
| b.org  |    1 |
| b.lobj |    2 |

However, now ~a.lobj~ has an older timestamp of 0, compared to ~b.org~ which still
has a timestamp of 1. And so Make will think it will need to run the batch
compilation again (it will think this way forever until we manually also update
the timestamp of ~a.org~). To avoid this scenario from happening, we run ~touch
$(obj_files)~ so that now all objects get the timestamp update. So in this new
scenario, the timestamps will look like

| File   | Time |
|--------+------|
| a.org  |    0 |
| a.lobj |    2 |
| b.org  |    1 |
| b.lobj |    2 |

and all of the object files will be newer than the Org files, which will
correctly inform Make that it won't need to run batch compilation again.

*** Archive

** Tangle Lilac with Lilac
:PROPERTIES:
:ID:       77786b08-6211-47b8-940d-6aaefc17ec47
:END:

We can tangle Lilac with itself.

#+name: make:Tangle sources
#+begin_src makefile
tangle: lilac.larc
	lilac tangle lilac.larc --out-dir .
	touch tangle
#+end_src

The =lilac= script is the one we created in [[nix/scripts.nix]] to automatically build
Lilac with Cabal.

The ~tangle~ file is a [[id:b649d761-1103-47be-86e4-56a7362a5ecc][sentinel file]] to help GNU Make avoid running the
tangling operation if there is nothing to do, very much like [[gitignore:Makefile sentinel:lint]].

#+name: gitignore:Makefile sentinel:tangle
#+begin_src gitignore
tangle
#+end_src

Making Lilac tangle itself is advantageous because it's faster than running
=org-babel-tangle= inside Orgmode in Emacs. However, doing this means we lose out
on being able to run the tangling function automatically on save, which we
historically did with [[https://github.com/yilkalargaw/org-auto-tangle][org-auto-tangle]] by having ~#+auto_tangle: t~ in our Org
file.

So we need another way of tangling every time this file (=build.org=) is changed.
We can do that with [[https://facebook.github.io/watchman/][Watchman]], but that would be unnecessarily heavy-handed
because we don't need to watch a directory or multiple files. Instead we can
just have a script which sleeps one second and checks the timestamp of
=build.org= (and other files we care about), and if it's different than before,
tangle it (and also run tests and weave and lint as needed). That's what we do
in [[tangle-loop.sh]].

#+name: tangle-loop.sh
#+header: :tangle tangle-loop.sh
#+header: :shebang #!/usr/bin/env bash
#+begin_src bash
set -euo pipefail

SCRIPT_ROOT="$(dirname "$(realpath "$0")")"

<<f:tangle-loop:get_tangled_program_files>>
<<f:tangle-loop:clean_build_files>>
<<f:tangle-loop:reset_tangled_program_files>>
<<f:tangle-loop:reset_everything>>
<<f:tangle-loop:tangle>>
<<f:tangle-loop:run_all_checks>>
<<f:tangle-loop:watch>>

main()
{
	__test_hs=1
	if [[ "${1:-}" == "fe" ]]; then
		__test_hs=0
	fi
	__ok_to_lint=1

	readarray -t org_files < <(find . -type f -regex '.+\.org$')
	watch "${org_files[@]}"
}

main "$@"
#+end_src

The ~main()~ entrypoint above sets up two global variables ~__test_hs~ and
~__ok_to_lint~, before entering the loop in [[f:tangle-loop:watch]].

#+name: f:tangle-loop:watch
#+begin_src bash
watch()
{
	local s1
	local s2
	local files=("$@")

	s1="$(stat -c %Y "${files[@]}")"

	run_all_checks # (ref:initial-call-tangle)
	while true; do
		s2="$(stat -c %Y "${files[@]}")"
		if [[ ! "${s1}" == "${s2}" ]]; then
			s1="${s2}"
			run_all_checks
		fi
		sleep 1
	done
}
#+end_src

[[f:tangle-loop:watch]] checks for timestamps on the files we're interested in every
second, and runs [[f:tangle-loop:run_all_checks]] if it detects a
modification timestamp change.

#+name: f:tangle-loop:run_all_checks
#+begin_src bash
run_all_checks()
{
	tangle || true  # (ref:tangle-one)
	if tangle; then # (ref:tangle-two)
		if ((__test_hs)); then
			if ! make -C "${SCRIPT_ROOT}" test; then # (ref:unit-tests)
				reset_everything
				return
			else
				__ok_to_lint=1
			fi
		fi
	fi

	echo "----------------------------------------"

	if ! time make -C "${SCRIPT_ROOT}" weave; then
		reset_everything
		return
	else
		__ok_to_lint=1
	fi

	echo "----------------------------------------"

	if ((__ok_to_lint)); then
		make -C "${SCRIPT_ROOT}" lint || true
	fi
}
#+end_src

[[f:tangle-loop:run_all_checks]] tangles first, runs all tests, weaves, and finally
runs the linter. If any of the earlier steps fail, then the later steps abort
execution.

[[f:tangle-loop:run_all_checks]] calls ~tangle()~ twice (at [[(tangle-one)]]
and [[(tangle-two)]]), because if we modify Lilac's behavior (by editing a Haskell
block), the newly-compiled Lilac will be created in the first invocation of
~tangle()~. The second invocation will then use the new Lilac version to tangle
itself again. It's a simple (albeit ugly) way of ensuring that we're always
tangling with the latest Lilac version.

[[f:tangle-loop:run_all_checks]] also runs the unit tests at [[(unit-tests)]], as a
convenience function, but only if the previous call to ~tangle~ succeeds. This
way, we only try to run the unit tests if Lilac can tangle itself. As for the
unit tests, the exit code is ignored with ~|| true~ because oftentimes the tests
break when we're adding new tests (without this, we would break out of the ~while~
loop, which is not desirable).

The initial call to ~run_all_checks()~ in the ~watch()~ function (outside of the
~while~ loop) at [[(initial-call-tangle)]] is there for convenience, just in case
we've modified the =build.org= file outside of a =tangle-loop.sh= session.

#+name: f:tangle-loop:tangle
#+begin_src bash
tangle()
{
	mapfile -t tangled_program_files < <(get_tangled_program_files) # (ref:tangled-files-array)
	if ! time make -C "${SCRIPT_ROOT}" tangle; then
		reset_everything
		return 1
	fi
	__ok_to_lint=1
	return 0
}
#+end_src

[[f:tangle-loop:tangle]] tangles source code; however it also resets the
~tangled_program_files~ global variable, because it may be the case that the
program files are slightly different than before when we tangle new code blocks
from an Org file.

If anything goes wrong during tangling, we call [[f:tangle-loop:reset_everything]]
to reset all tangled code blocks to their previously known (good) state in
[[f:tangle-loop:reset_tangled_program_files]], and also delete any intermediate
build artifacts to get us to a clean state.

#+name: f:tangle-loop:reset_everything
#+begin_src bash
reset_everything()
{
	reset_tangled_program_files
	clean_build_files
}
#+end_src

[[f:tangle-loop:reset_everything]] calls ~reset_tangled_program_files()~ and also
~clean_build_files()~, which cleans up incremental build artifacts like ~*.lobj~ and
~*.larc~ files. This is needed if we make a change to the structure of [[id:5df15f17-c630-4ddf-bade-66084c430a07::data:OrgDoc][data:OrgDoc]]
or anything else that's serialized out to a file and read back in. For example,
if we rename a field to a new name, then any existing build artifact with the
old name will become invalid and fail to parse; in this case the best thing to
do is remove the old build artifact (via ~clean_build_files()~) and build these
files again from scratch.

The [[f:tangle-loop:reset_tangled_program_files]] function assumes that the current
Git commit has a working Lilac version. Based on this assumption, it runs ~git
checkout~ on tangled files at [[(git-checkout)]] if there are any errors. So if it
turns out we edited Lilac's own sources and broke the build, we want to undo the
broken (tangled) changes, which we can do by simply resetting the Haskell source
code back to the checked-in state with ~git checkout~. This is safe because the
changes we want to try out are always stored in the Org files (=build.org=, etc),
because we use Literate Programming. If we didn't use Literate Programming we
would be very cautious of resetting any source code files, but we don't have
that worry here.

#+name: f:tangle-loop:reset_tangled_program_files
#+begin_src bash
reset_tangled_program_files()
{
	__ok_to_lint=0
	echo >&2 "Error encountered; cleaning Haskell tangle paths."
	>/dev/null git checkout -- "${tangled_program_files[@]}" \ (ref:git-checkout)
		Makefile \
		.gitignore \
		nix
}
#+end_src

Note that the ~tangled_program_files~ is created by calling
[[f:tangle-loop:get_tangled_program_files]] at [[(tangled-files-array)]], which only
looks at the tangled Cabal, Haskell, Nix, or shell files. This means you can
make changes to the original Org files to make Lilac compile or pass tests
again, as needed, by tweaking those code blocks responsible for these file
types.

#+name: f:tangle-loop:get_tangled_program_files
#+begin_src bash
get_tangled_program_files()
{
	git -C "${SCRIPT_ROOT}" grep -E '^#\+header: :tangle' -- '*.org' \
		| awk '{print $3}' \
		| grep '\.\(cabal\|hs\|nix\|sh\)$'
}
#+end_src

Lastly, [[f:tangle-loop:clean_build_files]] just runs [[make:Clean]].

#+name: f:tangle-loop:clean_build_files
#+begin_src bash
clean_build_files()
{
	echo >&2 "Cleaning build files."
	make -C "${SCRIPT_ROOT}" clean
}
#+end_src

For weaving, we use the ~doc~ directory.

#+name: make:Weave

Because [[id:21ccfaf6-cd49-46b6-9075-4952f3eea207::f:lilacWeave][f:lilacWeave]] writes CSS to the ~css~ subdirectory, the CSS ends up getting
written to ~css/default.css~. This ~css~ directory will not exist in CI (when
Lilac is cloned and built on a fresh machine), so we have to create it.
Otherwise, the [[id:7e6758c8-a642-4cfa-9e03-498163d6ce68::make:Build prod JS][make:Build prod JS]] rule will fail because the
[[id:90d66ea1-a994-4fdb-b969-c28cec04352d::cfg:figwheel-main.edn][cfg:figwheel-main.edn]] expects the ~css~ directory to exist.

#+header: :tangle css/.gitkeep
#+begin_src txt
#+end_src

We make Git ignore the ~weave~ file because it's a [[id:b649d761-1103-47be-86e4-56a7362a5ecc][sentinel file]].

#+name: gitignore:Makefile sentinel:weave
#+begin_src gitignore
weave
#+end_src

We add the ~--write-css~ flag at [[(weave-write-css)]] because we want to regenerate
(every time) the CSS file from Haskell sources in [[id:7147b743-084d-4abc-8561-5417c7fe10b3::f:genCss][f:genCss]], in case anything in
there changed. However we don't do the same for JavaScript (we don't supply
~--write-js~), because we don't want to overwrite the same ~js/lilac.js~ path
used by [[id:783de6bf-e36b-4c9e-a405-2a86d0897795::make:Start frontend development environment (CLJS REPL)][make:Start frontend development environment (CLJS REPL)]].

To clarify, there are 2 flavors of JavaScript artifacts, development and
production. The development version is not a single JavaScript file and is not
optimized; this allows us to get a ClojureScript REPL where we can play around
with a direct connection to a browser. The production flavor is a single,
optimized JavaScript file and does not have ClojureScript REPL support. The
production flavor is copied out to another file ~js/lilac.js.injectme~ by
[[id:7e6758c8-a642-4cfa-9e03-498163d6ce68::sh:update-injectable][sh:update-injectable]]. It is this separate file which is injected into Haskell in
[[id:e31aed94-98f5-4c47-b9ab-e82a529e5be7::f:lilacJs][f:lilacJs]], so that Lilac is able to generate this file on its own.

When we're developing Lilac with Lilac, we generally want to only look at the
development version of the JavaScript because this allows REPL interaction. This
means we cannot use the ~--write-js~ flag to Lilac in [[make:Weave]], because doing so
would make Lilac overwrite the development file (which shares the same
~js/lilac.js~ target path that Lilac targets with the ~--write-js~ flag) with
its own (pre-baked) JS file.

For serving the woven (development) HTML pages through a server (instead of
making the browser fetch it via the ~file://~ protocol), see [[id:6d407e24-fb34-460a-83bd-7b39cf7a56bb][Frontend]].

:END:

There are two ways to build =lilac=. The first option, ~build~, builds with
=cabal=, Haskell's default tooling for building Haskell programs.

#+name: make:Build lilac with Cabal
#+begin_src makefile
build: $(org_files) lilac.cabal
	cabal build
	touch build
#+end_src

This results in building the binary. The binary will end up in an obscure path
like =./dist-newstyle/build/.../lilac=. You can get this path with ~cabal list-bin
lilac~. To run the binary from that path, use ~cabal run lilac -- [LILAC
OPTIONS...]~ where =[LILAC OPTIONS ...]= are the options for =lilac=. The double dash
is required to tell =cabal= to stop interpreting command line options (to leave
them to be handled by =lilac=).

The above ceremony with =cabal run= might be a little bit annoying during
development. This is why [[nix/scripts.nix]] includes ~lilac~ which acts as a shell
wrapper around those various ~cabal~-centric options for us. Specifically, the
[[cabal-run-invocation]] uses some default flags:

  - ~-j~ to use all available CPU cores for ~cabal~

  - ~+RTS~ to mark the start of runtime system options

  - ~-N~ to use all available CPU cores for ~lilac~

  - ~-RTS~ to mark the end of runtime system options

#+name: cabal-run-invocation
#+begin_src bash
cabal run lilac -v0 -j -- +RTS -N -RTS "$@" (ref:nix/scripts.nix-cabal-run-flags)
#+end_src

We have to ignore the =build= file because it's just a [[id:b649d761-1103-47be-86e4-56a7362a5ecc][sentinel file]].

#+name: gitignore:Makefile sentinel:build
#+begin_src gitignore
build
#+end_src

Another option is to build with Nix, which wraps everything up for public
consumption, as a Nix package.

#+name: make:Build lilac with Nix
#+begin_src makefile
LILAC_GIT_VERSION := $(shell git describe --abbrev=10 --always --dirty)
build-release: $(org_files) lilac.cabal
	nix-build ./nix/release.nix \
		--argstr lilacGitVersion $(LILAC_GIT_VERSION)
	touch build-release
#+end_src

#+name: gitignore:Makefile sentinel:build-release
#+begin_src gitignore
build-release
#+end_src

You can run the version of Lilac built with Nix via ~result/bin/lilac~, which we
wrap as ~lilac-nix~ in the [[nix/scripts.nix]] as well.

* Linters via ~pre-commit~
:PROPERTIES:
:ID:       b4d2ace9-2d11-4606-b7a3-ce9ad7763c1a
:END:

Git has an elaborate system of hooks that it can run every time you do something
important with it. A common hook is a /pre-commit/ hook, which will run just
before creating a new commit. It's useful to add linters and other things in
here.

There is a project called https://pre-commit.com which is in the business of
standardizing Git hooks. One of the selling points is that for the various
formatters and linters that it already supports, by default it only runs them
against changed files in the Git index. This optimization is annoying to set up
separately for each formatter or linter, so it's nice to let ~pre-commit~ handle
it for us.

In addition, ~pre-commit~ supports all of the usual Git hooks, not just
=pre-commit=. This can come in handy..

** =git-hooks.nix=
:PROPERTIES:
:ID:       e2a2e1b9-bc08-4b17-9826-e8ac1f5df13b
:END:

The https://github.com/cachix/git-hooks.nix project brings ~pre-commit~ into Nix,
so that we can define all of the hook infrastructure in a reproducible way with
Nix (such as using specific versions of linters, formatters, etc).

For us we already have the set of linters and formatters we are interested in
defined inside our [[id:73b60692-f369-4707-a7ee-434cc7a4549f][development shell environment]] in [[nix:devShellEnv]], so we tell
~git-hooks~ to reuse those same tools.

While formatting isn't important for tangling (the computer doesn't care about
formatting), it's important for weaving because we want code blocks in woven
output to still look decent and consistent.

#+name: nix:pre-commit-checks
#+begin_src nix
gitHooksPkgs = import (import ./sources.nix)."git-hooks.nix";
pre-commit-check = gitHooksPkgs.run {
  src = projectRoot;
  hooks = {
    <<hook-editorconfig-checker>>
    <<hook-nixfmt>>
    <<hook-ormolu>>
    <<hook-shfmt>>
    <<hook-shellcheck>>
    <<hook-lilac-lint>>
    <<hook-unit-test>>
    <<hook-vale>>
    <<hook-sort-file-contents>>
  };
};

toolOpts = opts: builtins.concatStringsSep " " opts;
#+end_src

By default the above tools will only run on changed files going into a new
commit (and these changed file names will be passed to each check). If you want
to run against all files to check for any existing violations, run ~pre-commit
run --all-files~.

The =pre-commit= tool writes a configuration file at =.pre-commit-config.yaml=. We
ignore this for Git because it has local machine-specific paths in it (and
because it's also just autogenerated by =pre-commit= based on our Nix
configuration above, thereby making it easy enough to reproduce as needed if we
delete it by accident).

#+name: Generated pre-commit config
#+begin_src gitignore
.pre-commit-config.yaml
#+end_src

** =EditorConfig=

[[https://editorconfig.org/][EditorConfig]] is a specification for setting some universal properties about
files in a project.

#+name: .editorconfig
#+header: :tangle .editorconfig
#+begin_src txt
root = true

[*]
charset = utf-8
end_of_line = lf

[Makefile]

[*.sh]

tab_width = 8

[js/lilac.js.injectme] # (ref:.editorconfig-injectme-binary)
insert_final_newline = false
trim_trailing_whitespace = false
end_of_line = unset
charset = unset
#+end_src

The ~root = true~ is required because the EditorConfig specification is
version-control agnostic and does not understand Git's notion of a project or
repository root. When EditorConfig plugins check whether a file complies with
EditorConfig configuration, it simply searches for the current or any parent
folders for the ~.editorconfig~ file. Setting the ~root = true~ tells the plugin to
stop searching upwards beyond the current file.

[[(.editorconfig-injectme-binary)]] prevents EditorConfig from trying to interpret
the ~lilac.js.injectme~ file (see [[id:7e6758c8-a642-4cfa-9e03-498163d6ce68::.gitattributes][.gitattributes]]) as a text file.

** Audit tangled vs tracked files
:PROPERTIES:
:ID:       bbdbcad0-7fb3-447d-a393-d840fc1df9b1
:END:

We should detect whether we've accounted for all tracked files via Literate
Programming. That is, we want to detect any files that are checked into source
control but which are not being tangled from an Org file, because that's an
anti-pattern and goes directly against LP principles.

Of course, there can be exceptions, such as generated code (code spat out by a
binary), binary files (like images), and metadata such as ~.gitmodules~. We
account for these exceptions in the arguments to ~git-ls-files~ in [[id:4375ba0d-b917-4d32-92f4-884be63659fe::(json:RawProjectConfig-nonTangledPathspecs)]].

The concerns above are addressed by the ~lint~ subcommand of the Lilac CLI, as
described in [[id:a0b8abe5-5b1c-4dc4-b482-5dbd4b233471][Linting tangled paths]]. What we have below is just the integration
with the pre-commit hooks system.

#+name: hook-lilac-lint
#+begin_src nix
lilac-lint = {
  name = "lilac-lint";
  enable = true;
  always_run = true;
  entry = "lilac lint lilac.larc";
  pass_filenames = false;
};
#+end_src

We set ~pass_filenames = false~ because we don't have to pass in any of the
changed filenames to the ~lint~ subcommand of Lilac, because Lilac reads all
tangled paths from the archive and also reads all tracked files from Git.

** Run lilac unit test before pushing
:PROPERTIES:
:ID:       caa38bf7-52ae-4246-8be0-8b2c9e58ccc2
:END:

Running unit tests requires compiling the tests, which takes more than a few
seconds. So it's a little bit resource intensive and we don't want to run it on
every commit. So we instead run it when we ~git push~ to save our work to a
remote, by putting in the ~pre-push~ stage at [[(pre-push)]].

#+name: hook-unit-test
#+header: :line-label tangle
#+begin_src nix
unit-test = {
  name = "unit-test.sh";
  enable = true;
  always_run = true;
  entry = "./unit-test.sh";
  pass_filenames = false;
  stages = [ "pre-push" ]; # (ref:pre-push)
};
#+end_src

#+name: unit-test.sh
#+header: :tangle unit-test.sh
#+header: :shebang #!/usr/bin/env bash
#+begin_src bash
set -euo pipefail

SCRIPT_ROOT="$(dirname "$(realpath "$0")")"

<<shell-func-is-wip>>

main()
{
	>/dev/null pushd "${SCRIPT_ROOT}"

	<<shell-skip-if-wip>>
	<<shell-fail-if-dirty-tree>>
	<<unit-test-run>>
}

main "$@"
#+end_src

We don't want to run unit tests if the current commit (~HEAD~ in Git) is a
work-in-progress (WIP) commit.

#+name: shell-func-is-wip
#+begin_src sh
is_wip()
{
	git show -s --format=%s HEAD \
		| grep -qi '^\(update\|wip\|fixup\|f \|s \)'
}
#+end_src

#+name: shell-skip-if-wip
#+begin_src sh
if is_wip; then
	echo >&2 "skipping (WIP commit)"
	return
fi
#+end_src

We can't just invoke ~make test~ directly to run unit tests for this hook, because
it may be the case that the working tree is dirty. If the tree is dirty, the
results of the unit test may no longer reflect what we are pushing to the remote
(which would only be the clean commits, not any of the dirty stuff), so we need
to abort if the tree is dirty.

#+name: shell-fail-if-dirty-tree
#+begin_src sh
if [[ -n $(git status --porcelain) ]]; then
	echo >&2 "$0: dirty tree"
	return 1
fi
#+end_src

For invoking the unit tests, we run ~make test~ (like we normally do during
development).

#+name: unit-test-run
#+begin_src sh
if make test; then
	echo >&2 "OK"
else
	echo >&2 "$0: failed"
	return 1
fi
#+end_src

** GHC compiler warnings
:PROPERTIES:
:ID:       74186bab-a0f9-40cf-b5e2-54dd774a034d
:END:

Our strategy with GHC warnings is to first turn on as many as possible ([[ghc:Warn
everything]]), followed by some flags to turn off harmless or overly pedantic
warnings.

#+name: GHC warning flags
#+begin_src txt
<<ghc:Warn everything>>
<<ghc:Disable safe Haskell>>
<<ghc:Disable missed specialisations>>
<<ghc:Disable missed extra shared libs>>
#+end_src

We turn on all warnings with ~-Weverything~.

#+name: ghc:Warn everything
#+begin_src txt
-Weverything
#+end_src

Now we disable some warnings that are not that important.

#+name: ghc:Disable safe Haskell
#+begin_src txt
-Wno-unsafe -Wno-safe -Wno-missing-safe-haskell-mode
#+end_src

"Safe Haskell" is essentially a dialect of Haskell that has stronger guarantees
about referential transparency. It's an interesting idea, but not one worth
pursuing in this program.

#+name: ghc:Disable missed specialisations
#+begin_src txt
-Wno-missed-specialisations
-Wno-all-missed-specialisations
#+end_src

These "missed specialisations" warnings are not really useful for us because we
don't (as of yet) care too much about performance. Plus they seem to be about
library functions we are importing.

#+name: ghc:Disable missed extra shared libs
#+begin_src txt
-Wno-missed-extra-shared-lib
#+end_src

Since GHC 9.12.2, we've been getting warnings like the following on Mac OS. As
it's benign, ignore these warnings.

** GHC threaded runtime flags

#+name: GHC threaded flags
#+begin_src txt
-threaded
-rtsopts
-with-rtsopts=-N
#+end_src

The ~-threaded~ flag links the executable with the threaded runtime, which can
manage multiple OS threads (as opposed to the default runtime which is
single-threaded).

The ~-rtsopts~ option allows the processing of RTS control options given either
on the command line or via the =GHCRTS= environment variable.

The ~-with-rtsopts=-N~ option lets the runtime choose how many simultaneous
threads to use (at runtime). Typically this means using all cores on the
machines.

For options that should only affect Cabal builds, we want to specify such

Define ~-O0~ to speed up Cabal builds.

#+name: cabal-faster-dev-build

#+end_src

* Searching with =ripgrep=

The [[https://github.com/BurntSushi/ripgrep][ripgrep]] (=rg=) tool is a popular tool used for searching text. While =rg=
respects the [[id:ae7b1a31-970d-41e4-b15a-8d7f383e1502::.gitignore][.gitignore]], we cannot solely rely on it because it will still
search tangled source code. We want to tell =rg= to ignore those files because
when we search for something we always want to look at the source of truth,
which in most cases (except for generated code) is an Org file.

To make =rg= behave as we want, we have to provide it a separate =.rgignore= file.

#+name: .rgignore
#+header: :tangle .rgignore
#+begin_src rgignore
,*.cabal
,*.hs
,*.nix
,*.lobj
,*.sh
csl-styles
test/*
#+end_src

We can't put these inside [[id:ae7b1a31-970d-41e4-b15a-8d7f383e1502::.gitignore][.gitignore]] because doing so will remove these files
from bundling it into a Nix package in [[nix:lilacSource]] (we actually want the
tangled content because they are required for the build).

* Ordering Git diffs

By default, Git orders diffs alphabetically by the filename (presumably to
guarantee determinism when running ~git diff~). However, you can change this
behavior to sort the diffs in a different way, by using /orderfiles/ (see ~man
git-diff~). Below is our orderfile:

#+name: git-orderfile
#+header: :tangle .git-orderfile
#+begin_src txt
# Org files
plan.org
release-notes.org
user-manual.org
index.org
build.org
types.org
parse.org
compile.org
tangle.org
weave.org
fe.org
cli.org
,*.org

# Infrastructure
,*.nix
,*.json
,*.sh
,*.yml
.*

# Haskell
cabal.project
,*.cabal
,*.hs

# ClojureScript
,*.edn
,*.cljs

# Tests
test*
#+end_src

The most important files are the Org files, because they serve as the source of
truth for Literate Programming in this project. So they appear first. The rest
of the groupings are not strictly necessary, because the diffs there will be
redundant with the diffs in the Org files; nevertheless we categorize them here
for completeness.
